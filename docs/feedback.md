### 补充：2026-10-10，InnoDB 第一版

WaterRun 看过《事务性与现代化：InnoDB》第一版的低清预演后的直接意见（原话照录）。第一版因此作废，按下表重做。

| 编号 | 反馈（原话） | 制作上的处理 |
|---|---|---|
| P6 | 「镜头一直晃来晃去要减少，作为科普视频不要干扰注意力」 | 停留时不做往复平移或环绕；镜头只在站与站之间移动，停留时最多极慢地单向推近。「任意 3 秒有可见变化」由跟着旁白出现的高亮、标注与图形变化满足，不靠镜头摆动凑数 |
| P7 | 「美术风格需要契合 MySQL && InnoDB 的风格，而不是抄袭之前别的项目的」；「设计语言不应该用之前 150s 的那个，完全不同的系列，完全重做的」 | 开工先取证讲解对象自己的视觉（标志、官网样式表、官方文档插图的配色、字体与图形），从中建立设计语言，并写明出处。与近期各片、尤其其他系列并排比较：只换强调色、保留同一套纸色底与平涂版式，不算新的设计语言 |
| P8 | 「不要一直提及本实验，事实上只要开头 MySQL 9.7 的一句话即可」 | 演示环境只在开头交代一次；正文直接讲现象与机制，实验步骤写成叙述，不反复说「本实验」「实验中」「日志显示」。实测与示意的区分留在画面标注和 FACTS 里 |
| P9 | 「参考 MyISAM 对引擎本身的介绍，要通俗易懂，易于理解」；「解释也有很多缺口，比如出现 SDI 时，动画并没有展现是什么的解释，目标观众——不了解 InnoDB 的读者看的懵逼」；「包括脏读之类的你都没解释」 | 每个术语第一次出现时，旁白用一句话讲清它是什么、为什么需要，画面同时给出对应的图形；讲不清或不需要的术语不出现。原始数值（页类型编号、十六进制、日志代码）只在支撑解释时出现。交审时附「术语—解释句」清单 |
| P10 | 「确保画面信息量完整的同时流畅自然」 | 画面要承载旁白的全部要点，同时运动连贯；不以删减信息换流畅，也不以堆叠文字换完整 |
| P11 | 「重新组织内容，制作新版本，搞明白定位，参考 MyISAM 的，那个讲的就还可以」；「主线还是清晰的，MyISAM 引入事务性 → 介绍事务性 → InnoDB 这样，所以一般引擎介绍 10 分钟，他有 15」 | 系列定位是「一个引擎怎样实现」：引擎部分按一集的正常体量组织（约 10 分钟），沿「怎么放、怎么找、怎么改、怎么并发、出错怎么办」展开；为引出概念增加的部分单独计时，不挤占引擎部分 |
| P12 | 「片尾不用配音」 | 片尾名单只在画面上展示，旁白不读 |
| P13 | 「配音体现 InnoDB 的现代感，又有一些年头没那么新」 | 声音的气质按讲解对象的年代与定位选择；交审时附试听，由策划者确认 |

### 2026-10-19：「刷一下」与制作者口吻（核心）

| 编号 | WaterRun 的反馈 | 后续要求 |
|---|---|---|
| P24 | 视频的一个普遍问题是「刷一下」：观众信息还没看完，画面突然就过去了。作为核心反馈。例：OpenCart 07:12 | **F04 升为核心规则**。实测 OpenCart 主片 6:58–7:16（每 0.5 秒一帧）：这一段大部分时间镜头推在右半边，左侧订单面板不在画内；「写入被拒，停在这里」与左侧红色报错框约 7:12.5 才完整出现，7:13.0 已进入下一段的转场模糊，完整可读不到 1 秒，而这一屏有十余处文字。要求先排信息再排动作，关键状态完整出现后按「1.5 秒 + 字数 ÷ 5 字/秒」留足稳定时间 |
| P25 | 画面上「只列常量名，不列值」这类话极具 AI 味道，人做视频根本不会提默认的事情 | 新增 F15：不写说明制作取舍、脱敏或默认处理的自我说明（同类还有「示意 · 按源码分支构造的只读组」）。不展示的东西直接不展示；来源署名一行即可；口径限定只在会造成误解时用一句自然的话说 |
| P26 | 非「XX 秒」系列的时长上限只是参照：长一点、多点留白（但不要过度），总比观众刷过去一脸懵好 | 与 F04 一起执行：先保证关键画面读得完，再看总时长；只有秒速通这类以时长为题的系列把时长当硬约束。留白用在结论、对比和状态变化之后，不在过渡处拖时间 |
| P27 | InnoDB 的配乐太弱，OpenCart 也是；和 MyISAM 那期差不多的配乐是不错的 | 加强 F06：配乐要有存在感，先有一层贯穿全片、有低频分量的铺底，再加动机与节奏；不能以稀疏的钢琴或和弦代替。实测电平（2026-10-19，主混音减去无配乐版的积分响度）：MyISAM 配乐比旁白低约 18 dB、InnoDB 约 15 dB，相差不大，差别主要在织体是否持续、低频是否饱满 |
| P28 | 看了草案：MyISAM 的视觉设计不太体现 MySQL 与 MyISAM，InnoDB 更糟糕；PostgreSQL 这一集的还不错 | 新增 F16：视觉取自讲解对象自己的材料，随便一帧都能认出在讲什么。PostgreSQL 一集为正面对照：直接取 postgresql.org 样式表的颜色、Open Sans 与文档部件（标题装饰线、表格、提示框、psql），左上角常驻大象标志；MyISAM、InnoDB 两集记为反面，原片未改 |

两条对以后每一部片子都适用，在制片按规则版本 2026-10-19.2 重新同步。OpenCart 原片中的两处问题尚未修改。

“事实有出处”只回答陈述是否可靠，不回答它是否值得放进这部片子。实验做得多、代码读得细、数字精确，都不能替代观众从一个问题走到一个答案的过程。下表保留初次源稿分析；随后已补充八部实际母版抽帧、平台对应抽样与精确时间线，见 [逐片复盘](reviews/2026-10-09.md#3-逐片复盘)。制作者的诊断与 P0 的直接评价分开记录，不将抽样检查写成连续通看。

| 对象 | 源稿中可定位的现象 | 叙事风险与修改方向 |
|---|---|---|

每次文案交审先给出四项：目标观众已有的知识；看完应能回答的一个核心问题；各章怎样推进这个问题；哪些查到的材料决定不讲。每章按“问题 → 必要解释或演示 → 本章答案 → 下一问”检查。删除一段不影响主线，就考虑移入说明或后续选题；保留它必须能说清用途。

## 5. 制作改进与验收

下表是本轮提出并写入制作文档的要求；秒数是制作起点，不是已验证的普遍阅读速度。现有成片已经按同日复盘的范围取样检查，但尚未修改、重新渲染，不把文档变更记为问题已解决。

| 项 | 具体做法 | 检查与完成条件 |
|---|---|---|
| 叙事保持题目与受众 | 先写核心问题和逐章答案，再选择证据、例子与数字；实验、源码细节和历史材料按解释需要取舍 | 文案交审及成片复查都核对“标题承诺 → 章节推进 → 结尾回答”；未能对应的段落删减或另立选题。叙事检查先于视听包装检查 |
| 章节卡与内容卡可读 | 先分清标题卡与承载论点的内容卡。短标题的完整可读停留从 2 秒起安排；标题加要点的内容卡从 3–5 秒起安排，随字数和图解复杂度增加。入场和退场另计；信息太多先拆，不靠加快刷屏 | 每种语言记录文字全部到位至开始遮挡/退场的时段；正常速度播放能读完并辨认关系后再换场。不能只检查某张静帧或章节总长 |
| 转场与动作有区别 | 先说明这次动作表现什么关系：跟随数据、展开结构、保留对象再换视角等；擦除可以用，但不能成为所有章节与所有新片的默认答案 | 将本片与近期两部的开头、换章、解释段各取一段并排比较；若只是换颜色或扫动方向，重新设计。连续性保留在字体、图形含义和结构上 |

## 6. 后续维护

- 每次新片开工或改片先读本页及最近相关复盘，按第 7 节填写本片的反馈应用表；收尾时逐项对应复盘。涉及 C3–C12 的技术陈述先完成相应事实核查。
- 发布后读取主评论和楼中楼，记下日期、覆盖范围、来源类别、评论定位和上下文；新增记录追加，不覆盖历史意见。
- 反馈的状态分为「已记录」「待事实核查」「待修改」「已修改待复核」「已验证」。每次关闭问题都附具体片段、文件或提交、实际检查结果；没有检查结果不写已验证。
- 本轮状态：P0、P4、P5 已完成脚本、时间线与实际成片抽帧定位，未改片；P1 的正面方法已作逐片分析，未代用户新增评分理由；P2 已测量并检查代表卡，待修改；P3 已检查动效实现、取样画面、配乐配置与声音数值，连续观感和主观听感仍待复核；C3–C8、C12 的技术陈述未在本轮重新核查。流程修订已实施，原片问题没有因此关闭。
- 本页不自动触发改片、重配音或发布。需要实质修改旁白时，继续按 [workflow.md](workflow.md) 的文案审查约定执行。
- **已发布或已交付的片子不因新增反馈返工。** 新反馈的落实对象是以后的片子：写进本页与 `feedback-rules.json`，在开工检查里避开。旧片的问题落盘留档、保持原样与线上版本一致，作为负面对照；不重新配音、不重渲、不改写发布记录。只有尚未交付、仍在制作的片子按当时的规则改到可交付为止。
