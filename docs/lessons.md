# 经验规则

每一条都来自一次真实的反馈：策划者的评价、观众的评论，或制作中摔过的跟头。它们写成对所有片子都成立的规则，让下一部片子不再犯同样的错。[质量标准](standards.md) 讲成片要达到什么样子，这里讲最容易在哪里失手、怎样查。

## 怎样用

- **开工前读这一阶段的几条。** `node kit/tools/lessons.js show --stage <阶段>`（例如 `--stage script`、`--stage design`）只打印这一阶段的规则。不必通读全表。
- **交付前逐条下结论。** 每部片子在 `review/lessons.json` 里给每条规则写一个结论：`pass`（附证据：成片的语言、时段、怎么查的）、`n/a`（附理由）或 `open`（已知未解决，交付时写进 README「交付」）。`pending` 表示还没考虑过，`check.js --final` 不放行。
- **规则变了，在制的片子跟着变。** 新增规则或某条的要求改变时（`rev` 加一），运行 `node kit/tools/lessons.js <视频> sync`，变化的几条回到 `pending`。只改措辞不影响已有结论。
- **已发布的片子不返工。** 新规则用在以后的片子上；旧片的问题记在它自己的 README「评价与复盘」里，作为对照。

## 反馈怎样变成规则

1. **记原话。** 策划者的评价、评论区的意见，原样记进 [反馈记录](log/feedback.md)，编上 P（策划者）或 C（评论）号，写明日期、哪部片子、哪个时刻。同时在那部片子 README 的「评价与复盘」里引用编号。
2. **找原因。** 在成片上定位问题（时刻、帧、源码行），分清是叙事、画面、声音还是流程的问题。
3. **提炼成通用的话。** 先看能不能并进已有的一条（改写它、`rev` 加一）；确实是新问题，才新增一条。规则里不写片名，片名放进「案例」。
4. **能查的做进工具。** 能用工具查的（例如片尾是否配音、文字的可读时长、样式是否雷同），做成检查，在规则的 `auto` 里注明。
5. **改 `docs/lessons.json`，运行 `node kit/tools/lessons.js render`** 重新生成下面的规则表；`npm run check:repo` 核对规则、文档与反馈记录的编号一致。

### 立项

#### F01 一个核心问题贯穿全片

开工先写下观众看完能回答的一个问题，以及每章怎样推进它。标题、开头、每章、结尾回答的是同一个问题；相关但回答别的问题的段落删去或另立选题。定长短片的每一场都直接回答片名的问题。先通读连贯文案，确认解释与章节推进成立，再铺开视听制作；形式和自动检查通过不能代替内容质量。

- **为什么**：材料可靠不等于该放进来；版本清单、历史与实现参数挤掉主线时，观众不知道在看什么。
- **怎样查**：先通读文案，复述主问题、解释路径与结论，指出跳步和无关内容；再在成片上标出提出问题、各章推进、结尾回答的时刻。README 记清取舍与未解决的问题，每一段说得出它为什么留在这里。
- **也用于**：文案、验收
- **案例**：正面 [myisam](../videos/database-engines/myisam/)、[postgresql](../videos/database-engines/postgresql/)；反面 [lean4](../videos/in-seconds/lean4/)、[openclaw-opencode-v2](../videos/standalone/openclaw-opencode-v2/)、[openclaw-hermes](../videos/standalone/openclaw-hermes/)、[web-login](../videos/in-seconds/web-login/)
- **来源**：P0、P5、P21、P33、P53、C10、C13（见 [反馈记录](log/feedback.md)）

#### F35 介绍产品讲它能做什么、什么时候用，不搬说明书

介绍一个产品或项目（宣发、功能介绍）时，每项功能只回答两件事：它能帮观众做什么，观众什么时候用它。行为保证（「做完会告诉你改了哪些文件」）、边界条件（「模型请求还走原来的网络」）、默认值（「默认都关着」）、实现细节（「手册用到哪本读哪本」）和免责（「这些是本地估算，不是账单」）不进旁白：README 写了，不等于片子要讲。免责只留会直接伤到观众的那一条，一句话说完。长列举压成一句概括（「还有更多限额可选」），除非列举本身就是卖点（几种模式、几个平台）。不要靠补细节去凑时长区间；讲完了还短，就问策划者。

- **为什么**：DSHU 宣发片第 4 稿把 README 里每项功能的保证、边界、默认值和免责都写进了旁白。策划者亲自改写时几乎全删（估算从 5:37 缩到约 4:50），只留「能干什么、你什么时候用」，并要求「整理风格和重心, 包括去掉你的风格和中心, 落盘文档, 之后自己写可以学习」。
- **怎样查**：逐句标出属于哪一类：「能做什么 / 什么时候用」，「保证 / 边界 / 默认值 / 实现 / 免责」，还是「列举」。第二类的每一句问：观众不知道这一句，会不会装错、用错、吃亏？不会就删。列举超过三项又不是卖点的，改成一句概括。（工具：暂无工具）
- **也用于**：文案、验收
- **案例**：反面 [deepseek-harness-uncensored](../videos/open-source-projects/deepseek-harness-uncensored/)
- **来源**：P124（见 [反馈记录](log/feedback.md)）

### 取证

#### F02 一个例子走完每一步，控制理解负担

用同一个具体例子走完机制：每一步交代输入、变化、原因和结果。讲多层系统时先建立整体结构与输入输出，再定位并展开局部，局部细节始终能回到全程中的位置；取证同时保留结构关系与一次操作的完整路径，不能只留内部字段。先讲清概念，再给术语、历史和数字。先定本片引入几个新名词，超出就删；每个术语第一次出现就用一句话讲清它是什么、为什么需要。难点先分到足够的时间，再安排包装与转场。

- **为什么**：「有例子」不等于讲清楚；名词堆叠、概念跳跃时，观众跟不上。局部拆得再深，缺少整体结构和部件之间的关系，仍解释不了系统怎样工作。
- **怎样查**：正常速度从输入跟到输出，每一步的原因都在画面或旁白里；列出全片新名词与它们的解释句。取证可还原整体结构与一条完整操作路径；文案与画面里的每个局部都说得出它位于整体哪里、负责哪一步。每个页号、编号第一次出现时，画面演出它从哪来：哪一页的哪一项指过来、按什么比较选中，不让它凭空跳到下一步。
- **也用于**：文案、设计、验收
- **案例**：正面 [myisam](../videos/database-engines/myisam/)、[two-factor-auth](../videos/in-seconds/two-factor-auth/)；反面 [lean4](../videos/in-seconds/lean4/)、[innodb](../videos/database-engines/innodb/)、[postgresql](../videos/database-engines/postgresql/)、[firebird](../videos/standalone/firebird/)、[web-login](../videos/in-seconds/web-login/)、[openclaw-hermes](../videos/standalone/openclaw-hermes/)、[openclaw-opencode-v2](../videos/standalone/openclaw-opencode-v2/)
- **来源**：P9、P17、P18、P34、P50、C10、C11、P80、P118（见 [反馈记录](log/feedback.md)）

#### F07 取证画面脱敏

演示数据与终端回显从源头就用干净的环境和通用路径，不把真实的个人目录、主机名、凭据、内网信息带进素材；脱敏在数据源做，不在画面上遮。

- **为什么**：曾有成片的终端画面露出个人目录。
- **怎样查**：逐屏核对最终 MP4、字幕、封面与说明文字里的路径、用户名与地址。
- **也用于**：实现、验收
- **案例**：正面 [luainstaller](../videos/open-source-projects/luainstaller/)

#### F09 反馈与证据分清来源

策划者的意见、观众原话、作者自评、制作者推断分开记录，各带日期与出处。涉及事实的异议回到本片 FACTS 核查后再下结论；工具通过不等于观感通过。

- **为什么**：把一条评论当成共识、把推断当成事实，都会让后面的修改走偏。
- **怎样查**：反馈记录逐条有来源类别与定位；技术异议有核查结论或「未核」。
- **也用于**：发布与反馈

### 文案

#### F03 名称、比较与边界在第一次出现时交代

名称、版本、比较对象和适用条件在第一次出现时说清。做比较时，两边共享同一个任务与同一套口径；说「更早」「更快」时说出和什么比。图注写含义：一串原始格式（例如快照的「最早进行中:下一个号:进行中列表」）不直接上屏，写成一句话；画面上的编号、数字写明是谁的。

- **为什么**：口径交代晚了，观众先形成错误印象，后面的纠正很难追回来。
- **怎样查**：逐个核对名称与比较第一次出现时的旁白、画面和结论；译文保留限制条件。
- **案例**：反面 [wsl](../videos/standalone/wsl/)、[dense-vs-moe](../videos/in-seconds/dense-vs-moe/)、[postgresql](../videos/database-engines/postgresql/)
- **来源**：P4、C5、C6、C7、C8、C14、P106（见 [反馈记录](log/feedback.md)）

#### F10 单集独立可懂

每一集只靠它自己就能看懂：直接提出本章的问题，必要的背景在本片补齐；不要求观众记得前一集，不用「上一期第几个问题」导航。

- **为什么**：系列连续性被做成了对前集的反复回指。
- **怎样查**：逐句检查对其他集的引用，各自说得出必要性；没看过前集的人能跟完。
- **案例**：反面 [innodb](../videos/database-engines/innodb/)
- **来源**：P16（见 [反馈记录](log/feedback.md)）

#### F11 外文材料给中文释义

需要观众读懂的外文标题、引文和术语，在画面上给出准确的中文释义；长材料移出主画面，只留支撑论点的那一句。

- **为什么**：把翻译的负担交给观众，增加了理解成本。
- **怎样查**：中文成片中每段外文材料旁都有可读的中文对应，且留够阅读时间。
- **也用于**：实现
- **案例**：反面 [innodb](../videos/database-engines/innodb/)
- **来源**：P19（见 [反馈记录](log/feedback.md)）

#### F13 陌生或历史对象先交代来龙去脉

讲观众不熟悉的对象，先从熟悉的情境引入：它是什么、什么年代、当时解决什么问题、为什么值得看，再给本片的路线。新旧对照固定具体的版本与任务，不用今天的数据倒推过去。讲人造出来的东西，交代是谁、在什么处境下做出来的、当时要解决的难处，留一两个有趣的细节；篇幅服从本片主线。

- **为什么**：一上来就讲系统内部，多数观众不知道对象是什么、为什么要看。
- **怎样查**：第一次观看的人能复述对象、年代和本片要走的路线。
- **案例**：反面 [opencart-1-5-admin](../videos/standalone/opencart-1-5-admin/)
- **来源**：P22、P110（见 [反馈记录](log/feedback.md)）

#### F14 片尾名单不配旁白，制作指令不进文案

文案只包含会被说出的话。署名、模型分工、开源链接只在画面上展示；片尾用无旁白的静默 cue（空字幕、pause、credits: true）保留时长。「片尾显示……」这类制作指令不写进文案。

- **为什么**：片尾被配过音，制作说明被混进过文案。
- **怎样查**：导出的校对稿里没有制作指令；成片片尾没有人声，名单完整可读。（工具：script-review.js 检查片尾 cue 无旁白）
- **也用于**：实现
- **案例**：反面 [opencart-1-5-admin](../videos/standalone/opencart-1-5-admin/)
- **来源**：P12、P23（见 [反馈记录](log/feedback.md)）

#### F15 不写制作者口吻的自我说明

画面和旁白只放观众需要的内容。不写说明制作取舍、脱敏、默认处理的话（如「只列常量名，不列值」「示意 · 按源码分支构造」），不反复提「本实验」「日志显示」；不展示的东西直接不展示。数据来源一行署名即可；口径限定只在会造成误解时，用一句自然的话放进正文。

- **为什么**：这类话一看就是模型写的，正常人做视频不会提默认的事。
- **怎样查**：逐屏列出说明性的小字与旁白，问一句「正常人做视频会不会写这句」，不会就删。
- **也用于**：实现
- **案例**：反面 [opencart-1-5-admin](../videos/standalone/opencart-1-5-admin/)、[innodb](../videos/database-engines/innodb/)
- **来源**：P8、P25（见 [反馈记录](log/feedback.md)）

#### F26 制作方主动通读、主动改文案

制作方对成片负责，也就对文案负责，不机械照搬已确认的稿。每次加句、删句、改章节之后通读整章：数字与画面、章节卡与旁白、前后的称呼是否一致（例：加了一个问题，「四个问题」要跟着改成「五个」）。发现错误或更好的讲法就主动改，改动写进 review/NOTES.md；改了含义的，交校对者确认后再配音。

- **为什么**：MyISAM 第 4 稿加了「改和删」，这一章实际讲五个问题，章节卡和旁白仍写「四个」，制作方照着配了音、做了画面，直到策划者指出「指五为四」。策划者随后要求：「你有很大的自由权，有能力，可以主动的修改文案，而不是傻傻的遵循。」
- **怎样查**：对照 review/NOTES.md 与当前 script.js：改句之后是否通读过整章？章节卡、数字、列举的个数与画面是否一致？制作中发现的文案问题是主动改的，还是等人指出的？
- **也用于**：配音、实现
- **来源**：P73（见 [反馈记录](log/feedback.md)）

#### F28 层层递进：先问题，再例子，最后起名字

每个新概念按这个顺序进场：先说观众会碰到的问题（「要按名字找 Alice，总不能把 47 页从头翻到尾」），再在贯穿的例子上演一次，最后才给名字和一句话的定义（「这叫……」）。概念第一次讲清时就选定一个说法和一个画法，后面各章沿用同一个（例：xmin 到 xmax 是一段可见范围，xmax 为 0 就一直延续下去；之后的查询、修改、并发、删除、回绕都用这条范围讲）。不提前用到后面才讲的东西（还没讲 VACUUM 就说「这一笔由 VACUUM 来记」）；两个相似的参数默认值不同，就点明是两样东西（「索引默认 90；表也有自己的，默认 100」），不让观众以为前后矛盾；不同实验测得的数（三个不同的事务号）不并列上屏当成同一件事。内容不删，宁可多一句铺垫。

- **为什么**：PostgreSQL 一集 r7、r8：概念一个接一个，名字先于问题出现，前后说法打架，策划者看到 9 分钟就看不下去——「那么快那么多概念观众怎么跟得上」「不要假设观众比如看着xmin xmax就知道是事务可见性范围」「前面说默认90后面又默认装满」「不能让观众出现"疑问"的情绪」。按本条重写第 3 稿后：「粗看整体叙事好太多了, 一开始就应该这样的」。
- **怎样查**：列出全片的新名词：每个都写出引出它的问题句、演示它的例子、给它起名的句子，三者依次出现；搜索每个名词第一次出现的位置，不早于讲清它的那一句；同名参数、同一个数字在各章说法一致。以只看过前几集的观众把文案通读一遍，标出每一处会冒出「这是什么」「为什么」的地方并改掉。
- **也用于**：验收
- **案例**：正面 [myisam](../videos/database-engines/myisam/)、[postgresql](../videos/database-engines/postgresql/)
- **来源**：P86、P87、P88、P93（见 [反馈记录](log/feedback.md)）

#### F32 台词分清这一次的例子与普遍规律

讲一次具体的实验或例子时，台词要让人听得出「这是这一次」：用「此时」「这一次」「例子中」「在这次实验里」点明，不要写成像在陈述所有情况的规律（「做一次检查点，这一页才写回文件」应为「此时做一次检查点……」；「别人的名字都是 User 加编号」应为「例子中别人的名字都是……」）。真正普遍成立的机制另起一句说，并有出处支撑；例子里的数字（文件长到多少、第几个叶页）只属于这一次。

- **为什么**：MongoDB 一集的台词把实验里的某一次检查点、演示数据的命名规律说得像普遍事实，策划者指出「你的台词把具体的例子讲的和通用的所有情况似的」，并逐句改成「此时做一次检查点」「例子中别人的名字都是」。
- **怎样查**：通读文稿，标出每一句讲的是「这一次实验／这个例子」还是「普遍机制」；前者看有没有「此时、这一次、例子中」之类的指认，后者看 FACTS 里有没有支持普遍说法的出处。（工具：暂无工具）
- **也用于**：配音、验收
- **案例**：反面 [mongodb](../videos/database-engines/mongodb/)
- **来源**：P123（见 [反馈记录](log/feedback.md)）

#### F33 系列里讲过的概念不再下定义，按观众所处的阶段写

写系列的后几集时，先列出前几集已经讲清的概念（事务、提交、B 树、索引、检查点、日志之类），这些在台词里直接用，不再「……叫某某」地重新下定义，注解也不再给通用定义，只写这一集的对象自己的做法（例如「4096 份文档只有两层：根页下面直接就是叶页」）。需要勾连时一句话点到前几集（「和 InnoDB、SQLite 一样」），并在 FACTS 里转录前几集的出处。只有这一集第一次出现的概念才交代是什么（F31）。

- **为什么**：MongoDB 一集是数据库引擎系列第六集，台词仍然重新定义事务（「要么全部生效，要么全部撤回」「生效的那一下，叫提交」）和 B 树（「这样一层层往下指的树，叫 B 树」），策划者指出「总体就是事务 B树这类概念在前面早就出现了」「搞明白阶段, 不要重新说明定义」。
- **怎样查**：列出这一集用到的概念，标出哪些是前几集讲过的；逐个看台词与注解有没有重新下定义，有就删去或改成勾连前几集的一句。（工具：暂无工具）
- **也用于**：设计、验收
- **案例**：反面 [mongodb](../videos/database-engines/mongodb/)
- **来源**：P123（见 [反馈记录](log/feedback.md)）

#### F36 用观众熟悉的参照和口吻说话，去掉制作方的腔调

先找观众已经熟悉的东西作参照：同类产品里的同类功能（「和 Claude Code 的 /btw 类似」）、圈内的说法和梗。一句类比胜过一段机制解释；类比前先核实对方确实有这个功能，只说「类似」，不比细节。对观众说话、给建议（「你不知道选什么的时候，选这个就行」）；先说观众的需求（「你想搞明白进度如何」），再给命令和名字。功能挂在产品名下介绍（「DSHU 另外引入了……」），不用结构性的过渡句。去掉制作方的腔调：路标句（「先说最要紧的」「下面这些」）、安抚句（「谁也不碍着谁」「就专心写」）、对称的两段式（「不用……也不用……」「不管是……还是……」）。一件事一句话说完，不拆成「这部分用的是…… / 具体是……」两句。口吻放开，事实不放开：梗和口语照样逐句对 FACTS；核对只改与出处冲突的地方，不借核对把作者的说法换成自己更稳妥的措辞。

- **为什么**：DSHU 宣发片：策划者看第 3 稿说「你的用语都太claude了」；第 4 稿改成口语，仍是整理过的口语。策划者亲自改写：加了 Claude Code、Codex 的类比，「梁文峰还是梁文谷」「再套一层马甲」「否则后果自负」这样的直白说法，以及「你不知道选什么的时候，选这个就行」这样的建议。改写稿里有几处与出处不符（「参考」应为「沿用」），核对后按出处修正；制作方顺手把「实验功能」「可选的」也换成了自己更稳妥的措辞，策划者要求改回：「s5 保留 实验功能的说法」「x11 保留 可选的输入预测」。
- **怎样查**：通读全稿：每个新功能有没有用观众熟悉的东西作参照？圈出路标句、安抚句、对称两段式，逐个删掉或改写。同一件事是否拆成了几句。每个类比、每个梗背后的事实，在 FACTS 里都有出处。（工具：暂无工具）
- **也用于**：验收
- **案例**：反面 [deepseek-harness-uncensored](../videos/open-source-projects/deepseek-harness-uncensored/)
- **来源**：P124（见 [反馈记录](log/feedback.md)）

### 配音

#### F12 读音与语义断句

列出专名、多音字、数字和长句的试听清单，逐个确认读法；停顿按语义安排，字幕怎么切不决定口播怎么停。多音字逐个用耳朵核对：Whisper 回听会把同一个字的不同读音转成同一个字（cháng、zhǎng 都是「长」），查不出读音错。通用的读法替换（例如把数据的「行」换成同音的「航」）加进读法表之后，把全稿被替换的地方逐个列出来核对，排除表要列全。

- **为什么**：成片里出现过读错与断句错，ASR 没有全部筛出来；「再长一层」读成了 cháng，回听的文本仍是「长」。
- **怎样查**：逐句听实际音轨；ASR 只用来筛候选，读错与断句的判断以人耳为准，听不到的如实写明。中文稿对着交审稿的「多音字清单」逐条听，已由 SAY 表或 tts 改写的也听。（工具：asr.js 筛查候选；script-review.js 导出稿列出多音字清单（供人耳核对，不是闸门））
- **案例**：反面 [innodb](../videos/database-engines/innodb/)、[postgresql](../videos/database-engines/postgresql/)
- **来源**：P14、P20、P81、P94、P105（见 [反馈记录](log/feedback.md)）

#### F17 配音有精神，先试听再合成

合成全片之前，用包含专名、长句、列举和解释句的代表段试听候选音色与语速：句子有起伏，强调处有重音，长句不被念成一串平读，讲解有往前推的感觉。音色气质贴合对象的年代与定位。音色记录里标为停用的不再选。代表段的试听交策划者确认。

- **为什么**：读得对不等于读得好，「懒洋洋」的语气与不合适的音色都被直接否定过。
- **怎样查**：成片后连续试听开头、难点段与章间；响度、语速数值和 ASR 都不检查语气。
- **案例**：正面 [postgresql](../videos/database-engines/postgresql/)；反面 [tmux](../videos/in-seconds/tmux/)、[opencart-1-5-admin](../videos/standalone/opencart-1-5-admin/)、[web-login](../videos/in-seconds/web-login/)
- **来源**：P13、P29、P38（见 [反馈记录](log/feedback.md)）

### 设计

#### F16 视觉取自讲解对象

先收集讲解对象自己的视觉材料（标志、官网样式表的颜色与字体、官方文档的部件、真实界面），以这些语汇作图，画面上有一个常驻的身份标识。随便截一帧，不看字幕也认得出在讲什么。比对时看官方页面实际渲染出来的样子（截图并排），版式、字重、部件与插图的画法都算，不只读样式表里的颜色。

- **为什么**：通用的「科技感」版式换个主题也能用，等于没有设计。
- **怎样查**：从成片任取几帧，不看字幕判断能否认出对象；列出每种颜色、字体、部件取自哪份官方材料。并排放一张官方页面的截图比对。
- **案例**：正面 [postgresql](../videos/database-engines/postgresql/)、[luainstaller](../videos/open-source-projects/luainstaller/)；反面 [myisam](../videos/database-engines/myisam/)、[innodb](../videos/database-engines/innodb/)
- **来源**：P7、P28、P30、P109（见 [反馈记录](log/feedback.md)）

#### F18 每章一个主画面

每一章都有一个以讲解对象为主角、说得出名字的主画面，尺度、层次与动作共同承载本章的解释，让人看完记得住。逐行出现、高亮、淡入可以用于引导注意，但不能代替该章需要讲清的结构、过程或关系；不靠镜头晃动、特效堆叠或元素数量充数。

- **为什么**：主画面需要完成解释任务；只陈列标签或只追求冲击力，都会让观众记不住内容。
- **怎样查**：连续观看每章，说出主画面表达了什么、观众如何从中理解结构或变化；图形与动作未承担解释任务时记为未通过。以实际理解效果判断，不以动作种类和数量打分。
- **也用于**：实现、预览迭代、验收
- **案例**：反面 [postgresql](../videos/database-engines/postgresql/)
- **来源**：P31、P53（见 [反馈记录](log/feedback.md)）

#### F20 图形承载内容，形式服从功能

画面上的每个图形都说得出它服务于哪一段解释、表达哪个对象或关系，说不出就删；不要求一句旁白换一个画面（F22）。不用几何姿态（倾倒、旋转、堆叠、漂移）代替因果，不画空框或抽象块充数；只靠旁边标签才读懂的图形没有完成它的工作。声明过的形状与颜色语义全片不换用；图形在被讲到时已经在场。图形的几何与它代表的结构一致：指针指到对象的起点，长度从起点长出；连线从框上离开，不沿着框线走；看起来应当一样的东西真的一样，不一样的地方画出来并写明。

- **为什么**：旁白在讲因果的地方，画面在做形状的表演。
- **怎样查**：逐屏列出图形服务的解释与对应关系，指不出的改；核对同一形状、同一颜色有没有中途换义。结合完整段落判断，不机械要求逐句换屏。
- **也用于**：实现
- **案例**：反面 [web-login](../videos/in-seconds/web-login/)、[postgresql](../videos/database-engines/postgresql/)
- **来源**：P39、P49、P53、P95、P103（见 [反馈记录](log/feedback.md)）

#### F21 每部片子自成一体，不被无关的片子带偏

视觉系统、配乐和讲法为这一部重新建立：不沿用上一部或系列起点的配色、部件与曲子，不把别的片子的做法当成默认。系列只共享系列说明里写明的约定（标题格式、时长规则、常驻元素的位置等），其余每集按自己的对象设计。想复用另一部片子的好做法，先把它提炼进 kit/ 或 docs/，再从那里取用。

- **为什么**：同一套纸色底、平涂版式和 120 拍秒针配乐反复出现，片子之间难以区分；任务书照搬系列风格，与策划者的要求冲突过。
- **怎样查**：与近期两部片子并排看关键帧、并排听开头：说得出这一部的视觉和声音取自哪里、和它们有什么不同。（工具：check.js 提示样式表或配乐脚本与起点模板、其他片子完全相同）
- **也用于**：声音
- **案例**：正面 [postgresql](../videos/database-engines/postgresql/)
- **来源**：P3、P7、C2（见 [反馈记录](log/feedback.md)）

#### F22 画面自己承担注解，不必与旁白逐句对应

旁白是讲解的节奏，画面是这一段要传达的内容，两者要对得上，但不要求一句一画面，画面也不能被旁白锁死：旁白说到的才有、没说到的就空着，不合格。每个新名词、每个关键结构第一次出现时，画面上要有它的注解：是什么、指画面上哪一块、数字或出处；注解补旁白没说的，不等旁白，也不复述字幕（F25）。文案里用星号标出的术语，注解元素带 data-gloss。一组并列的对象（例如同一类的一批状态码、同一组可选部件）可以先成组摆出来，再只把正在讲的那几个高亮、推进或取出，其余留在画面上作背景；不必为了「配合这一句话」把画面切成一个个碎片。也不要把每样东西都钉在一个词上：逐词弹出、到下一段就收走，画面跟着字一下一下跳，停不住、读不完，看起来被旁白锁死。词的时刻用来对齐指认和关键动作；进场可以成组、提前，讲完的东西留够时间再走（F04）。画面上可以有旁白没提的元素与注解，前提是它服务于这一段，不另起一条讲解主线。反过来仍受 F20 约束：画面上的每个元素都要说得出它服务于哪一段内容，不能出现与内容无关的装饰。

- **为什么**：把画面绑死在旁白的每一句上，会把一组并列的东西拆成一堆碎片，观众失去「这是一类」的整体印象（《96 秒了解 HTTP 状态码》审稿）。只「允许」画面多给东西还不够：InnoDB 新版的画面只给旁白说到的词贴同名标签，新名词出现时观众不知道它是什么、指哪一块，策划者指出「被旁白过度绑定」「聚簇索引的出现也缺少注解」「回表 覆盖索引之类也缺乏解释脚注」。 Firebird 一集几乎每个元素都按词的时刻进场、按下一段的时刻退场，readable.js 报 38 处停留不足，策划者看成片说「锁的太死」。
- **怎样查**：看每个场景：旁白是否被画面切成了一帧一个的碎片？一组并列的对象是否整组在场、只推进其中的几个？列出全片的新名词与关键结构，逐个看它第一次出现时画面上有没有注解（是什么、指哪一块、数字或出处），关掉声音能不能看出它指的是什么？scan.js 的 GLOSS 报出的缺注解逐条补上。画面上有没有与内容无关的元素？数一数一段里有多少元素的进场、退场都卡在词的时刻上；连续几句都是「一个词一个东西」的，改成成组进场、只推进其中几个。（工具：scan.js GLOSS（标星号的术语第一次出现时，data-gloss 注解在场））
- **也用于**：实现、预览迭代、验收
- **案例**：反面 [innodb](../videos/database-engines/innodb/)、[firebird](../videos/standalone/firebird/)
- **来源**：P49、P79、P119（见 [反馈记录](log/feedback.md)）

#### F23 动画演示过程本身，不做幻灯片

讲机制的段落，用随时间推进的动画演示过程本身：时间轴与播放头、数据在结构里移动、状态随时间累积和改变，旁白骑在动画上讲。先把动画设计成能自己「跑」起来的过程模型（例：表锁的时间轴上，读锁条随播放头生长、写锁在斜纹里排队、轮到时独占），旁白的时刻只用来对齐关键节点。不要先定稿文字、再给每一句配一张逐条出字、面板淡入的画面；文字出现、高亮、淡入只作引导，不能当作推进本身。

- **为什么**：先出文稿、再按句配画面的做法，让后来的片子变得像 PPT，失去了灵动；策划者点名喜欢旧版 MyISAM 表锁的滚动动画。
- **怎样查**：逐章看讲机制的段落：画面里有没有随时间连续推进的过程，而不是靠新文字、新面板出现来推进？关掉声音，能否从动画本身看出发生了什么？连续几屏只是文字与面板依次出现的，记为未通过。
- **也用于**：实现、预览迭代、验收
- **案例**：正面 [myisam](../videos/database-engines/myisam/)
- **来源**：P64（见 [反馈记录](log/feedback.md)）

#### F24 镜头服从内容：正在讲的东西始终看得见

镜头为内容服务。每一次平移、推近、拉远都要说得出它让观众看清了什么；说不出的就不动。移动途中与停稳之后，这一刻正在讲的内容都完整在可读范围里，不被画面边缘、顶栏或字幕栏切掉，缓慢漂移的幅度也算在内。字幕条（画面下方 968–1080）里不放要看的东西，图形也算：人物的脚、房间的地面、车辆、底部的标签和引线都收在字幕条之上。大范围、频繁的镜头运动会把注意力从内容上拉走，能在原地换内容就不必穿越画布；强调可以靠颜色、方框、箭头和元素自己的动作。动几次、用什么手法，由各片按自己的设计决定。

- **为什么**：MyISAM 新版第一轮照旧文档「每场至少三次镜头运动、推近 1.3–1.6 倍、边缘文字被切属正常」去做，策划者看片指出镜头动作太大、到处乱动、内容都没了，要求根治「镜头动来动去不管内容看不看得见」。
- **怎样查**：按每句说完的时刻与每次镜头移动的中途，用 look.js 或总览图看：正在讲的内容是否完整在画内、没有压在字幕栏或顶栏下？scan.js 的 CUT、CAPZONE 提示逐条看过，正在讲的内容被切的已经改掉，保留的写了理由？以正常速度连续看，有没有哪一段镜头的动作比内容更抢眼？scan.js 的 CAPZONE 只查文字；图形有没有伸进字幕条、被字幕压住，逐帧看或列出外框越过 968 的元素。（工具：scan.js CUT、CAPZONE（只查文字）；图形伸进字幕条暂无工具（Firebird 一集用临时脚本查出房间地面压在字幕下，候选做进 scan.js））
- **也用于**：实现、预览迭代、验收
- **案例**：反面 [firebird](../videos/standalone/firebird/)
- **来源**：P70、P71、P72、P119（见 [反馈记录](log/feedback.md)）

#### F25 画面自己承载内容，不被文案捆住

画面是讲解对象本身，旁白是指着它讲的那根手指。一段开始时，讲解对象（文件、字节、结构、时间轴、终端回显）就带着真实内容在场，旁白讲到哪里就点亮、指出、推动哪里；不要先摆一排空框、讲到一个词才往里填一个字。字幕已经说出的话，画面上不再写一遍；画面上的字留给数据本身、要记住的术语名、轴标与图例。画面需要的事实（年份、版本、数值）在 FACTS 里没有时，去查证补进 FACTS 再画，不因为缺事实就把画面删空。信息量要适中：空到只剩一行字和堆到要暂停才看得完都不合格。最常见的复述是「结果块」：旁白说「做一次检查点，写到文件末尾」，画面就弹出一块写着「写到文件末尾」的实心字块；旁白问「读到的是 42 还是 43」，画面就排出「读到的是 · 42 · 还是 · 43」。这类块不管做得多醒目，都只是把字幕又念了一遍，画面依旧被旁白捆住。结论应当由对象自己做出来：页真的搬到文件末尾、文件条真的变长、读的人真的顺着链走到某一版停下。为过像素静止检查补变化时同样如此，补的是对象的一步动作或状态，不是一块字。

- **为什么**：MyISAM 新版第一轮画面跟着文案一句一句出字：结构先是空框、讲到才填，版本轴删到只剩两个版本号、没有年份，不少说明把字幕又写了一遍。策划者指出「被文案捆的太死，太 PPT」「文字没有画面就没有」「连个年份都不会写」，同时提醒「也不要画面信息过于密集」。 MongoDB 一集 r6 为过静止检查，在十几处停留里补了「找到这一份」「整页重新整理，写成新的一块」「多出 36 KB」一类字块，加上原有的「读到的是 42 还是 43」，策划者说「这种什么人机动画简直就是旁白了, PPT都没这么PPT」「无数次强调你还是始终给旁白捆死」「哪个容量条变大就足够直观了」。
- **怎样查**：关掉声音和字幕连续看：每一段有没有讲解对象的实物在场？有没有一段画面只是空框或空白在等旁白？画面上的字有没有在复述字幕？用 sheets.js 每 3 秒一帧通看，空荡的帧与挤满的帧各记下来改掉。再把全片每一块带字的结果块、标签和当时的台词并排：意思相同的删掉，改成对象自己的动作或状态变化；具体的差值（「多出 36 KB」）在形状已经看得出时也不写。
- **也用于**：实现、预览迭代、验收
- **案例**：反面 [mongodb](../videos/database-engines/mongodb/)
- **来源**：P76、P97、P102、P123（见 [反馈记录](log/feedback.md)）

#### F29 一章一个连续的画面：对象常驻，换段带一样东西过去

范本是 MyISAM 一集：一分钟里屏上一直是同一张 .MYD 字节表，先一长串，再原地折成每行 16 字节，标注一层层叠上去，一句旁白只在它身上推进一小步。每一章都是这样一个画面：讲解对象常驻、在原地变化（页摊成字节表，一行从表里升起来摊成十六进制）；不是「一句话变一下」，不是一页页换的面板。章内要换段时，至少带一样东西过去——上一段的结论飞成下一段的对象（两个版本飞成索引那一段的「堆里两个版本」，一页缩进堆里那一格、下一段再从那一格放大出来），两段共用的对象摆在同一位置、换段前就到位，交叉淡变时它不动不闪。指认用对象本身的高亮或选区（字节表上的选区随旁白滑过去），不用一个框在文字之间跳来跳去；暂时不讲的部分退淡，同屏的字少一半。章节之间仍用系列约定的整屏章节卡。

- **为什么**：PostgreSQL 一集 r7、r8 每段一个面板、一个红框在字之间移动：「动画整体还是太PPT 各个文字打框动来动去看的眼花」「你还是做PPT的思路, 而不是视频, 最直接的就是画面缺乏连续性」「视频是运动的画面和语句的有机结合, 而不是PPT, 一句话 变一下」「最优先参考MyISAM」。r9 按本条重做后策划者认可。
- **怎样查**：按章用 sheets.js 看总览：每章说得出常驻的主对象是什么、它在哪几步里变了；每一处章内换段说得出带过去的是哪一样东西，整屏内容全换、什么都没带过去的要改；找出在文字之间移动的框改成原地指认；同屏文字多的段落，确认暂时不讲的部分已退淡。
- **也用于**：实现、预览迭代、验收
- **案例**：正面 [myisam](../videos/database-engines/myisam/)、[postgresql](../videos/database-engines/postgresql/)
- **来源**：P89、P90、P91、P92、P93、P96（见 [反馈记录](log/feedback.md)）

#### F31 注解先给定义：新名词第一次出现，先说清它是什么，再说别的

把自己当成第一次听到这些词的观众：旁白或画面上第一次出现的每一个名词（不只是文案里标了星号的术语，也包括顺口带出的「驱动程序」「副本集」「mongos」一类），都要有注解说清它是什么，指的是画面上哪一块。术语注解（data-gloss）的第一句是定义：它属于哪一类东西、和同类的区别或用途（「集合：MongoDB 里成组存放文档的地方，属于某一个数据库，相当于关系数据库的表」「索引：在集合之外另存的一棵 B 树，存某个字段的值、按值排好序，每一项指回一份文档」）。定义优先取权威出处的原意（官方文档的术语表、规范、项目自述），没有现成定义就按已核实的事实自己下一个；用法、特性、来历、结构、小贴士都排在定义之后，不能拿来顶替定义。介绍一样有分量的东西（一个引擎、一家公司、一个格式），定义之后可以分条写来历与特性，篇幅给够、版面给够。某样东西是自动生成的还是要人去做的（自动建的索引、手动建的索引），注解要说明白。五种写法不合格：一、只说用法或性质、不说是什么（「集合：不用事先创建，第一次存文档就自动建出来」「存储引擎：这一集后面的文件、缓存、检查点、日志都归它管」「索引：每个索引单独占一个文件，自己就是一棵树」「ObjectId：不用问数据库，同时生成也几乎不会撞号」）；二、该给定义的时候讲结构（BSON 刚出现就写「开头 4 字节记整份多长；每个字段 = 1 字节类型 + 字段名 + 0 + 值」，结构留到讲字节的时候）；三、把同一时刻的台词换个说法再写一遍；四、拿不重要的细节充数（介绍一家公司时罗列创始人名单，却不说这家公司是做什么的）；五、写成正确的废话。名词的定义一两行读得完，数字带单位；注解需要的事实在 FACTS 里没有时，先去查一手出处补进 FACTS，不拿手头仅有的材料凑数。

- **为什么**：MongoDB 一集 r5、r6：DoubleClick 的注解写「一家网络广告公司；MongoDB 的三位创始人……都在这里干过」，只重复了台词里的「广告公司」，再堆上三个人名，没说这家公司做什么；「存储引擎」的注解与台词逐字相同；「索引」的定义写成「按某个字段排好序的另一棵树」；ObjectId 的注解只是复述，「驱动程序」第一次出现时没有任何解释。策划者指出「这种几乎没有提供额外信息的注解还是反复发生」「注解一堆这种和台词一模一样的存在的意义是什么」「你管索引的定义叫这个」「缺事实就去查而不是懒惰」「你很多图注简直是废话文学」「你要假设自己是用户, 面对抛出的新名词, 有没有说是什么」。F22 早已要求注解「补旁白没说的，不复述字幕」，只写成一句要求挡不住，这里单列写法与查法。 r7 按「回答观众此刻会问的问题」重写以后，注解多半写成了用法与性质：集合写「不用事先创建」、存储引擎写「后面的东西都归它管」、索引写「单独占一个文件」、ObjectId 写「不会撞号」、BSON 一出场就讲字节结构，WiredTiger 只写了一句被收购。策划者：「注解写的不是集合的定义, 而是MongoDB里集合的类似怎么用」「索引给的也不是MongoDB索引的定义, 都不知道是啥, 写的和小贴士似乎的」「基本上都要改成定义, 权威没有你自己下」「WiredTiger的介绍更详细点, 涵盖历史, 定义和特性」「如果是自动建立的, 图注要有解释」。
- **怎样查**：列出全片每一条术语注解，逐条只读第一句：能不能回答「X 是什么」（属于哪一类东西、和同类的区别或用途）？答不上来的改成定义，原来的内容挪到定义之后或删掉。再按时间顺序列出旁白和画面上第一次出现的名词，逐个看出现时有没有注解；结构、来历、特性类的说明是不是排在定义之后、出现在讲到它的时候。逐条和同一时刻的台词并排看，去掉与台词重复的字还剩下什么；注解里的人名、年份、数字是不是观众此刻需要的；每一条事实在 FACTS 里有编号，定义写明取自哪个权威出处或注明是自拟。（工具：暂无工具（候选：把 data-gloss 与贴实物标签的文字和同一时刻的台词做字面重合度比对，重合过半的列出来））
- **也用于**：实现、预览迭代、验收
- **案例**：反面 [mongodb](../videos/database-engines/mongodb/)
- **来源**：P122、P125（见 [反馈记录](log/feedback.md)）

### 实现

#### F04 看得完，也看得懂（不能「刷一下」）

先排信息，再排动作。关键状态（结论、对比、报错、章节卡）完整出现后，至少稳定「1.5 秒 + 必要文字字数 ÷ 5 字/秒」再退场；一步机制完成后，另留看懂这一步的时间，其间不引入新东西。关键信息不在一句旁白的最后半秒才出现；镜头推近时，要读的部分在画内。非定长的片子宁可长一点；定长的片子靠删内容腾时间，不压留白。

- **为什么**：全仓库最普遍的问题：信息还没看完、还没看懂，画面就过去了。
- **怎样查**：用 readable.js 量每个关键状态从全部到位到开始遮挡或退场的区间；再以正常速度连续观看全片，需要暂停才看得完、没看懂就换场的画面都算未通过。逐帧量达标不能代替连续观看。（工具：readable.js 测量完整可读区间）
- **也用于**：预览迭代、验收
- **案例**：反面 [opencart-1-5-admin](../videos/standalone/opencart-1-5-admin/)、[innodb](../videos/database-engines/innodb/)、[web-login](../videos/in-seconds/web-login/)、[openclaw-hermes](../videos/standalone/openclaw-hermes/)、[firebird](../videos/standalone/firebird/)
- **来源**：P2、P15、P24、P26、P36、P37、P98、P119（见 [反馈记录](log/feedback.md)）

#### F05 运动解释关系

每个关键动作都在展示对象、因果、数据流或状态变化：同一对象的初态、触发、变化、结果依次可见。擦除、刷屏、整屏换面板只作必要的过渡。镜头只在站与站之间移动；停在一屏上时不缩放、不推近、不往复、不环绕，最多朝一个方向极慢地横移（参考：一屏合计不超过 48 像素、每秒不超过 2 像素；一章之内各屏朝同一个方向、换屏时随内容回位，相邻两章方向相反，不左右来回），章节卡停留时至多整张极慢推近一次（不超过 3%）。画面停着时让内容分步变化，不用镜头动作掩盖。

- **为什么**：反复的擦入刷出和晃动的镜头制造了动静，却没有解释任何东西，还分散注意力。为了让静止检查过关而加的往复缩放、慢推也是一样：观众看到的是一直在动的镜头，画面上的内容其实停着。
- **怎样查**：连续观看代表机制段，能看见前因后果；与近期两部片子的开头、换章、解释段并排比较，不只是换了颜色或方向。scan.js 的 ZOOM 报出的停留缩放与往复逐条改掉；章节卡与元素自己的慢推工具量不到，连续观看时核对。（工具：scan.js ZOOM（镜头画布在停留时的缩放与往复））
- **也用于**：预览迭代、验收
- **案例**：正面 [two-factor-auth](../videos/in-seconds/two-factor-auth/)、[myisam](../videos/database-engines/myisam/)；反面 [innodb](../videos/database-engines/innodb/)
- **来源**：P3、P6、P17、P78、P85（见 [反馈记录](log/feedback.md)）

#### F19 中间帧也是画面

按实际字宽排版：文字不超出所在色块，色块不越过别的框线；后到的元素不盖住正在讲的内容；画面的前后层次事先定好：底板、示意图、引线、标签、卡片各在哪一层，后加的底板、面板、引出框垫在它要承托的内容下面，不压住已经在场、还要讲的东西；两样东西要占同一块地方时，旧的先让开或退场；反色高亮不让底色与字色同时渐变；元素退场交代去向，不在刚到达时直接消失。渐变、飞入、落位、退场的中间帧都要成立。同一个元素的显隐要接得上：已经收起或压暗的元素不再用写定起点的淡出收一次（会先闪回原样再消失），成组收起时只收要走的那几样，没写出现时刻的元素不会从场景开头就挂在画面上。不用元素的缓慢漂移凑画面变化。注解、标签、图注与旁边不相干的东西留出间距（至少约 24 像素）：不贴着别的框、不压在别的字或色块上、不跨在底板的边上；一段注解要放几行，先算好它在那一处有多高、多宽，放不下就给它挪出一块地方（收窄或压矮旁边的图、换到空着的一侧），不把字挤进剩下的缝里。

- **为什么**：成片里出现过溢出、压盖、渐变途中字与底同色、元素突然消失。 MongoDB 一集 r7：「文档」的注解压在「字段」「值」两块上，「集合」「存储引擎」的注解贴着旁边的框、挤成四行窄条，BSON 的注解被后来的两行说明压住，scan.js 一处都没报；策划者看了几分钟就不看了：「我不想把时间放在这种重叠bug」「你自己先过一遍吧」「这个东西落盘文档, 之后不要再犯, 太离谱了」。
- **怎样查**：交出之前先跑 overlap.js（全片、每 0.25 秒一帧），持续 0.4 秒以上的每一条都修掉或写明为什么保留（删除线、正在飞行的一块），短暂的逐条看是不是飞行与交叉淡变的中间帧；scan.js 只报连续多帧的成对文字重叠与对比度，过闸不算通过。每个动作前后逐 0.1 秒取帧，专看中间状态。比对时间线上每段不透明度补间的起点与上一段的终点，列出跳变；列出场景开头就可见、之后才收起的带字元素。（工具：overlap.js（字压字 TT、色块与线条盖字 COVER、字跨框边 EDGE、字被裁 CLIP、注解贴边 TIGHT）；scan.js 部分覆盖（OVERLAP、CONTRAST）；显隐跳变与「开场就在」暂无工具（PostgreSQL 一集用临时脚本读 GSAP 时间线比对，候选做进 scan.js））
- **也用于**：预览迭代、验收
- **案例**：反面 [postgresql](../videos/database-engines/postgresql/)、[web-login](../videos/in-seconds/web-login/)、[firebird](../videos/standalone/firebird/)、[mongodb](../videos/database-engines/mongodb/)
- **来源**：P32、P35、P36、P99、P100、P101、P119、P125（见 [反馈记录](log/feedback.md)）

#### F27 检查通过不等于看得懂：交付前以观众身份看完全片

自动检查只量得出能量化的东西。请人审片或交付之前，制作方自己以观众身份把全片完整过一遍：能看视频的按正常速度看；只能看图的用 sheets.js 每 3 秒一帧通看全片的总览图，再对可疑处用 look.js 看原图。逐段问：正在讲的东西看得见吗？画面空不空、挤不挤、像不像幻灯片？镜头有没有抢戏？扫描的每一条提示都要看过，修掉或写明为什么保留。

- **为什么**：MyISAM 新版第一轮在扫描、可读时长全部通过后交给策划者看，被接连指出镜头乱动、文字压在字幕条下、光标不闪、画面空荡、像 PPT；全片总览图逐帧复查是在策划者指出之后才做的。
- **怎样查**：README「交付」里是否写明全片通看的方式（看视频或总览图）、时间与发现的问题？scan.js 的提示是否逐条有处理？
- **也用于**：预览迭代、验收
- **来源**：P70、P72、P75、P76、P77、P99（见 [反馈记录](log/feedback.md)）

#### F30 出现、消失、高亮都有过渡：不硬切、不闪

元素出现与消失都带一小段淡入淡出（约 0.2–0.4 秒）或移入移出，不在一帧里蹦出、蹦没；场景开头的初始隐藏除外。换段时上一屏淡出、下一屏淡入，带一点位移更好；一组东西结束时让它们去到下一个地方（飞进合并后的那一块、沉下去换上另一组），不是整组同时消失。高亮亮起后慢慢退回，不让类名一下切回去；不用循环的明暗脉冲吸引注意，看着像闪。一件东西没了，跟它有关的动画一起撤（断电后，缓存里的箭头、转着的沙漏都收掉），不留还在动的残余。本身就是瞬间的事件（断电、强行杀掉）可以硬切，但前后要交代。

- **为什么**：ClickHouse 一集 r9：出现与消失全是硬切（出现 0.01 秒、消失瞬间），面板背景一明一暗地循环，高亮到点「啪」地灭掉，换段整屏一跳，被策划者连续指出「缺乏过渡」「到处闪烁」「快速切换的老毛病」。
- **怎样查**：换段、高亮收回、一组东西退场处，逐 0.1 秒取帧看：任何元素都不能前一帧还在、后一帧全没（或反过来）；全片搜一遍持续 0.01 秒的出现、瞬间的隐藏、循环的背景脉冲与只切类名的高亮；看每次「东西没了」之后，有没有还在动的残余。（工具：暂无工具（ClickHouse 一集把出现、消失改成全片统一带淡入淡出，高亮用叠一层再淡出的做法，靠逐帧拼图核对））
- **也用于**：预览迭代、验收
- **案例**：反面 [clickhouse](../videos/database-engines/clickhouse/)
- **来源**：P121（见 [反馈记录](log/feedback.md)）

#### F34 框里的内容左右留白相当，不贴死一边

带边框或底色的框（卡片、面板、表格、事务框、字块）里，内容左右两边的留白要相当：一排并列的块整体居中，不能最左一块离边框几十像素、最右一块顶住边框；拆开、平移、放大之后也要重新算一遍，不伸出框外。字块里的字左右留白相同，字不贴着底色的边。叠在框上的兄弟元素（不是框的子元素，只是画在框的范围里）同样按框里的内容算。

- **为什么**：MongoDB 一集 r6：Dave 注册时三个块在事务框里左边空 40 像素、最右一块顶住边框；开场 ClickHouse 那张卡里两列拆开后顶到虚线框；people 集合里几份文档的字伸出卡片；日志行与根页格子的字贴着底色的左边。策划者说「向右顶死不平衡的bug 视频里挺多的」。
- **怎样查**：逐秒取帧，对每个带边框或底色的框，算出里面可见内容（含叠在框里的兄弟元素）的左右边，与框的内边比较：右边留白远小于左边、或内容伸出框外的列出来逐条改。（工具：暂无工具（MongoDB 一集用临时脚本 videos/database-engines/mongodb/tools/balance.js 逐秒检查，候选做进 kit））
- **也用于**：预览迭代、验收
- **案例**：反面 [mongodb](../videos/database-engines/mongodb/)
- **来源**：P123（见 [反馈记录](log/feedback.md)）

### 声音

#### F06 声音有存在感，音效有含义

配乐为本片单独设计：先有一层贯穿全片、带低频分量的铺底，再加动机与节奏，随章节发展；稀疏的钢琴或和弦不等于克制。换预设或换音色不算新配乐。音效只给有含义的关键动作，不同动作不同声音；慢移、阅读保持、装饰动作可以无声，不默认配气流声。

- **为什么**：配乐太弱、各片配乐与「刷」声同质化，都被直接指出过。
- **怎样查**：主混音、无配乐版、仅旁白版连续试听开头、密集段与章间，与近期作品比较；事件数量和响度数值不能代替听感，听不到的如实写明。
- **也用于**：验收
- **案例**：正面 [myisam](../videos/database-engines/myisam/)；反面 [innodb](../videos/database-engines/innodb/)、[opencart-1-5-admin](../videos/standalone/opencart-1-5-admin/)
- **来源**：P3、P27、C2（见 [反馈记录](log/feedback.md)）

### 验收

#### F08 记录与最终文件一致

帧率、时长、响度、峰值、文件名与版本，一律在最终编码的文件上测量后再写进记录；混音 WAV、旧报告和文件名都不能代替。

- **为什么**：曾有成片名为 60 帧实为 30 帧，曾有交付记录的峰值与最终文件不符。
- **怎样查**：用 ffprobe 与响度测量读取最终 MP4，与 README 的交付记录逐项对照。（工具：finish.js 与 check.js --final 测量最终文件）
- **也用于**：发布与反馈
- **案例**：反面 [openclaw-opencode-v2](../videos/standalone/openclaw-opencode-v2/)、[innodb](../videos/database-engines/innodb/)
