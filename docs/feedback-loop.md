# 让反馈持续进入下一部视频

反馈通过四层传递：**用户原话与成片证据 → 结构化制作规则 → 每部片子的处理计划 → 实际成片复核**。不能只在总账追加一段文字。

## 1. 单一规则入口

[feedback.md](feedback.md) 保留 P / C 来源、F 编号、历史评分和实际测绘；[feedback-rules.json](feedback-rules.json) 保存当前 F01–F14 的要求、验证方式和对照案例。新增共性反馈时同步修改两处并更新版本，编号持续保留，不把旧问题删除后当作已解决。

`new.js` 从规则文件生成 README 的开工 / 结尾表和 `review/feedback.json`，自制与委托共用同一入口。以后增加 F15 等规则，无需逐个模板补一行。`repo-check.js` 检查总账与规则编号一致；回归测试覆盖新增规则进入下一部以及已有片补录。

## 2. 开工和接续

```sh
node kit/tools/feedback.js <视频> sync
node kit/tools/feedback.js <视频> check
```

sync 启用本片的 `project.json.feedback.required`，创建或补齐记录。新增规则为 pending；既有规则内容变更时，把旧记录放入 history，要求重填变化项，不把旧的“已验证”自动套到新要求上。

每一项填写：

- `applicability`：`applies` 或 `not_applicable`。不适用必须在 `reason` 说明本片的具体原因。
- `plan`：针对本片的做法；不是“注意一下”或复制一句原则。
- `script_evidence`：文案、分镜、术语表或检查清单的定位，说明改在哪里、怎样检验。

新片默认启用，不能通过删字段或设 false 绕过。旧片的历史交付不补造应用记录；**接续或改片时先 sync**，按当前要求准备。单纯查看旧稿不会被自动改写。

## 3. 制作前检查

文案导出稿链接反馈记录。先完成具体处理计划，再取得正常的文案确认。配音、声音、预演、正式渲染与封装入口在已有确认检查后核对反馈；缺编号、版本过期、未判断适用性或未写具体处理就停止。

Lean 4 固定作为 F01 / F02 的典型负面例子，MyISAM 保留为叙事正面对照。InnoDB 的新反馈进入 F04–F06、F10–F12。每部片子说明自己怎样避免重演，不能仅写“已阅读”。

## 4. 结尾核对实际成片

```sh
node kit/tools/feedback.js <视频> check --stage final
node kit/tools/check.js <视频> --final
```

适用项需要 `result: "verified"`、具体的 `verification`，以及各语言的 `clips`。每个 clip 写实际主成片的相对位置、语言、起止秒数和完整 SHA-256，例如字段为 `file`、`lang`、`start`、`end`、`sha256`。时间须在对应渲染清单的总长以内，文件必须是该语言的正式主成片；预演或其他附件不能代替。

工具按流读取实际 MP4 检查哈希，文件变化后旧证据失效。尚未观看、试听或未解决的项保持 pending / needs_work，并在 README 记录待办；可以交出文件供讨论，但不能把完整验收写成通过。不适用项同样保留理由。

这套检查保证编号、版本、记录和文件身份一致，不能判断一个例子是否讲清楚，也不能验证人是否真的听过。判断仍由实际读稿、看图、连续观看和人耳试听承担；元数据不能伪造。

## 5. 修改规则也要验证

`npm test` 覆盖新片自动带入、已确认文案仍受反馈约束、规则更新使在制片待复查、下一部片自动获得新增规则、实际成片哈希和时段失效。模板相关改动另跑 `npm run smoke`。

反馈修复的最后一步仍是重做受影响的影片、给出新的成片证据。仅改本页、工具或 JSON 不会关闭原片问题。
