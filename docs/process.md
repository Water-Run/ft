# 制作周期

一部片子的主线是：取证与文案 → 本地审片页 → 文案确认与配音 → 实现 → 预览迭代 → 正式片 → 发布与复盘。阶段之间是依赖关系，不是流水线：取证之后就可以找视觉材料，文案确认之前可以探索关键帧。不能越过的只有三道闸门（第 4 节）；其余顺序与做法，由当时负责的一方判断。

各阶段由谁做、谁说了算，见[角色与权限](roles.md)。

## 1. 主线

1. **立项与取证。** `new.js` 建目录，在 README 的「简报」里写清受众、核心问题、时长、语言和策划者的原话要求。然后查一手来源、做实验，事实只进 `research/FACTS.md`。见[取证](guides/research.md)。
2. **文案初稿。** 先写能通读的中文讲述，逐章检查是否回答核心问题。制作方同样通读、主动改稿。见[文案与配音](guides/script.md)。
3. **本地审片页。** 初稿一成，就做一张本地 HTML 页面，放在本片 `out/audition/index.html`（`out/` 不入库），用浏览器打开交给策划者，让策划者在一处看完、一次选定：
   - 连贯全文，带句号，标出新增句与待定问题；
   - 5 个配音候选，读同一组代表句，避开前几部用过的音色。这只是试听，全片配音仍等文案确认；
   - 3 个配乐方向的小样；
   - 两三个视觉方向的关键帧截图。

   策划者的选择与原话记进 README 的「简报」和 `review/NOTES.md`。各部分的做法见[文案校对](guides/script-review.md)、[音色](guides/script.md#9-音色记录)、[配乐](guides/sound.md#2-配乐)与[关键帧](guides/visual.md#3-关键帧)。
4. **文案确认，全片配音。** 按意见改到校对者明确确认当前稿本（第一道闸门），再用选定的音色合成全片，回听读音与断句。
5. **实现。** 先做 15–30 秒的有声代表段，验证选定的方向；再铺开场景、配乐与音效，边写边查。见[场景与动态](guides/scenes.md)、[声音](guides/sound.md)。
6. **预览迭代。** 每一轮先做自对抗审查（第 2 节），修完再出低清有声预览，用 `preview.js --round r3` 另存一份带轮次的文件（`out/zh/preview-r3.mp4`）交给策划者。之后的验证预演只写固定的 `preview.mp4`，不会覆盖交出去的那一份。策划者的意见逐条记进 `review/NOTES.md`，下一轮逐条回应。轮数不固定，直到策划者说可以出正式片。
7. **正式片。** 正式渲染、封装、出封面，运行 `check.js --final`。第一份完整成片做好就交出，策划者可能当即发布；交出之后还要改，先说明并征得同意，不悄悄重渲。见[验收](guides/acceptance.md)。
8. **交付、发布与复盘。** 策划者看过并同意后登记交付。发布后回填平台记录、冻结源码，收集评价与评论，可推广的教训进[经验规则](lessons.md)。见[发布与收尾](guides/release.md)。

## 2. 自对抗审查

策划者的时间用来判断内容、叙事和审美，不用来找简单的 Bug。审片页、预览或成片交出之前，制作方先把自己当成挑剔的观众和找茬的测试者，攻击自己的作品：哪里看不懂，哪里看起来坏了，哪里和旁白、文案或事实对不上。自动检查通过，只说明它负责的那几项通过。

这不是一张固定清单。每一轮按本片的内容和上一轮的意见决定查什么、怎么查；工具只是帮手，需要时为本片临时写检查脚本。下表是反复出现过的问题类别，用来提醒，不用来打勾：

| 类别 | 例子 |
|---|---|
| 几何 | 线条或箭头穿过文字；框的边、视线框压住文字；文字被容器裁掉；箭头不从它所属的对象出发；没画出来的路径留下一个圆点 |
| 时序 | 东西在旁白讲到之前出现，或闪一下就没了；重复的句子让同一个动画触发两次；关键揭示之后没有停留；大段空白或静止 |
| 理解 | 新名词、编号、页号没有交代来处；画面上的数量与旁白不符；一屏信息过密，或空空荡荡 |
| 声音 | 多音字、英文与缩写的读法；停顿的位置；配乐压住旁白 |
| 一致 | 审片页、文案、画面、字幕与片尾名单之间有出入 |
| 工程 | 改过的源文件有语法错误（每个改过的场景运行 `node --check`）；成片不是当前源码的产物 |

做法：

- **看全片，不只看改过的地方。** `sheets.js` 每隔几秒出一张接触表，可疑处用 `look.js` 细看；`scan.js`、`readable.js` 与低清预演查各自负责的项目。几何类问题按需写脚本，逐帧比对文字框与线条、色块的位置。
- **当轮修掉，再过一遍。** 直到一轮查不出严重问题，才交出。
- **如实记录。** 在 `review/NOTES.md` 记这一轮查了什么、修了什么、还剩什么；交出时说明没看、没听的范围。
- **从漏网的问题学查法。** 策划者指出的问题，先想自查为什么没发现，把这一类的查法加进下一轮；可推广的进[经验规则](lessons.md)，能做成工具的做进工具。

## 3. 阶段

`stage` 是本片 `project.json` 里记录当前阶段的值，片单据此显示进度。每次停工前更新它与 `next`。`lessons.js show --stage <阶段>` 打印该阶段要遵守的经验规则，开工前读一遍。

| 阶段 | `stage` | 主要产出 | 先读 |
|---|---|---|---|
| 选题 | （片单） | `videos/catalog.json` 的条目 | — |
| 立项 | `brief` | README 的「简报」 | 系列说明（如有） |
| 取证 | `research` | `research/FACTS.md`、`research/lab/`、`research/MATERIALS.md` | [取证](guides/research.md) |
| 文案 | `script` | `src/js/script.js` | [文案与配音](guides/script.md) |
| 审稿 | `review` | 本地审片页、`review/script.*.md`、`review/approval.json` | [文案校对](guides/script-review.md) |
| 配音 | `voice` | `src/js/timing.*.js` | [文案与配音](guides/script.md) 第 5–9 节 |
| 设计 | `design` | `src/design/`、README 的「设计」 | [视觉设计](guides/visual.md) |
| 实现 | `build` | `src/js/` | [场景与动态](guides/scenes.md)、[引擎](reference/engine.md)、[踩过的坑](reference/pitfalls.md) |
| 声音 | `sound` | `tools/music.py`、混音 | [声音](guides/sound.md) |
| 预览迭代 | `preview` | `out/<语言>/preview-rN.mp4`、`review/NOTES.md` 里的意见与自查 | 本页第 2 节、[验收](guides/acceptance.md) |
| 成片 | `render` | 成片、字幕、封面 | [工具](reference/tools.md) |
| 验收 | `accept` | `review/lessons.json`、README 的「交付」 | [验收](guides/acceptance.md) |
| 交付 | `delivered` | 片单状态改为已成片 | [发布与收尾](guides/release.md) |
| 发布与复盘 | `released` | `project.json` 的 `release` 与 `reception` | [发布与收尾](guides/release.md) |

设计、实现与声音通常交错进行，`stage` 记当前的重心即可。

## 4. 三道闸门

内容与叙事是进入制作的前提：先通读全文，检查核心问题、解释路径和取舍，再看逐句表。文案尚未成立时，工作回到取证或改稿。

| 闸门 | 之前不能做什么 | 由谁把关 |
|---|---|---|
| 文案确认 | 校对者明确确认当前稿本之前，不配全片，不按稿铺开场景 | `tts.js`、`audio.js`、`render.js`、`finish.js` 等核对 `review/approval.json` 与当前内容的哈希 |
| 自动闸门与成片审查 | 自动检查、内容与叙事审查、实际视听核对及交付记录未完成之前，不写「验收完成」；未解决的项写明，交策划者判断 | `check.js --final` 查一致性；内容与成片按[验收](guides/acceptance.md)核查 |
| 策划者同意 | 策划者看过成片并明确同意之前，不登记交付、不发布 | 人 |

三条之外还有两条底线，任何时候都成立：不为通过检查而放宽阈值或改工具；不补造确认、验收或看过、听过的结论。

## 5. 改动之后从哪里重做

本节针对尚未发布的片子。已发布的片子按[发布后冻结](guides/release.md#发布后冻结)处理，收到反馈或发现漏署名都不自行重做；先取得策划者明确的重做要求。

成片是源码的产物，改了源码，成片就过期了；`check.js --final` 会查出渲染之后改过的源文件。

| 改了什么 | 从哪里重做 |
|---|---|
| 文案的含义、范围、句子增删、章节结构 | 回到审稿，确认后从配音起 |
| 读法、停顿、字幕断句（不改含义） | 记进 `review/NOTES.md`，从配音起 |
| 场景或任何入场时刻 | 从声音起（音效挂在场景的时刻上），再出预览 |
| 只改样式 | 重出预览或成片 |

## 6. 交接

准备方把前期交给制作方时：

1. 在 README 写「交接」：做完了什么、放在哪里，还有哪些没解决、哪些取舍拿不准。策划者在会话里说过的要求，原话照录进「简报」。交接应让接手者能复述核心问题、解释路径和证据边界，不以材料数量代表准备完成。
2. 运行 `node kit/tools/check.js <视频> --handoff`：事实表、确认有效的文案、简报齐全才能交接。工具查的是事实表是否填写陈述、可定位的出处与核查状态；记录本身是否可靠，仍要逐项复核。
3. 制作方开工时读「简报」「交接」、`research/` 与已确认的稿本；准备方留下的关于成片的建议，按[角色与权限](roles.md#4-制作方的权限)自行取舍。

## 7. 停工与接续

- **停工前**：更新 `project.json` 的 `stage`、`next`，在 README 的「状态」写清停在哪一步、为什么停、下一步依赖什么。
- **接续时**：先读 README 的「状态」，再核对实际文件：当前稿本的确认是否有效、时间线是不是最新、`out/` 里的成片是不是当前源码渲染的。旧的 README、历史排期、片单状态或已有的 MP4 都不能证明当前版本已经完成。计划中、仅保留简报的项目，按 [new.js 的重开方式](reference/repository.md#2-一部片子的目录)继续。
- **规则变了**：经验规则更新之后，在制的片子运行 `node kit/tools/lessons.js <视频> sync`，新增或改变的规则进入待复核。

## 8. 多个会话并行

见[角色与权限](roles.md#6-多个会话同时工作)：一个会话一个视频目录，提交用 `git commit -m "…" -- videos/<系列>/<片>/`，共享文件的改动单独提交。
