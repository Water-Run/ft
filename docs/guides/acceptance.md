# 验收

验收分三层：自动闸门（工具查）、成片审查（人与模型对照成片逐项看、逐项听）、交付记录（写给人看）。审查先确认内容与叙事成立，再判断视听表达。自动闸门通过只是起点；事实、观感、听感与经验规则要单独核对，不能用闸门通过代替。

## 1. 自动闸门

```bash
node kit/tools/check.js <视频>            # 制作期
node kit/tools/check.js <视频> --final    # 交付前
```

输出逐项「✓ 通过 / ✗ 不通过」和明细，最后一行是结论。阈值与风格规则写在该片 `project.json` 的 `check` 段（字段见 [工具](../reference/tools.md)），动笔之前定好；不为了通过而事后放宽阈值、把某一项改成提示，或删改逐句对应表（[角色与权限](../roles.md) 第 2 节）。

| 项 | 查什么 | 不通过时 |
|---|---|---|
| 文案确认 | 选中的语言是否有与当前内容一致的明确确认、指定校对者、日期和依据 | 按 [文案校对](script-review.md) 交审；工具不能代替确认真实性的核查 |
| 经验规则复核 | 制作期：`review/lessons.json` 是否跟上当前规则（只提示）。交付前：每条规则都有结论，`pass` 附证据、`n/a` 附理由、`open` 附说明 | `node kit/tools/lessons.js <视频> sync`，逐条写结论；见第 7 节 |
| 源码规则 | 有没有破坏「画面只由 t 决定」的写法（CSS 动画与过渡、定时器、时间线回调、未固定种子的随机数），以及 `check.style` 打开的风格规则（阴影、渐变、模糊、圆角、调色板以外的颜色、系统字体、emoji） | 按提示的文件与行号改。确有理由的一行，行尾注释写 `lint-ok: <原因>` |
| 场景齐全 | 脚本里的每个场景都已实现并加载；没有残留的 `TODO`；`check.camera` 为真时每个场景都用了镜头 | 补上 |
| 自成一体（F21） | 样式表、配乐脚本与模板、系列起点或另一部片子完全相同 | 为本片重新设计。制作期只提示；新版目录交付前不通过 |
| 时长与节奏 | 每种语言都有实测时长；总长在 `check.duration` 范围内；每句字幕不超过一行；单句不超过 `check.max_cue_seconds` | 拆句、删字、调停顿 |
| 全片扫描 | 即 `scan.js`，每种语言各一遍，见第 2 节 | 见第 2 节 |
| 音效覆盖 | 事件总数、种类数、每场景数量、最长无声间隔、名称是否合法 | 给缺音效的关键动作补登记，见 [声音](sound.md) |
| 署名登记与片尾名单（`--final`） | 新旧目录均查：策划、仓库地址、非空模型名单、明确型号、实际分工；片尾 cue 无旁白；画面上完整出现每个名字与分工、策划与开源标记及仓库地址。未记录等占位名不能交付 | 片尾名单从 `credits` 读，参与者还须按本片记录人工核对，见 [角色与权限](../roles.md) 第 5 节 |
| 交付物（`--final`） | 成片、仅旁白版、无配乐版（配置为 none 时不要求）、字幕、四张封面齐全；时长、规格、响度；静止段与空画面；源码（含署名与许可）是否在渲染之后改过；README 的「交付」是否写了 | 缺什么补什么；源码改过就重新渲染和封装 |

系列里的一集另有一条提示：系列建议的栏目在本集缺了哪些、先后是否不同。只是提示，不计入通过与否。

## 2. 全片扫描

`scan.js` 每 0.5 秒取一帧，用文字规则检查，并在每句旁白说完的那一刻再取一帧。错误码在方括号里。

```bash
node kit/tools/scan.js <视频>                       # 第一种语言，全片
node kit/tools/scan.js <视频> --lang en --from 20 --to 55
```

| 错误码 | 含义 | 处理办法 |
|---|---|---|
| `EXPECT` | 某句旁白说完的那一刻，逐句对应表要求的文字不在画面上，或不完整（被画面边缘切掉、伸进字幕条、不透明度不到一半都不算数） | 用 `look.js <视频> <句号>` 看那一刻实际有什么。常见原因：元素出现得太晚；镜头推得太近把它切掉了；文字与要求不一致；一句完整的文字被拆进了多个块级元素 |
| `NOTEXT` | 某句旁白说完时画面上没有任何文字，也没有任何图形 | 同上 |
| `OVERLAP` | 两段文字的范围重叠超过 20%，持续 1.5 秒以上 | 挪开其中一个，或让旧的先退场。确属有意压盖才加 `data-overlap-ok` |
| `SMALL` | 文字的实际大小（算上镜头缩放）小于 `check.min_font`，持续 1.5 秒以上 | 放大字号，或别把镜头拉得那么远 |
| `CONTRAST` | 文字与它底下的颜色对比度不够：56px 以下要 4.5:1，以上要 3:1。先按 DOM 推断底色，推断不合格时再截下那一小块按实际像素量 | 换一组颜色搭配 |
| `CAPWIDE` | 字幕在画面上折成了两行，或宽到离两侧不足 96px | 拆成两句或删字 |
| `EMPTY` | 画面上 1 秒以上没有任何内容（整屏的章节卡算内容） | 把下一个元素的入场提前，或让上一个元素晚点走 |
| `STILL` | 画面 3 秒以上没有任何变化（不算字幕与常驻角标；SVG 与 canvas 里的变化算） | 加镜头漂移或元素动作 |
| `NONDET` | 同一时刻，「顺着播到这里」和「直接跳到这里」的画面不一样 | 检查：有没有元素缺少「入场前不可见」的初始状态；有没有在 `F()` 里累加变量；同一个属性有没有被两个补间在重叠的时间段里同时改；有没有用带 `overwrite` 的补间互相覆盖 |
| `PAGE` | 页面脚本报错，资源加载失败，或 `T()` 找不到句号、词 | 报错信息里有原因。`word not in cue`：这个词不在该句的合成文本里，用 `timeline.js <视频> <句号>` 查可用的词 |

提示（`!` 开头，不影响通过，但要逐条看一眼）：

| 提示码 | 含义 |
|---|---|
| `CUT` | 文字被画面边缘切掉 1.5 秒以上。推近时边缘的次要文字被切属正常；被切的是这一刻的主体就要改 |
| `CAPZONE` | 文字伸到了字幕条里 |
| `MARGIN` | 文字离画面左右边缘不足 `check.margin` |
| `DENSE` | 同时可见的文字超过 `check.dense` 段（缺省 16）。考虑分步出现 |

**逐句对应表**是可选的：在视频目录下放 `expect.<语言>.json`，写明每句说完时画面上必须有的文字：

```json
{ "a3": ["COMMAND.COM"], "b2": ["echo hello", "回显||ECHO"] }
```

`甲||乙` 表示二者有其一即可；比较时忽略空白与大小写。这张表由制作方在分镜定下之后写；字幕断句改了，句号随之变化，要按新句号重写，不能沿用断句前的表。

## 3. 低清预演

```bash
node kit/tools/preview.js <视频> [--lang en] [--from 秒 --to 秒]
```

用四分之一分辨率、15 帧/秒快速渲染一遍，再从像素层面找静止段。它比 `scan.js` 的 `STILL` 更接近观众的实际感受：元素在变但变化太小时，这里会查出来。超过 `check.still_seconds`（缺省 3 秒）的静止段必须消除。整片预演且已有混音时，另出一条带音轨的 `out/<语言>/preview.mp4` 供快速通看。

## 4. 渲染与封装的完整性

渲染（`render.js`）的每一层都有核对，任何一步对不上都以非零码退出：

| 核对 | 说明 |
|---|---|
| 每张截图 | 验 PNG 的头、尺寸与结尾；不合法就重截，重试六次 |
| 截图的像素格式 | 个别帧会因为合成层边缘的透明像素变成带透明通道的 PNG；入管道前改写成不带透明通道的（否则编码器中途重建滤镜图，成片悄悄丢帧） |
| 每一段 | 编码完用 `ffprobe` 数帧，不符就单独重渲这一段，最多两次 |
| 整片 | 拼接后再数总帧数。日志末行应是 `verified frames=<总帧数>` |

封装（`finish.js`）先核对画面帧数、声音时长与时间线总长三者一致，不一致就不封装。封装后报告：

- 规格（分辨率、帧率、时长）与响度（目标 −16 ± 1.5 LUFS，或本片 `audio.lufs` ± 1.5；峰值不高于 −1 dBFS）。
- 画面基本不动达 3 秒以上的段落（不看字幕条）。
- 空画面检查：几乎是空的时段（占比不足 0.6%，持续 0.3 秒以上）与内容很少的时段（不足 2%，持续 1.2 秒以上）。常驻角标所在的区域在 `check.blank_ignore` 里排除。换屏途中内容还没进场、一屏开头等关键词等得太久，都会在这里显出来。

结果写入 `build/finish.<语言>.json`。响度与真峰值在最终 AAC 编码后的 MP4 上测量；各音轨版本都测真峰值，超过上限时重新限幅与封装。持续到片尾、没有结束事件的静止段也会计入。

报告与实际文件按内容关联，`check.js --final` 核对以下记录：

| 记录 | 绑定的内容 |
|---|---|
| `out/<语言>/video.json` | 渲染开始时的源码快照、实际画面文件的 SHA-256、帧数与规格 |
| `build/audio.<语言>.json` | 旁白、配乐及辅助源文件、源码时序、正式混音配置和输出音轨的 SHA-256 |
| `build/finish.<语言>.json` | 当前渲染、混音输入、封装配置、每个最终 MP4 与字幕的 SHA-256、最终文件上的测量 |
| `build/covers.<语言>.json` | 源码快照与四个封面文件的 SHA-256 |

文件被替换、混音或源码过期、报告缺项，均不能沿用旧结论。生成期间输入发生变化时也失败，不能把完成后的新源码补记成旧画面的依据。`--no-blank` 只供临时出片，其报告不能通过最终交付检查。媒体命令失败不会写入新的成功报告。

旧报告缺少这些内容记录时，按原制作版本恢复归档，或在已获授权的后续制作中重跑对应工具；不能手填校验和冒充完成过检查。已发布影片仍按冻结规则处理。

成片后先核对时长：成片的时长应等于脚本总长。抽帧总览里字幕与画面若对不上，优先怀疑丢帧而不是时间轴。

## 5. 看得完：可读时长

```bash
node kit/tools/readable.js <视频> [--lang en] [--scene <场景号> | --from 秒 --to 秒] [--all]
```

逐 0.1 秒取帧，找出画面上每一段文字从完整可读（不透明度过半、整块在画内、左右没被裁）到开始退场的时长，对照经验规则 F04 的下限「1.5 秒 + 字数 ÷ 5」。报告带场景号与句号，缺省只列不够的段落。打字机的中间状态与计数中的数字不计。它只保证读得完文字；一步机制做完后有没有留出看懂的时间，要连续正常速度观看判断。

## 6. 成片审查

渲染、封装之后做。发现问题就改、重渲、重查，直到这一轮查不出问题。能看图、能听声音的模型亲自看、亲自听；不能的，用文字与数值工具做到能做的部分，并在交付记录里写明没看、没听的范围。

### 6.1 叙事

对照 [经验规则](../lessons.md) 的 F01–F03、F10、F11、F13：标题、开头、各章与结尾是否回答同一个问题；关键机制是否用同一个简单例子逐步走完；术语、名称与比较口径是否在第一次出现时交代；史料、版本清单、代码名与规模数字是否挤掉了必要解释。在成片上记下提出问题、各章推进、结尾回答的时刻。事实逐条正确、字幕不超长、自动闸门通过，都不能代替这一项。

### 6.2 事实

对脚本里的每一句：

1. `node kit/tools/look.js <视频> <句号>`，把画面上的每一段文字与 `research/FACTS.md` 的对应行逐字比对：终端回显、代码、数字、年份、版本号、引文、出处。
2. 画面上有没有 FACTS 里没有的事实性内容。有就补齐依据，或删掉；「待核实」条目不得留在成片中。
3. 重建的旧系统画面是否都带「示意」。
4. 有没有本机路径、主机名、用户名（F07）。
5. 会变化的外部事实联网复核，读原始来源，核对版本、环境、日期、单位与适用范围。
6. 标题、字幕、封面与各语言译文中的事实，有无遗漏条件、夸大比较或把推断写成定论。
7. 在 FACTS 的「复核」一节记录核查范围、日期、依据、发现的问题、更正与结论；没有实际核查的写「未核查」。

### 6.3 读音与节奏

```bash
node kit/tools/asr.js   <视频>     # 逐句并排打印「合成文本」与语音识别「听到」的文本
node kit/tools/stats.js <视频>     # 语速与停顿
```

读音的判断方法见 [文案与配音](script.md) 第 7 节。ASR 只筛候选；语气、读音与断句以人耳为准（F12、F17）。

### 6.4 旁白与画面的对应

按完整解释段核对，再用句号定位：旁白正在解释的对象或关系是否在场、注意力是否跟得上？一组对象可以持续在场并逐步推进，不要求一句一画面（F20、F22）。

- `scan.js` 的「逐句」一段给出每句说完时画面上的文字，通读一遍，确认没有「旁白已经讲下一件事了，画面还停在上一件事」。
- `node kit/tools/sheets.js <视频> cue` 把每句说完那一刻的画面拼成总览图，逐张比对；`sheets.js <视频> every 4` 通看版面与空屏。
- 关键词的动作抽查：`node kit/tools/look.js <视频> c6:0.7` 看 c6 进行到 70% 时的画面。每个场景抽两三处。
- `node kit/tools/margin.js <视频>` 按像素量每句画面的外接范围，列出贴近画面边缘的句子。

### 6.5 动态与声音

对照 [质量标准](../standards.md) 第 2–4 节与经验规则 F04–F06、F18–F21：

- 总览图看构图，低清预演看节奏，再以正常速度连续观看正式成片。每章说出它的主画面；动作抽查入场、中段、落点与转场接缝，专看渐变与飞入的中间帧。
- 与近期两部片子并排比较开头、换章与解释段的动作与配乐，说得出区别。
- 主混音、无配乐版、仅旁白版连续试听开头、密集段与章间。
- 不能把「没有静止段」「音效覆盖率达标」记成观感或听感通过。

### 6.6 原创、片尾与开源链接

- 对照参考来源与 README「设计」里的记录，检查文案、分镜、标志性构图及动效有没有照搬现成产品。
- 先按[署名规则](../roles.md#5-署名)对照会话、审稿与交接记录逐一核对参与模型及分工；不能只比较 `credits` 与片尾，否则两边漏掉同一位参与者仍会通过。型号未查明的继续留在制作期。
- 逐个语言、逐个交付版本看实际片尾：「策划：WaterRun」、全部参与模型与分工、「开源视频」与完整的 `github.com/Water-Run/ft`，字号、对比度、停留时间够不够读完；片尾没有人声。交付前打开仓库页面，确认链接可公开访问。
- 核对片尾的 GPL 标识，并按[开源交付清单](../reference/third-party.md#对应源码与发布材料)检查对应版本的源码、可编辑材料、制作步骤和第三方权利。第三方制作也要完成。工具检查文字是否出现，不能认证授权或源码包的完整性。

## 7. 经验规则复核

交付前，在本片 `review/lessons.json` 里给 [经验规则](../lessons.md) 的每一条写结论：

| 结论 | 要写什么 |
|---|---|
| `pass` | `evidence`：成片的语言与时段、用什么方法查的（连续观看、逐帧、readable.js、试听），例如「zh 1:02–1:10 章卡稳定 3.4 s（readable.js）；全片连续观看一遍」 |
| `n/a` | `note`：本片为什么不适用，具体到本片 |
| `open` | `note`：问题是什么、为什么交付时仍未解决；同时写进 README「交付」，由策划者决定是否接受 |

结论只写实际做过的检查。没看、没听、只抽样的范围如实写；文件生成成功、数值过闸、改了流程文档，都不能记为 `pass`。`check.js --final` 只核对每条都有结论，不判断结论是否属实。

## 8. 交付记录

写在本片 README 的「交付」一节（旧片在 `DELIVERY.md`）：

- 成片文件、语言、时长、规格、响度——在最终编码的文件上测（F08）。
- `check.js --final` 的结论；记为 `open` 的经验规则。
- 成片审查中发现并改掉了什么。
- Credit 核对：参与者名单所据记录、每个最终文件片尾的核对时刻与结论；没查的明确写「未核」，不以字段检查代替。
- 开源交付：许可、源码地址与版本、必要外置材料及校验和、第三方权利核查结论。
- 实际看过、听过的范围；没看、没听的部分，以及供人通看的总览图位置。
- 制作中的取舍及理由；推翻了准备方哪些建议、为什么。
- 未做或未通过的项目，没有就写「无」。

发布之后的平台记录写进 `project.json` 的 `release`，评价写进 README 的「评价与复盘」，见 [发布与收尾](release.md)。语体客观克制：陈述做了什么、结果是什么，不写自我评价。

## 9. 已交付的片子能否重建

交付后先按 [发布与收尾](release.md) 归档源码版本、原配音和检查证据，再清理生成物；检查归档用 `clean.js --verify`。制作机已经清理时，须恢复对应版本的输出与报告，才能重跑完整的交付闸门。

仓库里只有源码，生成物留在制作机上。按 README「复现」的命令重做时：

- 旁白：在线语音服务的输出可能随时间变化，时长随之略有不同；画面会自动跟着走。
- 混音：确定性的，同样的输入得到逐样本相同的输出。
- 画面：同一份源码、同一版本的浏览器与字体，画面在压缩噪声之内一致。画面依赖播放历史的旧片子例外，见该片 README。
- 封装：无声画面原样复制；声音由同一条混音与同一个增益得到。
