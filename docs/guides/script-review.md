# 文案、用户校对与定稿

用户应能直接阅读全文、按句号指出问题并确认一个明确版本。制作者负责把反馈改进源码、解释取舍、核对事实和保留记录。自动检查负责发现版本不一致，不能代替人的判断。

## 1. 文件各管什么

| 文件 | 作用 | 谁改 |
|---|---|---|
| `src/js/script.js` | 唯一文案源稿，包含旁白、字幕、章节与读法 | 制作者 |
| `research/FACTS.md` | 每句事实的依据、范围、核查与审稿摘要 | 制作者据证据维护 |
| `review/script.<语言>.<内容哈希>.md` | 从源稿导出的只读全文，带句号、章节和预估时长 | 工具生成，不手改 |
| `review/NOTES.md` | 交审说明、术语表、逐条意见、修改回应、确认记录 | 制作者记录用户的真实意见 |
| `review/approval.json` | 当前各语言的确认状态、内容哈希、确认者、时间与依据 | 人工确认之后据实填写 |
| README 的当前状态 | 当前轮次、待办、下一步 | 制作者 |

这些文件都入库，公开前脱敏。用户可直接在会话中反馈，不需要编辑 JS 或 JSON。只保留确认所需的必要摘录或可定位记录，不整段复制私人会话。

## 2. 从草稿到确认

1. 取证后先写中文稿，同时说明目标观众、核心问题、章节各自的答案、舍弃的材料与时长预算。术语逐个列出首次出现和解释句号。片尾内容与停留时间也在预算内。
2. `node kit/tools/script-review.js <视频> export` 导出主语言。先通读生成稿的「连贯阅读」检查叙事，再用「逐句校对」定位意见；静默 cue 不进入阅读正文。两种视图来自同一源稿，阅读视图不补标点、不改变句意。附上 README、FACTS 和 NOTES 即可交审。
3. 用户按“句号 / 章节 + 问题 + 建议”给意见。例如：`a2：这个术语第一次出现，先解释再给数字。` 制作者逐项记录接受、修改方式或保留理由；存在事实异议时先补取证。
4. 修改 `script.js` 后重新导出。新内容产生新文件，旧稿与旧意见保留。交回本轮全文、变更摘要和仍待决的问题，避免只给零散替换句。
5. 指定校对者明确确认某一版本后，在 NOTES 记录语言、稿本、内容 SHA-256、确认时间与依据，再填写 approval。没有回复、模型自评、自动测试通过都不算确认。
6. 中文确认后翻译。逐句核对译文的事实、语气和限定条件；用 `export --lang en` 导出并记录译文校对。需要分阶段制作时，`check --lang zh`、`tts.js --lang zh` 只处理已确认的中文；默认制作命令会检查所有选中语言。

```sh
node kit/tools/script-review.js <视频> export --lang zh
node kit/tools/script-review.js <视频> check --lang zh
node kit/tools/script-review.js <视频> export --lang all
node kit/tools/script-review.js <视频> check
```

export 首次创建的记录为 `pending`。以下只是字段说明，不能直接作为已确认记录使用：

同一内容哈希的稿本保留首次导出的估算时间；只改停顿时，用 `timeline.js` 查看当前时间，并在 NOTES 更新时长预算。配音后的时间以实测为准。

```json
{
  "schema": 1,
  "languages": {
    "zh": {
      "status": "pending",
      "content_sha256": "复制工具输出的完整内容 SHA-256",
      "reviewer": "与 project.json 的 review.reviewer 一致",
      "confirmed_at": "",
      "evidence": ""
    }
  }
}
```

真实确认后才将 `status` 改为 `approved`；日期用带时区的 ISO 格式，例如 `2026-10-18T14:30:00+08:00`；`evidence` 指向 NOTES 中该轮的确认记录。工具不会自动确认，也不会把已有确认的哈希改成新稿。

## 3. 确认后修改

| 改动 | 处理 |
|---|---|
| 含义、范围、增删句、章节结构、标题承诺 | 重新取证必要部分、导出全文，再交指定校对者确认 |
| 新语言或译文实质变化 | 导出该语言，逐句校对并记录确认 |
| 纯读法、停顿、lead / tail、配音实测时间 | 不改变内容确认；记录调整，重跑配音、回听、时间线和受影响的成片检查 |
| 不改含义的字幕断句、标点等编辑 | 在 NOTES 保留原稿、新稿、对应关系和“不改含义”的理由；沿用原有确认依据并更新对应内容哈希，无须新增审批；不能借此放行实质改写 |

**内容哈希覆盖哪些字段**：语言、片名（`project.json` 的 `titles`）、各场景的场景号与章节卡（编号与标题）、各句的句号、字幕文字、是否无旁白；**不含** `SAY` 读法表、`tts`、`gap`、`pause`、`lead`、`tail` 等时间与读法参数。所以改章名也会让确认失效。因此它会保守地拦住字幕文字变化，但无法判断语义，也不能发现把 `tts` 改成另一种陈述的行为；这些仍须逐句人工核对。改读法、时间与字体后成片是否过期，由时间线与成片检查负责。

## 4. 工具实际保证什么

新片默认带 `review.required: true` 和指定校对者。`tts.js`、`tts_probe.js`、`audio.js`、`preview.js`、`render.js`、`finish.js`、`covers.js` 及总闸门在开展工作前核对记录。缺失、未确认、哈希过期、确认者不符或缺少时间与依据均失败。

这是可审计的工作约定与一致性检查，不是签名认证。能改源码的人也能改 JSON；不能因此把填过 JSON 当成人已经看过。不得关闭 `review.required` 来绕过确认。

既有视频不自动补造历史确认，也不追改当前制作任务。旧格式视频未设置此字段时保留兼容提示；新版目录（`layout: 2`）缺少 `review` 会失败，不能靠删除配置绕过确认。原有 WaterRun 审稿规则继续执行；历史记录见各片 FACTS。需要接入版本检查时，先整理已有真实确认，再配置 `review`。原仓库新开工片子的指定校对者为 WaterRun；独立 fork 按 [getting-started.md](../getting-started.md) 设置实际负责人。
