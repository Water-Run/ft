# 审查与交付

验收分三层：自动闸门（工具查）、成片后的三项核心审查与完成度检查（对照输出逐项查）、交付记录（写给人看）。本文逐项说明各检查的含义、阈值与处理办法。事实依据、原创性、动画完成度与片尾名单都要单独核对，不能用自动闸门通过代替。

## 1. 自动闸门

```bash
node kit/tools/check.js <视频>            # 制作期
node kit/tools/check.js <视频> --final    # 交付前
```

输出逐项「✓ 通过 / ✗ 不通过」和明细，最后一行是结论。只有「全部通过」才算通过自动闸门；成片验收还须完成第 5 节的检查。

阈值与风格规则写在该片 `project.json` 的 `check` 段里（字段见 [tools.md](tools.md)）。它们是这部片子的标准，动笔之前定好；不允许为了通过而事后放宽阈值、把某一项改成提示，或删改逐句对应表。已交付的旧片子里降为提示的项目，在它的 README 里逐条说明原因。

| 项 | 查什么 | 不通过时 |
|---|---|---|
| 源码规则 | 场景、`config.js`、样式、封面里有没有破坏「画面只由 t 决定」的写法（CSS 动画与过渡、定时器、时间线回调、未固定种子的随机数），以及本片 `check.style` 打开的风格规则（阴影、渐变、模糊、圆角、调色板以外的颜色、系统字体、emoji） | 按提示的文件与行号改。确有理由的一行，在行尾注释里写 `lint-ok: <原因>` |
| 场景齐全 | 脚本里的每个场景都已实现并在 `index.html` 里加载；没有残留的 `TODO`；`check.camera` 为真时每个场景都用了镜头 | 补上 |
| 时长与节奏 | 每种语言都有实测时长；总长在 `check.duration` 范围内；每句字幕不超过一行；单句不超过 `check.max_cue_seconds` | 拆句、删字、调停顿 |
| 全片扫描 | 即 `scan.js`，每种语言各一遍，见第 2 节 | 见第 2 节 |
| 音效覆盖 | 事件总数、种类数、每场景数量、最长无声间隔、名称是否合法 | 给缺音效的动作补登记，见 [sound.md](sound.md) |
| 交付物（`--final`） | 成片、仅旁白版、字幕、四张封面是否齐全；成片时长、规格、响度；静止段与空画面；源码是否在渲染之后改过；本片 README 是否存在；委托制作时 `DELIVERY.md` 是否写全 | 缺什么补什么；源码改过就重新渲染和封装 |

系列里的一集另有一条提示：系列建议的栏目在本集缺了哪些、先后是否不同。它只是提示，不计入通过与否。

## 2. 全片扫描

`scan.js` 每 0.5 秒取一帧，用文字规则检查，并在每句旁白说完的那一刻再取一帧。错误码在方括号里。

```bash
node kit/tools/scan.js <视频>                       # 第一种语言，全片
node kit/tools/scan.js <视频> --lang en --from 20 --to 55
```

| 错误码 | 含义 | 处理办法 |
|---|---|---|
| `EXPECT` | 某句旁白说完的那一刻，逐句对应表要求的文字不在画面上，或不完整（被画面边缘切掉、伸进字幕条、不透明度不到一半都不算数） | 用 `look.js <视频> <句号>` 看那一刻实际有什么。常见原因：元素出现得太晚；镜头推得太近把它切掉了；文字与要求不一致；一句完整的文字被拆进了多个块级元素 |
| `NOTEXT` | 某句旁白说完时画面上没有任何文字，也没有任何图形 | 同上 |
| `OVERLAP` | 两段文字的范围重叠超过 20%，持续 1.5 秒以上 | 挪开其中一个，或让旧的先退场。确属有意压盖才加 `data-overlap-ok` |
| `SMALL` | 文字的实际大小（算上镜头缩放）小于 `check.min_font`，持续 1.5 秒以上 | 放大字号，或别把镜头拉得那么远 |
| `CONTRAST` | 文字与它底下的颜色对比度不够：56px 以下要 4.5:1，以上要 3:1。先按 DOM 推断底色，推断不合格时再截下那一小块按实际像素量 | 换一组颜色搭配 |
| `CAPWIDE` | 字幕在画面上折成了两行，或宽到离两侧不足 96px | 拆成两句或删字 |
| `EMPTY` | 画面上 1 秒以上没有任何内容（整屏的章节卡算内容） | 把下一个元素的入场提前，或让上一个元素晚点走 |
| `STILL` | 画面 3 秒以上没有任何变化（不算字幕与常驻角标；SVG 与 canvas 里的变化算） | 加镜头漂移或元素动作 |
| `NONDET` | 同一时刻，「顺着播到这里」和「直接跳到这里」的画面不一样 | 检查：有没有元素缺少「入场前不可见」的初始状态；有没有在 `F()` 里累加变量；同一个属性有没有被两个补间在重叠的时间段里同时改；有没有用带 `overwrite` 的补间互相覆盖 |
| `PAGE` | 页面脚本报错，资源加载失败，或 `T()` 找不到句号、词 | 报错信息里有原因。`word not in cue`：这个词不在该句的合成文本里，用 `timeline.js <视频> <句号>` 查可用的词 |

提示（`!` 开头，不影响通过，但要逐条看一眼）：

| 提示码 | 含义 |
|---|---|
| `CUT` | 文字被画面边缘切掉 1.5 秒以上。推近时边缘的次要文字被切属正常；被切的是这一刻的主体就要改 |
| `CAPZONE` | 文字伸到了字幕条里 |
| `MARGIN` | 文字离画面左右边缘不足 `check.margin` |
| `DENSE` | 同时可见的文字超过 `check.dense` 段（缺省 16）。考虑分步出现 |

**逐句对应表**是可选的：在视频目录下放 `expect.<语言>.json`，写明每句说完时画面上必须有的文字：

```json
{ "a3": ["COMMAND.COM"], "b2": ["echo hello", "回显||ECHO"] }
```

`甲||乙` 表示二者有其一即可；比较时忽略空白与大小写。委托制作时由准备方写好这张表，它是「旁白与画面对应」的硬约束。

## 3. 低清预演

```bash
node kit/tools/preview.js <视频> [--lang en] [--from 秒 --to 秒]
```

用四分之一分辨率、15 帧/秒快速渲染一遍，再从像素层面找静止段。它比 `scan.js` 的 `STILL` 更接近观众的实际感受：元素在变但变化太小时，这里会查出来。超过 `check.still_seconds`（缺省 3 秒）的静止段必须消除。整片预演且已有混音时，另出一条带音轨的 `out/<语言>/preview.mp4` 供快速通看。

## 4. 渲染与封装的完整性

渲染（`render.js`）的每一层都有核对，任何一步对不上都以非零码退出：

| 核对 | 说明 |
|---|---|
| 每张截图 | 验 PNG 的头、尺寸与结尾；不合法就重截，重试六次 |
| 截图的像素格式 | 个别帧会因为合成层边缘的透明像素变成带透明通道的 PNG；入管道前改写成不带透明通道的（否则编码器中途重建滤镜图，成片悄悄丢帧） |
| 每一段 | 编码完用 `ffprobe` 数帧，不符就单独重渲这一段，最多两次 |
| 整片 | 拼接后再数总帧数。日志末行应是 `verified frames=<总帧数>` |

封装（`finish.js`）先核对画面帧数、声音时长与时间线总长三者一致，不一致就不封装。封装后报告：

- 规格（分辨率、帧率、时长）与响度（目标 −16 ± 1.5 LUFS，峰值不高于 −1 dBFS）。
- 画面基本不动达 3 秒以上的段落（不看字幕条）。
- 空画面检查：几乎是空的时段（占比不足 0.6%，持续 0.3 秒以上）与内容很少的时段（不足 2%，持续 1.2 秒以上）。常驻角标所在的区域在 `check.blank_ignore` 里排除。换屏途中内容还没进场、一屏开头等关键词等得太久，都会在这里显出来。

结果写入 `build/finish.<语言>.json`，`check.js --final` 读它。

成片后先核对时长：成片的时长应等于脚本总长。抽帧总览里字幕与画面若对不上，优先怀疑丢帧而不是时间轴。

## 5. 成片后的三项核心审查与完成度检查

渲染、封装之后做。每项的结论写进本片 `research/FACTS.md` 的「复核」一节与 README（委托制作时写进 `DELIVERY.md`）。发现问题就改、重渲、重查，直到这一轮查不出问题。

### 5.0 叙事

先按 [feedback.md](feedback.md) 核对标题承诺、受众前提、章节推进与结尾回答。逐章说明观众在本章解决了什么问题，下一章为何接在这里；关键机制用同一个简单例子逐步走完。检查史料、版本清单、代码名与规模数字是否挤掉了必要解释。事实逐条正确、字幕无超长、自动闸门通过，都不能代替这项检查。

从本片「开工反馈应用」的 F01–F03 逐项回看：例子里每一步的原因是否解释，观众能否从输入跟到输出；名称与比较口径第一次出现时是否清楚。记录实际成片的时间窗口，尤其检查核心答案是否被无关材料推迟。不能把“已经有例子”当成解释完成，也不能仅用降低语速来填补推导缺口。

### 5.1 事实

对脚本里的每一句：

1. `node kit/tools/look.js <视频> <句号>`，把画面上出现的每一段文字与 `FACTS.md` 的对应行逐字比对：终端回显、代码、数字、年份、版本号、引文、出处标注。
2. 检查画面上有没有 `FACTS.md` 里没有的事实性内容。有就补齐依据并完成核查，或删掉；「待核实」条目不得留在成片中。
3. 重建的旧系统画面是否都带「示意」。
4. 有没有出现本机路径、主机名、用户名。
5. 版本史等外部事实联网复核，读取原始来源，核对版本、环境、日期、单位与适用范围；检查交叉印证是否来自独立证据，不能只看搜索摘要或模型回答。
6. 核对标题、字幕、封面与各语言译文中的事实，检查有无遗漏条件、夸大比较或把推断写成定论。封面在[制作流程](workflow.md)第 9 步生成后补查，交付前完成。
7. 在「复核」一节记录核查范围、日期、依据、发现的问题、更正与复查结论；没有实际核查的项目写「未核查」。

### 5.2 读音与节奏

```bash
node kit/tools/asr.js   <视频>     # 逐句并排打印「合成文本」与语音识别「听到」的文本
node kit/tools/stats.js <视频>     # 语速与停顿
node kit/tools/sheets.js <视频> every 4     # 每 4 秒一帧，通看版面与空屏
```

读音的判断方法见 [script-and-voice.md](script-and-voice.md) 第 7 节。节奏上不应有「过快」「过长」「停顿过短」的句子。

### 5.3 旁白与画面的对应

对每一句：这句话讲的东西，是不是在这句话的时间里出现在画面上，并且是画面的主体？

- `scan.js` 输出的「逐句」一段给出了每句说完时画面上的文字，通读一遍，确认没有「旁白已经讲下一件事了，画面还停在上一件事」。
- `node kit/tools/sheets.js <视频> cue` 把每句说完那一刻的画面拼成总览图，逐张比对。
- 对关键词的动作抽查：`node kit/tools/look.js <视频> c6:0.7` 看 c6 进行到 70% 时的画面，确认对应的元素此刻已经出现。每个场景抽两三处。
- `node kit/tools/margin.js <视频>` 按像素量每句画面的外接范围，列出贴近画面边缘的句子；有意出血的句子记在 `check.margin_skip` 里并写明原因。

### 5.4 动态与声音

对照 [standards.md](standards.md) 第 2–4 节逐条自查；出试听片；数值自检的读法见 [sound.md](sound.md)。

- 用总览图检查构图与图形细节，用低清预演检查节奏，再通看正式成片；代表性动作抽查入场、中段、落点与转场接缝。逐项检查主体层级、运动中的可读性、路径与缓动、遮挡、闪烁、跳位和穿帮。
- 记录具体片段、缺陷与修正结果。仅有镜头漂移或通过静止检测，不能据此认定动画精美精良。
- 无法看图或播放时，记录已做的文字与数值检查、待复核的片段和文件位置；观感仍属待确认，不记为已通过。

### 5.5 原创、片尾名单与开源链接

- 对照参考来源与设计记录，检查文案、分镜、标志性构图及动效有没有照搬现成产品，或仅换色、换字、换标志。引用材料与自行设计的内容须有清楚区分，标准见 [standards.md](standards.md) 第 2 节。
- 逐一检查各语言、各交付视频版本的实际片尾：包含「策划：WaterRun」（英文 `Planning: WaterRun`）及全部实际参与模型与分工，名称、版本与 `FACTS.md` 的「制作署名」记录一致，没有遗漏或虚构。
- 核对片尾包含「开源视频」（英文 `Open-source video`）和完整可读的 `github.com/Water-Run/ft`；交付前打开 [GitHub 仓库](https://github.com/Water-Run/ft)，确认链接可公开访问、指向本视频源码所在仓库，并与 `FACTS.md`、README、委托片的 `DELIVERY.md` 一致。仅在说明文档中列链接不能通过。
- 核对名单的字号、对比度、停留时间与完整可见性；确认能逐项读完，并与 README、委托片的 `DELIVERY.md` 一致。名单只出现在文档中不能通过。
- 抄袭、事实未核实、已发现的动画缺陷、署名缺漏或开源链接缺失、错误，须修正后复查；未完成的检查如实记为待复核，不能写「全部验收通过」。

### 5.6 阅读时间与跨片重复

- 对每张章节卡和内容卡，记录各语言文字全部到位至开始遮挡或退场的有效阅读区间；正常速度能读完并理解图形关系。入场、退场不计入，不能只看静帧和章节总时长。
- 与近期两部视频比较开头、换章和解释段：运动是否只是反复擦除，气流声是否机械重复，配乐是否仅换了音色。对照 [scenes.md](scenes.md)、[sound.md](sound.md) 和 [feedback.md](feedback.md) 记录具体差异。
- 不能将“没有静止段”“音效覆盖率达标”记成观感或听感通过；无法连续观看或试听时如实保留待确认项。反馈文档更新不等于现有成片已经修好。

### 5.7 开工问题的结尾复盘

交付前必须对照本片 README 的「开工反馈应用」，按 [feedback.md](feedback.md) 第 7 节用同一组问题编号逐项写「结尾反馈复盘」，委托片同步到 `DELIVERY.md`。每项包含原计划、实际做法、最终 MP4 的语言与时间区间、证据文件、实际检查方式、结果和未解决项。不适用的项也要核对理由，不能漏行。

- F01–F03 查主问题、解释步骤、名称与边界；F04–F06 查稳定阅读时间、动作和音乐音效与近期两部的具体差别。已有正面对照不代表复制其所有视听做法。
- F07 查终端等取证画面、字幕、封面与说明里的个人路径等信息；从数据源脱敏后再检查最终成片。公开记录只保留脱敏证据。
- F08 对实际交付 MP4 重新读取分辨率、帧率、时长、音轨响度与峰值，并与文件名和 README 对照。记录哈希或可明确定位的版本；混音 WAV、旧报告与文件名不能代替最终编码文件的检查。
- F09 对技术异议写明一手核查依据、适用范围与结论，归入 `FACTS.md`；用户分数、作者自评、观众评论和制作者推断保持各自来源。
- 结果区分「已验证」「已修改待复核」「待修改」「待事实核查」「不适用（原因）」。未连续观看、未试听或只抽样的范围明记，不能写整体已通过。发现新共性问题追加反馈总账，旧片改后另存复测，不覆盖旧分数。

本项是制作与交付记录要求，不新增人工审批环节；文案实质改动沿用现有审稿规则。文档已更新、实现已修改、成片已验证是三个不同状态。

## 6. 交付记录

自制的片子，交付记录写在本片的 `README.md` 里；委托制作的片子另有 `DELIVERY.md`（格式见 [delegation.md](delegation.md)）。两者都要写清：

- 文件位置、时长与规格、响度。
- 闸门结果。
- 三项审查中发现并改掉了什么。
- 开工反馈表与结尾同编号复盘：成片时间点、验证证据、结果、遗留问题；规则更新与实际影片修复分别记录。
- 原创检查的参考来源与结论；动画完成度的检查范围、缺陷与修正；片尾名单、各版本出现的时段及核对结果。
- 需要人来判断的事项：配乐与音效的听感（制作者听不到）、音色、画面观感（制作者看不到图时如实写明，并指出供人通看的总览图）。
- 制作中的取舍及理由。
- 未做或未通过的项目。没有就写「无」。
- 从头重新生成成片的命令序列。
- 发布（见 [workflow.md](workflow.md) 第 11 节）：平台、日期、视频链接、平台上的标题与时长、所属合集，以及片尾「开源视频」的仓库地址打开核对的结果。尚未发布就写「未发布」，发布之后按第 11 节回填。

语体客观克制：陈述做了什么、结果是什么，不写自我评价。只写实际运行过的命令和实际得到的输出；没做的写「未做」，没通过的写「未通过」并附上工具输出。

## 7. 已交付的片子能否重建

仓库里只有源码，生成物留在制作机上。按复现命令重做时：

- 旁白：在线语音服务的输出可能随时间变化，时长随之略有不同；画面会自动跟着走。
- 混音：确定性的，同样的输入得到逐样本相同的输出。
- 画面：同一份源码、同一版本的浏览器与字体，得到的画面在压缩噪声之内一致。画面依赖播放历史的旧片子例外，见该片 README 的「已知问题」。
- 封装：无声画面是原样复制的；声音由同一条混音与同一个增益得到。
