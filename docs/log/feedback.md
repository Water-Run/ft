### 补充：2026-10-10，InnoDB 第一版

WaterRun 看过《事务性与现代化：InnoDB》第一版的低清预演后的直接意见（原话照录）。第一版因此作废，按下表重做。

| 编号 | 反馈（原话） | 制作上的处理 |
|---|---|---|
| P6 | 「镜头一直晃来晃去要减少，作为科普视频不要干扰注意力」 | 停留时不做往复平移或环绕；镜头只在站与站之间移动，停留时最多极慢地单向推近。「任意 3 秒有可见变化」由跟着旁白出现的高亮、标注与图形变化满足，不靠镜头摆动凑数 |
| P7 | 「美术风格需要契合 MySQL && InnoDB 的风格，而不是抄袭之前别的项目的」；「设计语言不应该用之前 150s 的那个，完全不同的系列，完全重做的」 | 开工先取证讲解对象自己的视觉（标志、官网样式表、官方文档插图的配色、字体与图形），从中建立设计语言，并写明出处。与近期各片、尤其其他系列并排比较：只换强调色、保留同一套纸色底与平涂版式，不算新的设计语言 |
| P8 | 「不要一直提及本实验，事实上只要开头 MySQL 9.7 的一句话即可」 | 演示环境只在开头交代一次；正文直接讲现象与机制，实验步骤写成叙述，不反复说「本实验」「实验中」「日志显示」。实测与示意的区分留在画面标注和 FACTS 里 |
| P9 | 「参考 MyISAM 对引擎本身的介绍，要通俗易懂，易于理解」；「解释也有很多缺口，比如出现 SDI 时，动画并没有展现是什么的解释，目标观众——不了解 InnoDB 的读者看的懵逼」；「包括脏读之类的你都没解释」 | 每个术语第一次出现时，旁白用一句话讲清它是什么、为什么需要，画面同时给出对应的图形；讲不清或不需要的术语不出现。原始数值（页类型编号、十六进制、日志代码）只在支撑解释时出现。交审时附「术语—解释句」清单 |
| P10 | 「确保画面信息量完整的同时流畅自然」 | 画面要承载旁白的全部要点，同时运动连贯；不以删减信息换流畅，也不以堆叠文字换完整 |
| P11 | 「重新组织内容，制作新版本，搞明白定位，参考 MyISAM 的，那个讲的就还可以」；「主线还是清晰的，MyISAM 引入事务性 → 介绍事务性 → InnoDB 这样，所以一般引擎介绍 10 分钟，他有 15」 | 系列定位是「一个引擎怎样实现」：引擎部分按一集的正常体量组织（约 10 分钟），沿「怎么放、怎么找、怎么改、怎么并发、出错怎么办」展开；为引出概念增加的部分单独计时，不挤占引擎部分 |
| P12 | 「片尾不用配音」 | 片尾名单只在画面上展示，旁白不读 |
| P13 | 「配音体现 InnoDB 的现代感，又有一些年头没那么新」 | 声音的气质按讲解对象的年代与定位选择；交审时附试听，由策划者确认 |

| 编号 | WaterRun 的反馈 | 后续要求 |
|---|---|---|
| P24 | 视频的一个普遍问题是「刷一下」：观众信息还没看完，画面突然就过去了。作为核心反馈。例：OpenCart 07:12 | **F04 升为核心规则**。实测 OpenCart 主片 6:58–7:16（每 0.5 秒一帧）：这一段大部分时间镜头推在右半边，左侧订单面板不在画内；「写入被拒，停在这里」与左侧红色报错框约 7:12.5 才完整出现，7:13.0 已进入下一段的转场模糊，完整可读不到 1 秒，而这一屏有十余处文字。要求先排信息再排动作，关键状态完整出现后按「1.5 秒 + 字数 ÷ 5 字/秒」留足稳定时间 |

每次文案交审先给出四项：目标观众已有的知识；看完应能回答的一个核心问题；各章怎样推进这个问题；哪些查到的材料决定不讲。每章按“问题 → 必要解释或演示 → 本章答案 → 下一问”检查。删除一段不影响主线，就考虑移入说明或后续选题；保留它必须能说清用途。

定稿与成片审查分别检查标题、开头、章节和结尾是否仍在回答同一个问题。尤其检查：例子是否变成主题、版本清单是否代替因果、实现参数是否先于概念、史料是否打断推导。叙事未解决时，不靠加快旁白、增加动画或扩充片长来补救。
