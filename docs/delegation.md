# 委托制作

委托制作指：准备方把一部片子备到「读完目录就能开工」的程度，交给另一个模型完成场景与收尾。本文规定两方各做什么、任务书怎么写、怎样交接与验收。自制的流程见 [workflow.md](workflow.md)。

已有的实例：[《古代来的 Shell：Windows 批处理（.bat）》](../videos/standalone/windows-batch/)，由 Claude 准备、DeepSeek 制作，它的 `AGENTS.md`、`brief/` 与 `DELIVERY.md` 保留在目录里。

## 1. 分工

| 步骤 | 准备方 | 受托模型 |
|---|---|---|
| 立项、环境 | 做 | 开工前复查环境 |
| 取证 `research/` | 做完 | 不重做；成片后把复核结论写进「复核」一节 |
| 旁白：脚本、合成、读音核对 | 做完并定稿 | 只可调停顿，不改文字 |
| 视觉系统 `style.css` | 定好，并用关键帧验证 | 在系统内构图，不另起一套 |
| 关键帧与一段示范场景 `src/design/` | 做 | 照着写 |
| 逐句对应表 `expect.<语言>.json` | 写 | 不删改 |
| 任务书 `AGENTS.md`、`brief/` | 写 | 读 |
| 分镜细化、各场景、常驻元素 | 留空壳或草稿 | 做 |
| 音效编排、混音、试听片 | — | 做 |
| 封面 | — | 做 |
| 渲染、封装、三项审查 | — | 做 |
| 交付说明 `DELIVERY.md`、本片 `README.md` | — | 写 |
| 验收 | 复跑闸门、通看总览图、核对交付说明 | — |

留给受托模型的部分要足够完整，这样才看得出它的水平；准备方不替它把场景写完，验收时也不替它整链路复跑一遍——只核对它报告的结果是否属实。

## 2. 新建

```bash
node kit/tools/new.js standalone/<视频> --title "…" --delegate "<受托模型>"
```

比自制多生成：`AGENTS.md`（任务入口）、`brief/01…06`（任务书骨架）、各语言的 `expect.<语言>.json`（空表），并在 `project.json` 与片单里记下 `production.mode: "delegated"`。

## 3. 准备方要做的

按 [workflow.md](workflow.md) 做完第 0–4 步，然后：

1. **示范场景**。挑信息最密的一小段（十来秒），写成 `src/design/` 下的一个场景文件，用到镜头、两三种入场动作、打字机、音效登记。它是受托模型照着写的范例，要经得起逐行模仿。
2. **参考关键帧**。三四张静态版面放在 `src/design/` 下的一个页面里：标题、信息最密的一屏、图解、章节卡。
3. **场景空壳**。每个场景一个文件，只有 `scene('<场景号>', ({ root, s, c0 }) => { /* TODO */ });`，并在 `index.html` 里按顺序加载。
4. **逐句对应表**。`expect.<语言>.json`：每句说完的那一刻画面上必须完整出现的文字。它把「旁白与画面对应」变成工具能查的硬约束。写法见 [review.md](review.md) 第 2 节。
5. **检查配置**。`project.json` 的 `check` 段按本片的标准定好：总长范围、最小字号、静止上限、风格规则（调色板、字体、是否平涂）、音效覆盖率。
6. **任务书**。填写 `AGENTS.md` 与 `brief/`。通用规则已经在 `docs/` 里，任务书只写本片特有的内容：

   | 文件 | 写什么 |
   |---|---|
   | `AGENTS.md` | 要做出什么；分工；阅读顺序；环境；工作步骤与过关条件；铁律；完成的定义 |
   | `brief/01-mission.md` | 主题、结构表、本片的质量要求、术语写法、交付物清单 |
   | `brief/02-script.md` | 旁白全文；哪些能调、哪些不能改 |
   | `brief/03-visual.md` | 颜色与允许的搭配、字号阶梯、版式、部件的类名与用法、图形语言、禁用的做法 |
   | `brief/04-storyboard.md` | 逐场景：要让观众明白什么、空间怎么布置、每句对应画面上的什么、建议的做法 |
   | `brief/05-motion-sound.md` | 本片在镜头、动作、音效、配乐上的特别规定 |
   | `brief/06-acceptance.md` | 本片的阈值及理由；事实审查时特别要查的；交付说明的格式 |

7. **交接检查**：

   ```bash
   node kit/tools/check.js <视频> --handoff
   ```

   它查：任务书里没有残留的「待填」与占位符；取证已完成；视觉系统已定；`src/design/` 里有范例；各语言的旁白已合成；逐句对应表不为空且句号都存在；每个场景都有对应的文件。全部通过后再交接。

写任务书时的要点：

- **把「好」写成可以照着做、可以用工具查的规则。** 受托模型很可能看不到画面、听不到声音。「构图要有张力」没有用；「主体在 x 96…1824、y 56…928 之内；最大的字是最小的字的四倍以上；强调色一屏最多三处」有用。
- **每一步给出命令与过关条件。** 工作步骤写成表：做什么、运行什么、看到什么才算过。
- **说清已经做好的和归它做的。** 已经做好的部分明确写「不要重做」，否则它会从取证开始重来。
- **把铁律单独列出来**，并说明违反的后果与原因（例如为什么画面必须只由时间决定）。
- **事实只许来自 `FACTS.md`。** 不知道的不写，不凭记忆补充。
- **要求如实报告。** 没做的写「未做」，没通过的写「未通过」并附工具输出；听不到、看不到的事如实写明。
- **预先说明何时该停。** 只有两种情况停下来报告：工具有缺陷导致无法继续；发现取证或旁白里有事实错误。其余的取舍自己决定并记录理由。

## 4. 受托模型的入口

受托模型在仓库根目录开工，入口是该片目录的 `AGENTS.md`。它按其中的阅读顺序读任务书与仓库文档，按工作步骤一路做到 `check.js --final` 全部通过，写好 `DELIVERY.md`。

不同的模型由各自的运行框架启动；任务的第一句话只需指明入口，例如「读 `videos/standalone/<视频>/AGENTS.md`，按它开工」。

## 5. 交付说明

受托模型把 `DELIVERY.md` 写在该片目录下，结构见任务书的 `brief/06-acceptance.md`：交付物、闸门结果（贴完整输出）、三项审查、需要人来判断的事项、取舍、未做或未通过、复现命令。`check.js --final` 会查它是否存在并写全。

## 6. 验收

准备方收到交付后：

1. 运行 `node kit/tools/check.js <视频> --final`，结果应与 `DELIVERY.md` 里贴的一致。
2. 通看 `node kit/tools/sheets.js <视频> cue` 与 `every 4` 的总览图：对照 [standards.md](standards.md) 看版面与节奏；对照 `FACTS.md` 抽查画面上的事实性文字。
3. 核对 `DELIVERY.md` 的陈述是否属实，尤其是「未做或未通过」与「需要人来判断的事项」。
4. 检查它有没有为了过关而改规则：`kit/` 下的工具、`project.json` 的 `check` 段、逐句对应表都不应被改动（看这些文件的改动记录）。
5. 把 `AGENTS.md` 开头的状态改为「已交付」并注明日期；片单里把状态改为 `delivered`；在 [retrospectives.md](retrospectives.md) 里记下这次委托得到的经验。

验收只核对，不重做：不替它修场景，不重新渲染一遍来「确认」。发现问题时退回给受托模型，或记为已知问题。

## 7. 目录里留下什么

委托制作的片子比自制的多出三样，都入库、都保留：

| 文件 | 作用 |
|---|---|
| `AGENTS.md` | 当时的任务入口。交付后开头标明「已交付」，只作记录 |
| `brief/` | 当时的任务书，连同受托模型写的分镜细化 `storyboard-detail.md` |
| `DELIVERY.md` | 受托模型的交付说明 |

它们记录了「给了什么要求、得到了什么结果」，是下一次写任务书时最直接的参考。
