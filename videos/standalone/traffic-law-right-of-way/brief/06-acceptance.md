# 06 · 预研交接与成片验收

## 本次预研交接

要求语言、排期明确，事实可定位、场景条件可查、未决项清楚，Opus 能接续写稿。doctor 已执行，自动检查与原文阅读分别记录。

- `tools/check_research.py` 查来源、摘录、案例引用、中文配置和生成数据一致性。
- `tools/gen_data.py` 以输入哈希确认再生一致，不改案例语义。
- 保留采集成功与失败；HTTP 200、关键词命中不等于事实通过。
- 目录、TODO、片单一致，保留共享目录其他在制改动。
- 脚本和场景仍为模板，不 TTS、不渲染，不声称完整制作的 `--handoff` 已通过。

## 后续成片验收

依 `docs/review.md` 完成所有必需检查，并重点核对：

1. WaterRun 确认日期与稿本哈希；实际旁白、字幕一致，改事实重新核查。
2. 每句、标题、封面和道路图对应 FACTS；待核项不进定稿。交付前重查版本与标准；限定条件实际出现在图上。
3. 来向去向、右侧通行、信号控制对象、相对右方、同出口冲突、让行主体一致；无虚构法定距离、速度、责任比例，示意标签可见。
4. 正常速度能回答谁让谁、为什么、哪个条件变化会改变答案；开篇和结尾回答同一问题。
5. 逐卡阅读区间、跨片动作与声音对照；如实记观看、试听或抽样范围。
6. 只有中文。最终编码实际帧率、分辨率、时长、音轨、哈希与记录一致；真实输出跑最终闸门，保存结果并处理失败。
7. 片尾包含 WaterRun、实际参与模型及分工、「开源视频」和 GitHub 链接；名字可核、可读，未参与者不署名。
8. README 与 `DELIVERY.md` 按 F01–F09 给最终 MP4 时间、证据、结果、遗留项。全部完成后才 delivered、勾 TODO，投稿后据实际链接回填。

`DELIVERY.md` 在真实交付时创建，包含仓库要求的交付物、闸门、三项审查、原创完成度、署名、反馈、需人判断、未通过项、复现命令；当前不创建虚假交付说明。
