## 3. 连贯正文

### 开场

今天开一家网店，可以使用 Shopify 这样的托管服务，也可以自己部署商城软件。商家登录后台，上架商品、查看订单、安排发货，这些操作已经很熟悉了。

把时间拨回十多年前。如果想经营自己的网店，也有现成的程序可选：把文件上传到主机，准备一个数据库，再通过安装页面完成设置。

OpenCart 就是其中一套。它是免费、开源的 PHP 网店程序，一边是顾客浏览商品、下单的商店，另一边是商家处理商品和订单的管理后台。

在当时的建站市场中，它属于可以自行部署和修改的开源商城。安装工具提供它的程序包，开发者为它制作主题和订单扩展，商家可以在现成的商城上继续改造。

本片选的是二零一四年四月的 1.5.6.4，属于 1.5 系列后期。我们要看的是这个年代的实现，同时对照后来的 4.1 版，看看哪些做法变了，哪些分工还在。

先从日常工作进入后台。第一步，登录以后，系统怎样认出人、分配权限；第二步，订单怎样从数据库变成页面；第三步，改一次状态，程序和数据怎样一起变化。

最后看一个匿名的长期改造案例，理解这种后台怎样接上仓储、查询和导出。官方演示里的账号、客户和订单都是合成数据，案例也只展示匿名结构。

现在，点开这张旧后台的订单列表。浏览器发出请求，服务器查出记录，再把页面送回来。我们从这一下点击开始，把刚才的大纲逐步展开。

### 一次请求怎样找到代码

先把浏览器和服务器分开。浏览器负责显示页面，把点击和填写的内容发出去。处理订单的 PHP 程序，以及保存订单的数据库，在服务器一侧。

演示环境由 Linux、Apache、PHP 和 MySQL 组成。Linux 是操作系统；Apache 接收网页请求；PHP 执行业务代码；MySQL 保存和查询数据。

这次演示使用 PHP 五点三和 MySQL 五点五。作为对照，OpenCart 的新版四点一，已经要求 PHP 八点一或更高。运行环境变了，接收请求、执行程序和取数据的职责仍然可以分开看。

后台页面的地址，经过同一个入口文件。订单列表的地址里，还有一项 route 参数，值是 sale/order。

route 是路由，用来选择这次要执行的代码。程序按这个值找到订单控制器，再执行相应的方法。

控制器负责组织这一次页面工作。它接收条件，安排取数据，再决定怎样输出。查询订单的代码交给模型，页面的具体排法交给模板。

每次请求到来，都会重新经过入口初始化：连接数据库，读入设置，再建立这次处理需要的对象。

入口还准备共用的设置、语言和计量对象，供后面的代码使用。例如每页显示多少条，来自后台设置；界面文字则从语言资源中取出。

但订单控制器还不能马上查订单。入口先安排了登录和权限检查。没有通过，程序会转去登录页或拒绝访问的页面。

### 登录怎样核对身份

还没登录时，直接打开订单页，会先转到登录页。填写账号和口令后，表单把它们送到服务器，由登录代码核对用户表。

这个旧版本把账号条件和口令计算写进 SQL，让数据库参与比较。SQL 是向数据库提出查询或修改要求的语句。

对这次新建的账号，程序把口令与一段随机字符一起计算，保存计算后的摘要。这段随机字符叫盐，让相同口令也能得到不同的存储值。

登录时，输入的口令按相同方法计算，再和保存的摘要比较。账号、口令与启用状态符合条件，才算通过；不符合，就留在登录页并提示错误。

通过后，程序把用户编号写进会话。登录这一步回答了你是谁；之后打开订单页，还需要把这个身份带到下一次请求。

### 会话怎样接上下一次请求

下一次点击是一次新的请求。服务器用会话把它和先前的登录关联起来。浏览器保存一个会话编号，放在 Cookie 里，随后访问后台时把它带回来。

在演示环境中，会话内容保存在服务器的文件里。浏览器带回编号，服务器找到对应文件，读到用户编号，再查用户表确认这个账号仍然有效。

所以浏览器保存的是寻找会话的编号，登录身份保存在服务器一侧。账号失效或主动退出时，程序会销毁会话，后续受保护页面需要重新登录。

这个后台还生成一个令牌，一份放在会话里，一份附在后台链接上。访问订单页时，程序把请求中的令牌和会话里的令牌比较。

Cookie 会由浏览器自动附上；令牌则要求请求额外带回一个匹配值。这能限制只有 Cookie、却不知道令牌的请求。在演示中，删掉链接的令牌，就回到登录页。

不过，网址中的令牌也会进入浏览器历史和访问日志。这是这个旧后台的实现方式。身份和请求检查通过后，还要检查这个用户的权限。

### 权限怎样分配和执行

后台用户属于一个用户组。组里保存两份路由清单：access 决定能访问哪些功能，modify 决定能修改哪些功能。

管理员在用户组页面勾选这两类权限，保存后写入用户组记录。新请求查到用户所属的组，再把这些清单读出来。

演示店员的访问清单包含订单和顾客，修改清单只包含订单。打开用户管理时，检查发现它不在访问清单中，于是返回没有权限的页面。

这个判断发生在服务器。即使手工输入用户管理的地址，也要经过同一道访问检查。菜单是否显示，不是这里作出允许决定的依据。

能看订单，也不能自动推出能改订单。提交状态修改时，订单控制器还会检查 modify；如果组里只有访问权限，这条写入就会被挡下。

权限管理页面会从控制器目录列出可选功能。加入新的控制器后，还要为相应用户组配置权限，并在写入动作里执行修改检查。

至此，我们分清了三个问题：登录核对是谁，会话接续身份，权限决定这个人能做什么。现在，订单请求可以继续去取数据。

### 数据库怎样组织这些数据

数据库里不只保存订单。后台用户、用户组、设置和业务记录，各有对应的表。入口先用配置中的连接信息，建立程序到数据库的连接。

这里有两种账号：连接账号供程序访问数据库；刚才的后台用户账号，用来识别操作后台的人。它们各有自己的作用。

看一张七号演示订单。订单主表保存它当前的状态和金额；商品明细表保存买了哪些商品；历史表保存它的状态记录。

商品项和历史记录都带着订单编号。程序按这个编号，找到属于同一张订单的内容。一张订单可以对应多条商品项，也可以有多条历史记录。

图中的线表示按编号查找的关系。这些安装表没有声明外键约束；不能因为两个表都有订单编号，就认为数据库会自动处理所有关联变化。

模型负责组织业务查询。它把 SQL 交给数据库包装层，再由配置选定的驱动发给 MySQL。驱动负责连接、执行语句，并把返回结果整理成程序里的记录。

因此，控制器要的是这一页订单，模型决定怎样查，驱动处理和数据库的通信。这条分工，接下来用翻页看得最清楚。

### 列表怎样查出来

列表上的筛选条件和页码，会成为这次请求的输入。控制器读取这些条件，算出从哪条开始、这一页最多取多少条，再交给订单模型。

演示后台每页显示二十条。第二页的 LIMIT 20,20，表示先跳过二十条，再取二十条。数据库按这个范围返回记录。

模型把条件组成 SQL：从订单表取数据，按条件筛选，再排序，最后限制取出的范围。

除了取这一页，还要知道总共有多少条。另一条查询计算总数。演示数据有四十六张订单，所以按每页二十条，页面得到三个页码。

这个版本主要用字符串拼出 SQL。文本值先经过驱动的转义，部分数值先转成整数，再放进语句中的相应位置。

查询结果回来后，驱动把它变成程序可以使用的记录列表。这些数据接下来交给模板，才会成为屏幕上的表格。

旧驱动通过 PHP 的 mysql 扩展和数据库通信。对照的新版提供 MySQLi 驱动，使用了更新的接口。接口可以更换，业务代码仍然要说明查询条件，并处理返回记录。

有些反复使用的小清单，还会先查缓存。例如已发货、已完成这些状态名称。第一次需要时从数据库取出并缓存，下次可以复用；修改名称时会清掉相应缓存。

这里缓存的是状态名称清单。当前页的订单记录，仍按这次条件和页码查询。页面上的不同部分，可以采用不同的取数方式。

这一页需要哪些记录、总共有几页，现在都有了结果。下一步，是把数据放进页面。

### 数据怎样变成页面

控制器把结果放进页面数据，交给模板。模板包含 HTML，也包含 PHP 的输出和循环语句，把每条订单放进相应的表格位置。

公共页头和页尾，也有各自的控制器与模板。它们的输出再和列表内容组合，形成发给浏览器的页面。

后来的 OpenCart 四点一改用 Twig 模板。旧版直接嵌 PHP，新版用另一套模板写法；它们都在把控制器交来的数据，组织成要显示的页面。

这时，再看开头那次点击的测量才有意义。这次处理涉及四十九个程序和模板文件，发出十六条数据库语句，生成三万六千多字节的页面。

这些数值属于同一条演示请求，不是所有页面的固定开销。此时，HTML 正文已经可以发回浏览器。

浏览器收到 HTML 后，还会按其中的引用，取得样式、脚本和图片。这次列表页面，正文之外又请求了十九个文件。

页头的蓝色细纹，不是一张铺满屏幕的大图。原样式把一条很窄的图片横向重复；菜单和选中状态也使用对应的图片。

服务器组织出的结构，在浏览器里成为菜单、表格和按钮。页面脚本还负责局部交互；输入顾客筛选条件时，再请求一份名单，以 JSON 格式返回。JSON 用文本表示这些数据，页面脚本读到后显示建议项。

地址选择代码，检查决定能否继续，模型取得数据，模板拼好页面，浏览器再把它显示出来。列表查询走完了，修改订单又有什么不同？

### 改状态会写下什么

打开七号演示订单，把状态改为已发货。页面脚本发出一条后台请求，不必刷新整张页面，这种交互通常称为 AJAX。

这次请求仍经过登录和访问检查，订单控制器再检查修改权限。只获得查看权限的用户，不能靠这种请求完成这次写入。

先更新订单主表中的当前状态，再向历史表插入一条记录。前者回答现在是什么状态，后者保留这次状态记录。这是两次主要写入，后续还可能有读取和通知处理。

这份官方安装中的表，使用 MyISAM 存储引擎。存储引擎负责表在数据库里怎样保存和读写；MyISAM 不支持事务。

事务可以把一组修改，作为一个整体提交或回滚。为了看清区别，演示先开启事务，修改一个状态，再执行回滚。MyISAM 表里的改动仍然保留。

换成同一台数据库上的 InnoDB 副本，再做这组步骤，回滚就能撤回修改。

前面的两次 MyISAM 写入，没有靠事务绑定成一个整体。在两条语句之间出错，已经发生的写入不会自动一起撤销。

正常完成后，服务器返回渲染好的历史记录片段，浏览器替换页面的对应区域。这里返回的是一小段 HTML；前面顾客自动补全返回的，才是 JSON 数据。

### 业务怎样沿着它扩展

官方版本说明了早期后台的一种组织方式。长期改造之后，同样的框架还可能承载更多工作。这里看一个完全匿名的本地源码案例。

这份源码中，有采购、库存、订单、称重等业务，也有后来增加的查询与导出功能。它们属于长期改造案例，不能算作官方版本的原有能力。

关键不是数出了多少页，而是新功能怎样接进来。控制器仍组织一次操作，模型或连接器负责取得数据，模板负责把结果交给页面。

有些查询页换用了不同的数据连接器，再增加归档或导出操作。取数据的接口发生变化，页面仍按条件、请求和结果组织。

例如一个查询功能，可以接收日期和状态条件，调用数据连接器，再把结果交给列表或导出处理。入口、权限和页面组织仍有各自的位置；新增数据来源，则属于后来的改造。

这是本地源码的静态观察，画面数据全部重新构造。它说明旧的页面组织方式，可以和后来增加的功能共存；不代表线上每条业务都已经验收。

### 收束

回到订单列表。表头的筛选、下面的页码、状态旁的按钮，对应着不同的请求。入口、检查、模型和模板，把这些请求接到具体的代码与数据上。

和新版对照，运行环境、数据库接口与模板写法都在变化。但识别用户、判断权限、组织数据和返回结果，仍是后台要完成的工作。看懂这条请求，就有了理解这些变化的起点。
