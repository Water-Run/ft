# 数据库引擎

逐个讲解数据库引擎的内部实现：数据怎样落到磁盘或内存里，一次读写在引擎内部经过哪些步骤，这种设计换来了什么、放弃了什么。面向写过 SQL、没有读过引擎源码的观众。

## 定位

| | |
|---|---|
| 讲什么 | 逐个数据库引擎的完整底层科普：内部实现、数据怎样落盘、一次读写的全过程、这种设计的取舍 |
| 面向谁 | 写过 SQL、没有读过引擎源码的观众 |
| 怎么讲 | 深入底层、深入浅出；务必严格事实核查，以该引擎真实运行的数据与同一版本的源码为准，注明版本；视觉各取自所讲的引擎（见下） |
| 每集多长 | 按 WaterRun 2026-10-24 给的各集预期（见「制作顺序与时长」），作为参照而不是硬上限：本系列不是「XX 秒」系列，宁可稍长、多留白，也不让观众「刷」过去看不懂；留白也不过度（2026-10-19）。早先的 5–10 分钟与 InnoDB、PostgreSQL 的单独参照由此取代 |
| 语言 | 仅中文（片单 `languages`） |

## 全系列文案主线（2026-10-24 草案）

这是八集共用的叙事骨架。WaterRun 2026-10-24 看过后调整了制作顺序与各集在系列里引入的东西（见「制作顺序与时长」），据此从 MyISAM 开工；每集的文案、事实与设计仍在本集目录里完成并各自交审。下面凡是讲到具体机制的地方，是各集取证的出发点，不是已核事实：每集开工后按本集 `research/FACTS.md` 核对，核不实的改主线。时长按 WaterRun 2026-10-24 给的预期（P57），作为参照。

### 判断标准

**直观、清晰。** 正常速度看一遍就懂，不需要暂停反复看；以旧版 MyISAM 的讲法为基准：观众始终追着同一个对象，一次只推进一件事，先立整体结构再进局部，新信息回答当下的疑问。WaterRun 2026-10-24 的评价（[P59](../../docs/log/feedback.md#2026-10-24旧四集的认知负载)）：旧版 InnoDB、PostgreSQL 的 B+ 树「消失不见，直接到页内」，认知负载偏大；旧版 Firebird「需要暂停反复观看才能看懂」。新版每集交审前按这一条通读全稿，页内细节只在结构立住之后、且确实帮助理解时才讲。

### 一句话

同一个应用、同一群人：Alice 注册、被查到、过生日改年龄、最后注销；Bob 在她改动时读她的资料，Carol 想同时写，Dave 后来注册。八种引擎各演一遍这段经历，看下来是同一件事的八种做法，以及每种做法换来了什么、放弃了什么。

### 系列的弧线

| 段落 | 集 | 这一段推进了什么 |
|---|---|---|
| 服务型关系数据库 | MyISAM → InnoDB → PostgreSQL → Firebird | 从没有事务到有事务；从表锁到行锁，再到多版本；从预写日志到「小心写」 |
| 极小 | SQLite | 没有服务进程，一个库、一个文件 |
| 极大 | ClickHouse | 数据量的另一端：按列存，一次分析成亿行 |
| 不是表 | MongoDB | 记录变成文档 |
| 不在磁盘 | Redis、KeyDB 与 Valkey | 数据主要在内存里；系列结尾 |

### 叙事原则

WaterRun 2026-10-24 看过 MyISAM 重写稿后的判断（[P63](../../docs/log/feedback.md#2026-10-24新的不如旧的叙事与讲故事)）：「总体而言, 你新的不如旧的. 思考对叙事, 讲故事的理解」「理解我想要的 ,包括其它集」。旧版 MyISAM 好在哪里，就是各集要做到的：

1. **从一个简单、真实的瞬间开场，提出一个问题。** 「一条查询，一行结果，零点零零七秒；这一瞬间，数据库在磁盘上做了什么」。不用修辞包装，不先摆数字。
2. **从能一眼看全的小例子开始，复杂度跟着问题长。** 旧版先用 8 行的表把数据文件摊开，到 B 树需要深度时才拿出十万行的表。不为全系列统一而一上来用大表。
3. **层层递进：每一章回答上一章留下的问题，自然引出下一章。** 数据文件 → 删了怎么办 → 变长了怎么办 → 找起来太慢 → 索引与 B 树 → 一次查询 → 很多人同时用 → 出了事怎么办。
4. **时代感是故事的一部分。** 引擎属于哪个年代、哪个版本，被谁取代或取代了谁（「在 5.5 版本之前，默认的引擎就是 MyISAM」）。讲旧引擎用它那个时代的版本与文件（MyISAM 讲 `.frm`），新版本的差异作画面注解即可。
5. **讲故事是结构，不是修辞。** 观众被问题牵着走，每一步的结果成为下一步的输入；比喻只在确实帮助理解时用。数字只留观众要记住的那一两个，其余放进画面。
6. **画面不被台本绑死。** 旁白讲故事，画面承载细节：字节、偏移、版本差异、出处可以只在画面上出现，不必每句旁白都点名画面上的东西（F22）。
7. **有好底子的先保留。** 旧版叙事好的（MyISAM），以旧版原文为底只做必要修改；InnoDB、PostgreSQL 先保留旧版叙事的长处，补上缺失的整体结构；不推倒重写。

### 灵活度与各集侧重

WaterRun 2026-10-24（[P61](../../docs/log/feedback.md#2026-10-24各集的灵活度与侧重)）：「流程不要太固定了, MyISAM更多是一个开场的引子, 整体叙事贴近原版即可」「要有灵活度, 每一集」「侧重点也都不同, InnoDB引入事务性当然大头是事务, Pg前面讲过那就不是重点了」。下面的六个问题、人物与示例是全系列的共同底子，不是每集必须照走的流程；侧重表也只是举例（WaterRun：「重点则变成不同引擎的实现, 和InnoDB对比, 这只是一些例子」）：各集按自己的对象与在系列里的位置定侧重，前面几集讲深的内容，后面只用一两句交代到能看懂为止。

| 集 | 侧重 |
|---|---|
| MyISAM | 开场的引子：引入数据库引擎，叙事贴近旧版（定长行、删除与空位、变长行与碎片、B 树与一次查询、表锁与并发插入、没有日志） |
| InnoDB | 事务是大头：全成或全不成、隔离与锁、崩溃恢复；聚簇索引作为它的存放方式讲清楚 |
| PostgreSQL | 重点是另一种引擎实现，处处与 InnoDB 对照：表是堆而不是主键树、旧版本留在表里而不是 undo、回收靠 VACUUM 而不是 purge；事务与预写日志的概念 InnoDB 已讲，简短交代 |
| Firebird | 服务型与嵌入式的衔接，以及不靠预写日志的小心写 |
| SQLite | 只做嵌入：一个文件、表 B+ 树与索引 B 树、两种日志模式 |
| ClickHouse | 列存、不可变的数据片段与稀疏索引 |
| MongoDB | 文档与 WiredTiger |
| Redis、KeyDB 与 Valkey | 内存里的键值与持久化，全系列收束 |

### 共同的六个问题

原先的四个问题（怎么放、怎么找、怎么并发、出错怎么办）按 P57 扩成六个，覆盖增删查改与事务。它们是每集取材的清单：按本集侧重取舍，结尾收束时只收本集讲过的。

| 问题 | 可以从这里取材 |
|---|---|
| 增：怎么放 | 先画整体结构（文件、树或堆或数据片段、它们之间的关系），再看 Alice 插入后落在哪里；需要时打开到字节 |
| 查：怎么找 | 一次查询从入口走到 Alice 的完整路径；有索引与没有索引的对比；实际读了哪些页或块，能跟踪就实测跟踪 |
| 改：怎么改 | Alice 的年龄 42 → 43：原地改、写新版本还是追加；旧值去了哪里 |
| 删：怎么删 | 删掉 Alice：标记、留版本、写墓碑还是立刻删；空出来的空间怎样复用，什么时候才还回去 |
| 事务与并发 | 一次修改怎样做到全成或全不成；两个人同时读写时谁等谁、各自看到什么 |
| 出错怎么办 | 写到一半中断之后靠什么回到一致；用真实进程终止实测一次 |

另外两项由制作方定为每集固定内容：**取舍**（这种设计擅长什么、放弃了什么，只说本集取证支持的）与**衔接**（进出各一句，见下）。

### 人物

旧版 MyISAM 的数据里已经有一组人：alice、bob、carol、dave、erin、frank、grace、heidi，后来插入的 ivan、judy、mallory。各集沿用这组名字，系列自然连续（WaterRun：「不止Alice, 还有Bob等之类的, 系列有连续性」）。谁在哪一集做什么由那一集的故事决定：需要「有人在读」「有人同时写」「有人注销、有人住进空位」时就用他们，不预先分配固定角色，不为出场而出场。

### 共同的示例与实测

- 示例从能一眼看全的小表开始（旧版 MyISAM 的 `users` 8 行、`notes` 3 行），需要规模时再加大（如为 B 树的深度用十万行），由那一集的讲解决定，不强求各集同一张大表。跨集对照时说明各自的数据。
- 讲旧引擎用它所属年代的版本做实验（MyISAM 用 MySQL 5.5）；当前版本的差异另做补充实测，作画面注解。
- 实测标准不变：固定版本与环境；结构由字节或引擎自带的内省工具重建并交叉核对；并发与恢复用控制顺序的真实进程；画面上的数字由脚本从实验产物生成。数字真实，不为叙事改动（需要更好的数字就去实测一个真的）。

#### 6. ClickHouse（约 12 分钟，新做）

| 项 | 内容 |
|---|---|
| 主角 | 按列存放；一次写入生成一个不再改动的数据片段（part），后台再合并；稀疏主键索引，每 8192 行一个标记；颗粒（granule）是最小的读取单位 |
| 整体结构主画面 | 表 → 若干个数据片段目录 → 每一列一个压缩数据文件、一个标记文件，加一份每颗粒一项的主键索引。人物换成大数据量（如一亿个用户，Alice 仍是 2050 号），画面从「一行挨一行」转成「一列挨一列」 |
| 增 | 一次插入：按排序键排好、按列拆开、压缩，写成一个新片段；不往旧片段里塞。后台把小片段合并成大的 |
| 查 | 两种问题对照：「一亿人的平均年龄」只读年龄这一列；「找 Alice」按主键二分稀疏索引，只读一个颗粒，再按标记到各列文件取对应的块；按不在排序键里的姓名找，只能读完整列姓名（先读条件列，再读命中块的其他列）。用 `EXPLAIN indexes = 1` 与查询日志里选中的标记数实测 |
| 改 | Alice 改年龄是一次「变更」：后台重写含她那一行的整个片段，新片段原子地替换旧的；改一行的代价远高于前面几集 |
| 删 | Alice 注销：轻量删除先在隐藏列里标记这一行不存在，查询自动过滤，真正移除等合并；被合并掉的旧片段约 8 分钟后删除 |
| 事务与并发 | 查询开始时拿到当时所有活动片段的快照，片段按引用计数保留；Bob 读的时候 Carol 的插入生成新片段，互不等待，没有行锁；单个插入块是原子的，多语句事务仍是实验功能 |
| 出错 | 新片段先写进临时目录，写完改名才算出现，所以没有半个片段；没有预写日志，缺省也不在每次插入后强制落盘；重启时跳过临时目录，校验和不对的片段移到 detached。实测：插入中途终止服务进程 |
| 进 | SQLite 为改一行、找一行而设计；问题换成「一亿行的平均值」，ClickHouse 把每一列单独存放，宁可改单行变贵，也只读需要的列 |
| 出 | ClickHouse 连 JSON 也拆成一列列子列来存，官方文档承认这样读取整个对象更慢；如果应用每次要的正是一整份记录，就要把它原样存在一起：MongoDB |
| 取证要点 | 官方没有 Windows 原生版，在 WSL2 的 Linux 文件系统里跑服务端（不放在 `/mnt/c`）；版本取当时的 LTS（2026-10-24 为 26.8 LTS）；实测当前片段目录里的真实文件名（标记与主键索引可能是压缩格式）；视觉取官网的黄（`#faff69`）与近黑，标志为单色竖条 |

#### 8. Redis、KeyDB 与 Valkey（约 9 分钟，新做，系列结尾）

| 项 | 内容 |
|---|---|
| 主角 | 数据主要住在内存：一张主哈希表装下所有键，扩容时渐进地搬桶；小对象用紧凑编码；命令在一个线程里逐条执行；持久化是另一回事：快照 RDB 与记命令的 AOF。三个项目同根，分歧画在同一张图上 |
| 整体结构主画面 | 进程内存：数据库 → 主哈希表（扩容时新旧两张表并存）→ 桶 → 对象（键与值放在一起）→ `user:2050` 这个哈希的紧凑编码；下方是磁盘上的 RDB 文件与 AOF 目录。三个项目并排：Redis 的链式桶、Valkey 8.1 起一个缓存行装七项的新哈希表、KeyDB 多个线程共用一张表 |
| 增 | 4096 个用户各是一个哈希 `user:<id>`；Alice 是 `user:2050`，字段 name、age 挨着存在一段紧凑编码里；键数达到桶数时扩容，之后每次读写顺手搬一个桶 |
| 查 | `HGET user:2050 age`：算哈希 → 定位桶 → 比较键 → 在紧凑编码里顺序找字段。没有二级索引：「按姓名找 Alice」要么扫描全部键，要么由应用自己另存一份「姓名 → id」（待取证官方说法） |
| 改 | Alice 改年龄：直接改内存里的这一个哈希 |
| 删 | Alice 注销：键立刻从主表里移除，内存随之释放（大对象可以交给后台线程释放）；另一种删除是过期与内存满时的淘汰（待取证） |
| 事务与并发 | 命令一条一条执行，Bob 的读要么在 Alice 的写之前、要么之后，不会落在中间；`MULTI/EXEC` 打包的命令之间不会插进别人的命令，但不回滚；Carol 用 `WATCH` 做乐观检查。Redis 与 Valkey 加了 I/O 线程，执行仍是单线程；KeyDB 让多个线程跑事件循环，用自旋锁保护主表 |
| 出错 | 内存里的数据进程一停就没了，靠持久化找回：RDB 由子进程借写时复制写快照，可能丢最近几分钟；AOF 记每条写命令，缺省每秒落盘，最多丢约一秒；两者都开时重启用 AOF。实测：两种落盘策略下终止进程，比较剩下什么。RDB 文件开头的魔数也露出分家：Redis 是 `REDIS0015`，Valkey 是 `VALKEY080` |
| 进 | MongoDB 的数据在磁盘上的 B 树里，内存只是缓存；最后一集倒过来：数据整个住在内存，磁盘只负责断电后把它找回来 |
| 出（全系列收束） | 同一群人、同一段经历，八个引擎给出八种答案；答案不同，是因为每个引擎愿意付出的代价不同 |
| 取证要点 | 版本与许可：Redis 8.10.2（2026-09-17；7.4 起 RSALv2/SSPLv1，8.0 起另可选 AGPLv3）、Valkey 9.1.2（2026-08-31，BSD-3-Clause；2024-03 由 Linux 基金会发起，基于 Redis 7.2.4）、KeyDB 6.3.4（2023-10-30，最后一次提交 2024-04-04）。Valkey 由前 Redis 维护者发起，不是 Redis 原作者；原作者 antirez 2024 年底回到 Redis，旁白不得把 Valkey 说成原作者的新项目。三者都没有官方 Windows 版，用 Docker 或 WSL2；KeyDB 有未合入的安全修复，实验只在本机回环地址运行。标志：Redis 红 `#FF4438`（商标规则不许模仿其视觉形象）、Valkey 蓝 `#123678`；KeyDB 未找到官方标志，只用文字 |

### 制作顺序与时长

按集数顺序做（WaterRun 2026-10-24：「顺序改成从重置的MyISAM开始, 引入数据库引擎. InnoDB引入事务性, Pg引入第二种实现(开场白还是占有率), Firebird作为服务型和嵌入式的衔接, 到SQLite」）。每集在系列里引入的东西就是它开场要立住的问题。

| 顺序 | 集 | 预期时长 | 在系列里引入什么 |
|---|---|---|---|
| 1 | MyISAM | 10 分钟 | 数据库引擎：同一条 SQL 交给存储引擎，数据怎样落到文件里、怎样被找到；B 树第一次出场 |
| 2 | InnoDB | 15 分钟 | 事务：全成或全不成、同时读写互不干扰、崩溃后回到一致 |
| 3 | PostgreSQL | 10 分钟 | 第二种实现：开场仍用占有率（开发者调查里 PostgreSQL 与 MySQL 的消长），随后看它与 InnoDB 不同的做法——表是堆、修改写新版本 |
| 4 | Firebird | 8 分钟 | 服务型与嵌入式之间的衔接：同一套引擎两种入口 |
| 5 | SQLite | 10 分钟 | 只做嵌入：一个库、一个文件；已有第 3 稿与十组实测，轮到时按主线对齐与压缩 |
| 6 | ClickHouse | 12 分钟 | 数据量的另一端：按列存放 |
| 7 | MongoDB | 11 分钟 | 不是表：文档 |
| 8 | Redis、KeyDB 与 Valkey | 9 分钟 | 不在磁盘：内存里的键值，全系列收束 |

合计约 85 分钟。旧版四集已在哔哩哔哩标记为归档（P57）；新版各自发布、各自登记 `release`，旧版记录保留。
