# 数据库引擎

逐个讲解数据库引擎的内部实现：数据怎样落到磁盘或内存里，一次读写在引擎内部经过哪些步骤，这种设计换来了什么、放弃了什么。面向写过 SQL、没有读过引擎源码的观众。

## 定位

| | |
|---|---|
| 讲什么 | 逐个数据库引擎的完整底层科普：内部实现、数据怎样落盘、一次读写的全过程、这种设计的取舍 |
| 面向谁 | 写过 SQL、没有读过引擎源码的观众 |
| 怎么讲 | 深入底层、深入浅出；务必严格事实核查，以该引擎真实运行的数据与同一版本的源码为准，注明版本；视觉各取自所讲的引擎（见下） |
| 每集多长 | 按 WaterRun 2026-10-24 给的各集预期（见「系列路线」），作为参照而不是硬上限：本系列不是「XX 秒」系列，宁可稍长、多留白，也不让观众「刷」过去看不懂；留白也不过度（2026-10-19）。早先的 5–10 分钟与 InnoDB、PostgreSQL 的单独参照由此取代 |
| 语言 | 仅中文（片单 `languages`） |

整个系列按同一条文案主线重置：旧版四集已在哔哩哔哩标记为归档（P57），七集按下表顺序逐集重做或新做。每集仍完整走审稿、配音、预览迭代与策划者同意（[制作周期](../../docs/process.md)）；各集当前的阶段看文末「分集」与本集 README，这里不另记进度。

| 顺序 | 集 | 预期时长 | 在系列里引入什么 | 结尾引出 |
|---|---|---|---|---|
| 1 | MyISAM | 10 分钟 | 数据库引擎：同一条 SQL 交给存储引擎，数据怎样落到文件里、怎样被找到；B 树第一次出场 | 有事务的 InnoDB |
| 2 | InnoDB | 15 分钟 | 事务：全成或全不成、同时读写互不干扰、崩溃后回到一致 | 另一种实现 PostgreSQL |

| 5 | ClickHouse | 12 分钟 | 数据量的另一端：OLAP 与按列存放 | 不是表的 MongoDB |
| 6 | MongoDB | 11 分钟 | 不是表：文档模型 | 内存里的 Redis |
| 7 | Redis | 9 分钟 | 不在磁盘：内存里的键值，全系列收束 | — |

### 重做的边界

- **先整体，后局部。** 每张表、每个索引的真实树形用实测数据画出，表与索引按引擎的真实结构区分（如 SQLite 表是 B+ 树、索引是 B 树）；页内布局放在同一操作走到那一页之后再展开（P50、P54）。并发与恢复用控制顺序的真实进程对照。
- **已发布版本不覆盖。** 原发布链接、`project.json` 的 `release`、原成片对应的 Git 历史都保留，重做版另行发布与登记（[发布后冻结](../../docs/guides/release.md#发布后冻结)）；开工时把阶段改回对应值。
- **重做版的署名完整更新，旧版的缺口在新版里补齐。** 按 WaterRun 原话「重置版本包括Credit的更新完整」「注意原有遗漏的Credit, 按新版本, 也要完整修复」：新版 `credits` 列出新版实际参与的全部模型与服务及分工；沿用旧版的任何材料（叙事、实验、核查结论）都署上原作者的准确型号与分工，型号不能确认的旧材料不沿用，改为重新实测。MyISAM、InnoDB 的新版已按此登记；PostgreSQL 旧版的事实测绘记为简称「6.1Sol」，沿用前请 WaterRun 确认准确型号。交付前按[署名](../../docs/roles.md#5-署名)逐项核对片尾。

## 全系列文案主线

这是七集共用的叙事骨架。WaterRun 2026-10-24 看过后调整了制作顺序与各集在系列里引入的东西（见「系列路线」），据此从 MyISAM 开工；每集的文案、事实与设计仍在本集目录里完成并各自交审。下面凡是讲到具体机制的地方，是各集取证的出发点，不是已核事实：每集开工后按本集 `research/FACTS.md` 核对，核不实的改主线。时长按 WaterRun 2026-10-24 给的预期（P57），作为参照。

### 判断标准

**直观、清晰。** 正常速度看一遍就懂，不需要暂停反复看；以旧版 MyISAM 的讲法为基准：观众始终追着同一个对象，一次只推进一件事，先立整体结构再进局部，新信息回答当下的疑问。WaterRun 2026-10-24 的评价（[P59](../../docs/log/feedback.md#2026-10-24旧四集的认知负载)）：旧版 InnoDB、PostgreSQL 的 B+ 树「消失不见，直接到页内」，认知负载偏大；旧版 Firebird「需要暂停反复观看才能看懂」。新版每集交审前按这一条通读全稿，页内细节只在结构立住之后、且确实帮助理解时才讲。

### 一句话

同一个应用、同一群人：Alice 注册、被查到、过生日改年龄、最后注销；Bob 在她改动时读她的资料，Carol 想同时写，Dave 后来注册。七种引擎各演一遍这段经历，看下来是同一件事的七种做法，以及每种做法换来了什么、放弃了什么。

### 系列的弧线

| 段落 | 集 | 这一段推进了什么 |
|---|---|---|
| 服务型关系数据库 | MyISAM → InnoDB → PostgreSQL | 从没有事务到有事务；从表锁到行锁，再到多版本；对照不同的存储与恢复实现 |
| 极小 | SQLite | 没有服务进程，一个库、一个文件 |
| 极大 | ClickHouse | 数据量的另一端：按列存，一次分析成亿行 |
| 不是表 | MongoDB | 记录变成文档 |
| 不在磁盘 | Redis | 数据主要在内存里；系列结尾 |

### 叙事原则

WaterRun 2026-10-24 看过 MyISAM 重写稿后的判断（[P63](../../docs/log/feedback.md#2026-10-24新的不如旧的叙事与讲故事)）：「总体而言, 你新的不如旧的. 思考对叙事, 讲故事的理解」「理解我想要的 ,包括其它集」。旧版 MyISAM 好在哪里，就是各集要做到的：

1. **从一个简单、真实的瞬间开场，提出一个问题。** 「一条查询，一行结果，零点零零七秒；这一瞬间，数据库在磁盘上做了什么」。不用修辞包装，不先摆数字。
2. **从能一眼看全的小例子开始，复杂度跟着问题长。** 旧版先用 8 行的表把数据文件摊开，到 B 树需要深度时才拿出十万行的表。不为全系列统一而一上来用大表。
3. **层层递进：每一章回答上一章留下的问题，自然引出下一章。** 数据文件 → 删了怎么办 → 变长了怎么办 → 找起来太慢 → 索引与 B 树 → 一次查询 → 很多人同时用 → 出了事怎么办。
4. **时代感是故事的一部分。** 引擎属于哪个年代、哪个版本，被谁取代或取代了谁（「在 5.5 版本之前，默认的引擎就是 MyISAM」）。讲旧引擎用它那个时代的版本与文件（MyISAM 讲 `.frm`），新版本的差异作画面注解即可。
5. **讲故事是结构，不是修辞。** 观众被问题牵着走，每一步的结果成为下一步的输入；比喻只在确实帮助理解时用。数字只留观众要记住的那一两个，其余放进画面。
6. **画面不被台本绑死。** 旁白讲故事，画面承载细节：字节、偏移、版本差异、出处可以只在画面上出现，不必每句旁白都点名画面上的东西（F22）。
7. **有好底子的先保留。** 旧版叙事好的（MyISAM），以旧版原文为底只做必要修改；InnoDB、PostgreSQL 先保留旧版叙事的长处，补上缺失的整体结构；不推倒重写。

### 灵活度与各集侧重

WaterRun 2026-10-24（[P61](../../docs/log/feedback.md#2026-10-24各集的灵活度与侧重)）：「流程不要太固定了, MyISAM更多是一个开场的引子, 整体叙事贴近原版即可」「要有灵活度, 每一集」「侧重点也都不同, InnoDB引入事务性当然大头是事务, Pg前面讲过那就不是重点了」。下面的六个问题、人物与示例是全系列的共同底子，不是每集必须照走的流程；侧重表也只是举例（WaterRun：「重点则变成不同引擎的实现, 和InnoDB对比, 这只是一些例子」）：各集按自己的对象与在系列里的位置定侧重，前面几集讲深的内容，后面只用一两句交代到能看懂为止。

| 集 | 侧重 |
|---|---|
| MyISAM | 开场的引子：引入数据库引擎，叙事贴近旧版（定长行、删除与空位、变长行与碎片、B 树与一次查询、表锁与并发插入、没有日志） |
| InnoDB | 事务是大头：全成或全不成、隔离与锁、崩溃恢复；聚簇索引作为它的存放方式讲清楚 |
| PostgreSQL | 重点是另一种引擎实现，处处与 InnoDB 对照：表是堆而不是主键树、旧版本留在表里而不是 undo、回收靠 VACUUM 而不是 purge；事务与预写日志的概念 InnoDB 已讲，简短交代 |
| SQLite | 只做嵌入：一个文件、表 B+ 树与索引 B 树、两种日志模式 |
| ClickHouse | 列存、不可变的数据片段与稀疏索引 |
| MongoDB | 文档与 WiredTiger |
| Redis | 内存里的键值与持久化，全系列收束 |

### 共同的六个问题

原先的四个问题（怎么放、怎么找、怎么并发、出错怎么办）按 P57 扩成六个，覆盖增删查改与事务。它们是每集取材的清单：按本集侧重取舍，结尾收束时只收本集讲过的。

| 问题 | 可以从这里取材 |
|---|---|
| 增：怎么放 | 先画整体结构（文件、树或堆或数据片段、它们之间的关系），再看 Alice 插入后落在哪里；需要时打开到字节 |
| 查：怎么找 | 一次查询从入口走到 Alice 的完整路径；有索引与没有索引的对比；实际读了哪些页或块，能跟踪就实测跟踪 |
| 改：怎么改 | Alice 的年龄 42 → 43：原地改、写新版本还是追加；旧值去了哪里 |
| 删：怎么删 | 删掉 Alice：标记、留版本、写墓碑还是立刻删；空出来的空间怎样复用，什么时候才还回去 |
| 事务与并发 | 一次修改怎样做到全成或全不成；两个人同时读写时谁等谁、各自看到什么 |
| 出错怎么办 | 写到一半中断之后靠什么回到一致；用真实进程终止实测一次 |

另外两项由制作方定为每集固定内容：**取舍**（这种设计擅长什么、放弃了什么，只说本集取证支持的）与**衔接**（进出各一句，见下）。

### 人物

旧版 MyISAM 的数据里已经有一组人：alice、bob、carol、dave、erin、frank、grace、heidi，后来插入的 ivan、judy、mallory。各集沿用这组名字，系列自然连续（WaterRun：「不止Alice, 还有Bob等之类的, 系列有连续性」）。谁在哪一集做什么由那一集的故事决定：需要「有人在读」「有人同时写」「有人注销、有人住进空位」时就用他们，不预先分配固定角色，不为出场而出场。

### 共同的示例与实测

- 示例从能一眼看全的小表开始（旧版 MyISAM 的 `users` 8 行、`notes` 3 行），需要规模时再加大（如为 B 树的深度用十万行），由那一集的讲解决定，不强求各集同一张大表。跨集对照时说明各自的数据。
- 讲旧引擎用它所属年代的版本做实验（MyISAM 用 MySQL 5.5）；当前版本的差异另做补充实测，作画面注解。
- 实测标准不变：固定版本与环境；结构由字节或引擎自带的内省工具重建并交叉核对；并发与恢复用控制顺序的真实进程；画面上的数字由脚本从实验产物生成。数字真实，不为叙事改动（需要更好的数字就去实测一个真的）。

#### 1. MyISAM（约 10 分钟）

| 项 | 内容 |
|---|---|
| 主角 | 数据与索引分成两个文件；定长行的位置靠乘法算出来；B 树第一次出场 |
| 整体结构主画面 | `.MYD` 一排定长行 + `.MYI` 整棵 B 树（叶子里存行的位置），两者并排。旧片在页字节之后才画整树，重做时整树先行 |
| 增 | 行追加到数据文件末尾；有删除留下的空位就先填空位 |
| 查 | 姓名索引 B 树逐层缩小 → 叶子给出行位置 → 乘法算出偏移 → 读数据文件；键缓存 |
| 改 | 定长行原地覆盖；变长行可能拆成碎片 |
| 删 | 行首打删除标记，空位串成链，后来的插入复用；`OPTIMIZE TABLE` 整理碎片 |
| 事务与并发 | 没有事务：一组修改做到一半，前面的已经落盘；整张表一把锁，读写互斥（并发插入是例外） |
| 出错 | 没有日志：表头计数标出未正常关闭，事后检查与修复，修不回的就丢 |
| 进 | 系列的起点，引入数据库引擎：一条查询零点几毫秒就返回，这一瞬间数据库在磁盘上做了什么；回答它的部件叫存储引擎，同一条 SQL 交给不同的引擎会有不同的做法 |
| 出 | MySQL 5.5 起默认引擎换成 InnoDB，它要补上事务与崩溃恢复 |
| 重做要点 | 文案沿用旧版原文（第 2 稿，只把开场耗时换成实测的「零点零零七秒」），事实依据为旧版 MySQL 5.5.62 的实测；重做视觉与声音，取自 MyISAM 与 MySQL 5.x 时代的材料；旧 README 记下的问题（暗色面板、渐变、静止过长、低频过重）都不再出现 |

#### 2. InnoDB（约 15 分钟）

| 项 | 内容 |
|---|---|
| 主角 | 表就是主键 B+ 树（聚簇索引）；二级索引存主键再回表；undo 与快照；redo 与恢复；记录锁与间隙锁 |
| 整体结构主画面 | 一个 `.ibd` 文件里两棵树并排：主键 B+ 树（整行在叶子）与姓名索引树（叶子存姓名 + 主键），按实测画出全部层级。旧片只有一页的真树和示意树，重做必须实测多层整树 |
| 增 | 按主键顺序插进叶页，页满分裂；二级索引同步插入 |
| 查 | 姓名索引 → 主键 2050 → 主键树 → 整行；缓冲池命中与读盘 |
| 改 | 原地改行，旧值写进 undo，行头记下事务号与回滚指针 |
| 删 | 先打删除标记，事务提交后由后台 purge 真正移除，空间留在页内复用 |
| 事务与并发 | 原子性与隔离：快照读看旧版本，写写靠行锁；间隙锁挡住幻影插入；死锁检测 |
| 出错 | 先写 redo；检查点；进程终止后重放 redo、用 undo 回滚未提交的；doublewrite 防半页写 |
| 进 | 引入事务：Alice 改年龄改到一半中断、Bob 在她改动时读、Carol 同时要写——同一个 MySQL 换成 InnoDB，这三件事怎样保证（MyISAM 做不到的部分在本片自足交代，不写「上一期」） |
| 出 | MySQL 之外，另一个开源数据库把旧版本直接留在表里，走了另一条路 |
| 重做要点 | 从取证起，补实测多层聚簇树与二级树；删去旧片对前集的十处回指、文献卡片与无中文释义的英文材料；章节卡留足阅读时间；事务部分仍是全片最长的一段 |

#### 3. PostgreSQL（约 10 分钟）

| 项 | 内容 |
|---|---|
| 主角 | 堆表与独立的 B 树索引；每次修改写一个新元组版本（xmin/xmax）；VACUUM 回收旧版本；WAL |
| 整体结构主画面 | 堆文件（不按主键排序）+ 姓名索引 B 树全貌（实测各层），索引叶子里的元组位置指向堆页。旧片的索引只是一个扁平方框，重做必须画出树 |
| 增 | 新元组放进有空闲空间的堆页，索引插入一项指向它 |
| 查 | 索引扫描与顺序扫描由规划器选；找到元组后还要判断这个版本对当前快照是否可见 |
| 改 | 不覆盖：写新版本、旧版本记下结束事务号；同页且不动索引列时走 HOT，索引不必改 |
| 删 | 只记下删除的事务号，元组还在；VACUUM 等所有快照都不再需要它时才回收空间 |
| 事务与并发 | 每个语句或事务拿快照，按 xmin/xmax 判断可见；读不挡写，写写排队 |
| 出错 | 先写 WAL；检查点；进程终止后从检查点重放 |
| 进 | 开场用占有率：开发者调查里 PostgreSQL 与 MySQL 此消彼长（数字在本片 FACTS 重新取证）；随后引入第二种实现——同样是关系数据库、同样有事务，PostgreSQL 的表不是主键树，而是按到达顺序存放的堆，修改写新版本 |
| 出 | 从独立的数据库服务进程，转向直接嵌进应用、用一个文件保存数据库的 SQLite |
| 重做要点 | 从取证起，补实测索引整树与堆的关系；历史一章压缩，把时间让给删除与 VACUUM |

| 项 | 内容 |
|---|---|
| 主角 | 一个文件；表 B+ 树与索引 B 树之别；回滚日志与 WAL 两种模式及其锁 |
| 整体结构主画面 | 553 页的文件与两棵整树（已实测，第 3 稿已有） |

#### 5. ClickHouse（约 12 分钟）

| 项 | 内容 |
|---|---|
| 主角 | 按列存放；一次写入生成一个不再改动的数据片段（part），后台再合并；稀疏主键索引，每 8192 行一个标记；颗粒（granule）是最小的读取单位 |
| 整体结构主画面 | 表 → 若干个数据片段目录 → 每一列一个压缩数据文件、一个标记文件，加一份每颗粒一项的主键索引。人物换成大数据量（如一亿个用户，Alice 仍是 2050 号），画面从「一行挨一行」转成「一列挨一列」 |
| 增 | 一次插入：按排序键排好、按列拆开、压缩，写成一个新片段；不往旧片段里塞。后台把小片段合并成大的 |
| 查 | 两种问题对照：「一亿人的平均年龄」只读年龄这一列；「找 Alice」按主键二分稀疏索引，只读一个颗粒，再按标记到各列文件取对应的块；按不在排序键里的姓名找，只能读完整列姓名（先读条件列，再读命中块的其他列）。用 `EXPLAIN indexes = 1` 与查询日志里选中的标记数实测 |
| 改 | Alice 改年龄是一次「变更」：后台重写含她那一行的整个片段，新片段原子地替换旧的；改一行的代价远高于前面几集 |
| 删 | Alice 注销：轻量删除先在隐藏列里标记这一行不存在，查询自动过滤，真正移除等合并；被合并掉的旧片段约 8 分钟后删除 |
| 事务与并发 | 查询开始时拿到当时所有活动片段的快照，片段按引用计数保留；Bob 读的时候 Carol 的插入生成新片段，互不等待，没有行锁；单个插入块是原子的，多语句事务仍是实验功能 |
| 出错 | 新片段先写进临时目录，写完改名才算出现，所以没有半个片段；没有预写日志，缺省也不在每次插入后强制落盘；重启时跳过临时目录，校验和不对的片段移到 detached。实测：插入中途终止服务进程 |
| 进 | SQLite 为改一行、找一行而设计；问题换成「一亿行的平均值」，ClickHouse 把每一列单独存放，宁可改单行变贵，也只读需要的列 |
| 出 | ClickHouse 连 JSON 也拆成一列列子列来存，官方文档承认这样读取整个对象更慢；如果应用每次要的正是一整份记录，就要把它原样存在一起：MongoDB |
| 取证要点 | 官方没有 Windows 原生版，在 WSL2 的 Linux 文件系统里跑服务端（不放在 `/mnt/c`）；版本取当时的 LTS（2026-10-24 为 26.8 LTS）；实测当前片段目录里的真实文件名（标记与主键索引可能是压缩格式）；视觉取官网的黄（`#faff69`）与近黑，标志为单色竖条 |
#### 6. MongoDB（约 11 分钟）

| 项 | 内容 |
|---|---|
| 主角 | 记录变成文档（BSON，字段名随每份文档一起存）；存储引擎 WiredTiger：集合与每个索引各是一个文件里的一棵 B 树；内存页与磁盘页是两种格式；乐观并发与写冲突重试 |
| 整体结构主画面 | 数据目录里的几个文件：集合文件（以内部记录号 RecordId 为键、整份 BSON 为值的 B 树）、`_id` 索引与姓名索引各一个文件（键是可直接按字节比较的 KeyString，值或尾部是 RecordId），上方是缓存里的内存页，旁边是日志。按实测画出各树的层级 |
| 增 | Alice 注册：没有 `_id` 时由驱动生成；文档编码成 BSON（她这一份约 39 字节，「name」「age」这两个字段名也在里面）；存储引擎分配下一个 RecordId；新项先进内存页，之后整页「协调」成磁盘格式写成新块 |
| 查 | 按姓名找：没有索引是集合扫描，看完 4096 份文档；有索引是索引扫描 1 项、再按 RecordId 取 1 份文档。用 `explain("executionStats")` 的已检查键数与文档数实测 |
| 改 | Alice 改年龄：内存里在这份文档的更新链头上挂一个新版本，旧版本留给还在读的快照，必要时移到历史存储；写盘时整页生成新块，已写的块不覆盖 |
| 删 | Alice 注销：更新链上挂一个删除标记，协调写盘时这份文档不再写出；文件里空出的块留给之后的写入（Dave 注册），文件不一定变小 |
| 事务与并发 | 文档级并发：Bob 按快照读到旧值；Carol 与 Alice 同时改同一份文档时，后者遇到写冲突，MongoDB 自动重试；集合以上只有意向锁 |
| 出错 | 写操作记入日志（预写），每 100 毫秒或要求 `j: true` 时落盘；每 60 秒一个检查点；进程终止后从最近的检查点起重放日志；未落盘的那一小段可能丢失。实测：强制结束 `mongod` 后重启 |
| 进 | 列存只读需要的几列；MongoDB 走到另一头，连表都不要了，每条记录带着自己的字段名，整份存成一个文档 |
| 出 | MongoDB 的数据住在磁盘上的 B 树里，内存只是缓存；倒过来，数据全住在内存、磁盘只做备份，就是最后一站：Redis |
| 取证要点 | 版本取当时的稳定版（2026-10-24 为 9.0，2026-09-28 发布，许可 SSPL）；Windows 有官方构建；页结构用 WiredTiger 的 `wt verify -d dump_pages` 等，需要自行编译或在 Linux 容器里对停机后的数据目录运行；`$collStats` 的 B 树深度与内部页、叶页数交叉核对。标志的使用规则很严（只准四种配色、不能改动、叶形不得用作插图），画面以官方配色（`#00ED64`、`#00684A`、`#023430`、`#001E2B`）为材料，标志原样使用 |
#### 7. Redis（约 9 分钟，系列结尾）

| 项 | 内容 |
|---|---|
| 主角 | 数据主要住在内存：键空间、哈希表与对象编码；持久化用 RDB 与 AOF。只讲 Redis 的实现 |
| 整体结构主画面 | 进程内存里的键空间、哈希表与对象，和磁盘上的 RDB、AOF 之间的关系；按选定版本实测 |
| 增 / 查 / 改 / 删 | 同一批用户的键值从写入、按键查找、原地修改到删除；哈希表扩容、过期与淘汰按本片需要取证 |
| 事务与并发 | 一条命令怎样执行，MULTI/EXEC 与 WATCH 各自保证什么、有什么边界；按选定版本核对 |
| 出错 | 比较 RDB 与 AOF 的写入、恢复流程及可能丢失的数据；用真实进程终止实验核对 |
| 进 | 从磁盘为主的存储转向以内存为主，解释持久化在这套设计里的位置 |
| 出（全系列收束） | 同一群人、同一段经历，七种引擎给出不同答案，收束各自的取舍 |
| 取证要点 | 按开工时选定的 Redis 版本核对源码、许可、实验与边界。KeyDB、Valkey 的差异转到独立片，不占本集篇幅 |
