# 数据库引擎

逐个讲解数据库引擎的内部实现：数据怎样落到磁盘或内存里，一次读写在引擎内部经过哪些步骤，这种设计换来了什么、放弃了什么。面向写过 SQL、没有读过引擎源码的观众。

## 定位

| | |
|---|---|
| 讲什么 | 逐个数据库引擎的完整底层科普：内部实现、数据怎样落盘、一次读写的全过程、这种设计的取舍 |
| 面向谁 | 写过 SQL、没有读过引擎源码的观众 |
| 怎么讲 | 深入底层、深入浅出；务必严格事实核查，以该引擎真实运行的数据与同一版本的源码为准，注明版本；视觉各取自所讲的引擎（见下） |
| 每集多长 | 5–10 分钟，作为参照而不是硬上限：本系列不是「XX 秒」系列，宁可稍长、多留白，也不让观众「刷」过去看不懂；留白也不过度（WaterRun 2026-10-19）。例外：第二集（InnoDB）按策划 2026-10-09 的要求为 14–16 分钟，其中事务性详解约 4–5 分钟；第三集（PostgreSQL）策划给出 8–12 分钟参照 |
| 语言 | 仅中文（片单 `languages`） |

## 共同约定
各集真正共享的约定记在这里，一项一行。视觉与配乐默认每集取自本集的讲解对象（经验规则 F16、F21），除非下面写明了策划者的决定；某一集的设计决定写在那一集的 README。要改约定先改这里。写法见 [系列](../../docs/guides/series.md)。

| 项 | 约定 |
|---|---|
| 标题 | `一个数据库引擎是如何实现的？——<副题>`，副题点出该引擎的特点 |
| 贯穿的线索 | 每集独立回答四个问题：数据怎么放、怎么找、怎么并发、出错怎么办。先建立整体结构，再沿同一读写操作进入局部；比较只在帮助理解时使用，并在本片补足前提 |
| 结构（建议） | 定位与整体结构 → 同一操作的输入、路径与结果 → 沿路径解释存储、记录、索引、修改与空间复用 → 并发与恢复 → 回答四个问题。章节按本集主线取舍，不为凑齐内部字段拆散过程 |
| 演示与取证 | 各集尽量用同一张示例表与同一批数据（首集是 `users(id, name, age)` 与 `notes(id, body)`），便于跨引擎对照；事实由「真实版本上的实验」与「源码」两路核对，画面上的字节与数字由脚本从实验产物生成 |
| 视觉与声音 | 视觉取自本集讲解对象的官方材料，配乐为本集设计；风格、动作和声音服务于解释，不共用旧片的方案。具体配色、部件、曲目与试验只记在各片 README；通用方法提炼到 `kit/` 与 `docs/` 后再使用（F16、F20、F21）。 |
| 承接上一集 | 2026-10-18 按 P16 修订：每集独立可懂，直接建立本片问题；章节直接讲“数据怎么放”“怎么找”等，不再用“上一期的第几个问题”串场。必要比较才引用前集，版本与前提在本片补齐；对照依据留在研究和制作说明中。规则见 [docs/guides/series.md](../../docs/guides/series.md) 第 6 节 |
| 概念的引出 | 前集已讲过的概念仍在本集第一次使用时提供足够的简短解释；不能假定观众记得事务、ACID、MVCC 等名词。解释深度围绕本集问题决定，论文、历史和参数不挤掉具体机制 |

## 系列路线

WaterRun 2026-10-19 定下后续各集的顺序与各自承担的角色。分集表里的标题与目录以片单为准；这里记录为什么是这个顺序，供各集开头与结尾衔接。

| 段落 | 集 | 角色与衔接 |
|---|---|---|
| 服务型开源关系数据库 | MyISAM、InnoDB（MySQL）→ PostgreSQL → Firebird | 三套服务型开源实现。PostgreSQL 一集结尾引出 Firebird：「两个开源巨头之外，一个更小众的选择」。Firebird 讲完，这一段收束 |
| 「极小」 | SQLite | 不再是服务进程，简练到嵌进程序里的数据库 |
| 「极大」 | ClickHouse | 由数据量的另一端引出 OLAP 与列式存储 |
| 不是 SQL | MongoDB | NoSQL 的文档模型 |
| 缓存，系列结尾 | Redis、KeyDB 与 Valkey | 一期讲完，作为整个系列的结尾。第三个实现由 WaterRun 2026-10-24 确认为 Valkey，片单标题与目录随之改为「缓存：Redis、KeyDB 与 Valkey」（`redis-keydb-valkey`） |

## 全系列计划（2026-10-24）

WaterRun 在 SQLite 一集的会话中要求把后续工作落盘（原话见 [P54](../../docs/log/feedback.md#2026-10-24数据库引擎系列的重做与全系列计划)）：前四集要重做，余下三集未做，并提出先写整体文案主线、再逐集实现。本节是执行计划；各集的设计决定仍写在各集 README。

### 做法

1. **先写全系列文案主线。** 在动手做任何一集之前，用一份主线把八集串起来：每集的核心问题、贯穿的同一示例（`users` 表与 Alice）、本集在「从服务型到嵌入，再到极大、非关系与缓存」这条路上的位置，以及进出两头各一句的衔接。衔接句写成本集自足的话，不用「上一期」「下一期」导航（F10）；系列路线的顺序与角色以上表为准。主线写在本页，经 WaterRun 确认后再逐集开工。
2. **再逐集制作。** 按集数顺序做；每集仍完整走审稿、配音、设计、验收与策划者同意三道闸门。主线确认后，审稿中的 SQLite 只按主线调整首尾衔接，重新交审。
3. **共同的内容要求。** 先建立整体结构，再定位到页内（P50、P54）：每张表、每个索引的真实树形用实测数据画出，表与索引的树按引擎的真实结构区分（如 SQLite 表是 B+ 树、索引是 B 树），页内布局放在同一操作走到那一页之后展开。并发与恢复用控制顺序的真实进程对照。

### 重做的边界

- 已发布版本不覆盖：原发布链接、`project.json` 的 `release`、原成片对应的 Git 历史都保留，重做版另行发布与登记（[发布后冻结](../../docs/guides/release.md#发布后冻结)）。四集各自的 README 已记下重做要求、范围与原链接；开工时把阶段改回对应值。
- **重做版的署名完整更新。** 按 WaterRun 原话「重置版本包括Credit的更新完整」：重做版 `credits` 列出新版实际参与的全部模型与服务及分工；沿用原版的部分（如 MyISAM 的文案）照实写明沿用及原作者型号；交付前按 [角色与权限](../../docs/roles.md#5-署名) 逐项核对片尾。原发布版的署名记录不改。
- 时长：本系列不是定长片；内容讲清优先，参照上文「每集多长」。
