### history · 01 学院出身

1986 年，伯克利开始实现一个研究系统 领头的是斯通布雷克教授，他之前做过关系数据库 *Ingres* 新系统取名 POSTGRES，意思是 Ingres 之后 1994 年，Andrew Yu 和 Jolly Chen 给它加上了 SQL 改名 Postgres95，作为开源软件发布 1996 年，定名 PostgreSQL 就是 POSTGRES 加上 SQL 今天，它的大版本是 18 2014 年度的图灵奖，授给了斯通布雷克 SQL:2023 的核心有 177 项必选特性 PostgreSQL 18 至少符合 170 项 还没有哪个数据库，声称 177 项全部符合 建表、加列这样的改动，也能放进事务 一回滚，表和列都像没建过一样 约束也由数据库自己把关 超出范围的年龄、不存在的用户，都写不进去

### layout · 02 一张表放在哪

先看这张表在磁盘上的样子 在 PostgreSQL 里，一张表就是一个文件 文件分成一页一页，每页 8 KB 行一行接一行地往页里放 一页放满 88 行，换下一页，一共 47 页 4096 个用户，都在这 47 页里 这样的文件，叫作*堆* 堆不按编号排序，谁先来，谁在前 Alice 是第 2050 个注册的 她落在第 23 页 是这一页里的第 26 项 「第几页、第几项」，就是一行的地址 它叫 *ctid* 这张表有三个索引：主键、姓名、年龄 每个索引是另外一个文件 都是一棵 B 树 主键树：一个根，下面 12 页叶子 姓名树：一个根，39 页叶子 一项姓名 64 字节，叶子就多 年龄树：一个根，5 页叶子 同一个年龄的地址，合成一项存放 叶子里存的，是键和行的地址 主键树里，2050 旁边记着第 23 页第 26 项 姓名树里，Alice 旁边也是这个地址 索引给出地址，再按地址去堆里取行 InnoDB 不一样 在 InnoDB 里，表本身就是那棵主键树 整行数据，就存在主键树的叶子里 姓名索引里存的是主键 按名字找，先拿到主键，再查主键树 PostgreSQL 里，没有哪棵树装着整行 每个索引都直接指向堆里的地址，主键索引也一样

### page · 03 一页之内

打开第 23 页 开头 24 字节是页头 记着空闲区从哪到哪 接着是 88 个*项目指针* 每个 4 字节，指向页里的一行 指针从前往后排 行从页尾往前放 两头之间的空隙，只剩 72 字节 已经放不下下一行了 第 26 个指针说：Alice 从第 5904 字节开始 占 82 字节 地址记的是第几个指针，不是字节位置 行在页里可能被挪动，指针不会 记住第几个，行挪到哪都找得到 这 82 字节里，前 24 字节是*行头* 后面 58 字节才是数据 编号 2050，名字 Alice，年龄 42 名字不满 50 个字符，用空格补齐 行头里的三样东西，后面每章都要用到 *xmin*：写入这一行的事务号 Alice 注册时，是 2809 号事务 *xmax*：作废这一行的事务号 现在是 0，还没有谁作废它 从 xmin 到 xmax，就是这一版能被看见的范围 *t_ctid*：这一行最新版本的地址 现在，它指着自己 InnoDB 的行头里，记的是事务号和回滚指针

### insert · 04 增

这些页，是怎样一行行填满的？ 用户一个个注册，新行放进最后一页 最后一页满了，就在文件末尾再接一页 Alice 注册时，表里有 24 页 她落在最后一页，第 23 页 同时，三个索引各插一项 2050 比已有的编号都大 插在主键树最右边的叶子 Alice 按字母排在所有 User 前面 插在姓名树最左边的叶子 叶子放满，就一分为二 有了第二页叶子，上面就长出一个根 编号一路递增，主键树总在最右边分裂 这时左边那页只装到九成 后来的编号都更大，不会再挤回左边 也不装满：装满的页，之后改几行就又要分裂

### query · 05 查

现在，按名字找 Alice SQL 先交给*规划器* 由它决定怎么找 要找的只有一行，它选姓名索引 从姓名树的根出发 走到最左边的叶子 叶子给出地址：第 23 页，第 26 项 取出堆的第 23 页 顺着第 26 个指针，找到这一行 还没完：先看行头，这个版本能不能看见 xmin 已经提交，xmax 是 0 看得见：Alice，42 岁 一共读了三页：树根、叶子、堆页 换个问题：一共有多少人？ 要统计每一行，它干脆不走索引 把 47 页从头读到尾 不同查询的性质，决定了它要走哪条路 InnoDB 按主键找，叶子里就是整行 PostgreSQL 的叶子里只有地址，还得再去一趟堆 只要名字的时候，可以不去堆 可还要确认这一行看得见，行头在堆里 堆旁边有个小文件，叫*可见性图* 一页的行对所有事务都可见，就记一笔 记过的页，就不必回堆 这一笔由 VACUUM 来记

### update · 06 改

Alice 过生日，42 岁改成 43 PostgreSQL 不覆盖原来那一行 它要另写一个新版本，年龄是 43 新版本先看原来那一页放不放得下 第 23 页只剩 72 字节 新版本连同指针要 92 字节 放不下，只好写到别的页 第 46 页，第 49 项 旧版本的数据不动 只在行头里改两处 xmax 记上这次修改的事务号 t_ctid 指向新版本 新版本的 xmin，也是这个事务号 同一个 Alice，现在有两个版本 三个索引里的项，指着的都是旧地址 每个索引都要再插一项，指向新地址 名字、编号都没变，也一样要插 InnoDB 是原位改，旧值进 undo 它的姓名索引里存的是主键 主键没变，姓名索引就不用动 PostgreSQL 也有少动索引的办法：*HOT* 条件有两个：一是改的列上没有索引 二是新版本还能放进原来那一页 这时新版本留在本页，旧版本指向它 索引一项都不加 查询先到原来的位置，再在页内跳过去 Alice 这次两个条件都不满足 年龄有索引，第 23 页也满了 主键树的叶子还留一成，表默认却把每一页装满 要给更新留位置，可以把填充比例改小 换一张每页留一成空位、年龄不建索引的表 同样改年龄，日志里只有一条 HOT 更新，没有索引插入

### mvcc · 07 事务与并发

两个版本都在表里 别人来读，该给哪一个？ 回到 Alice 改年龄、还没提交的时候 她的事务号是 4856 每个事务提交了没有，另有一处记着 这时是「进行中」 Bob 来读 他的查询带着一张*快照* 快照写着：4856 起的事务，都还看不见 新版本的 xmin 是 4856，看不见 旧版本的 xmax 是 4856，作废还不算数 所以 Bob 读到旧版本：42 Bob 不用等 Alice，Alice 也不用等他 Carol 也要改 Alice 这一行 她只能等 她等的，是 Alice 的事务结束 Alice 对这一行的锁，就记在行头的 xmax 里 不占内存，锁多少行都行 Alice 提交了 状态从「进行中」，变成「已提交」 Carol 接着改，改的是 43 这一版 后来她放弃了这次修改 Bob 再查一次，读到 43 默认的隔离级别是*读已提交* 每条语句开始时，都拿一张新快照 如果 Bob 用的是*可重复读* 整个事务都用开头那一张快照 他会一直读到 42 这时他再去改 Alice，就会报错 并发修改，无法串行化 InnoDB 默认的，是可重复读

### delete · 08 删与回收

后来，Alice 注销了账号 DELETE 也不擦掉这一行 只在 xmax 记上删除它的事务 别人查不到她了，可行还在页里 Bob 的可重复读事务还开着 他仍然读到 Alice 旧版本和删掉的行，靠 *VACUUM* 来收 只要还有快照可能用到，就不能收 趁 Bob 的事务开着做一次 结果是：这一行已死，但还不能回收 Bob 结束后再做一次 这一行才被收走 三个索引里指向它的项，一起删掉 第 26 个指针空了出来 第 23 页的空隙，从 72 字节变成 160 哪页空出多少，记进另一个小文件 *空闲空间图* Dave 来注册 插入前先问空闲空间图，哪页放得下 他落在第 23 页、第 26 个指针 正是 Alice 原来的位置 InnoDB 要等 purge 做完，Dave 才用上这块空间 其实不是每次都要等 VACUUM 页快满时，读到它的查询会顺手清理 Alice 改完年龄，下次查询一读到第 23 页 旧版本就清掉了，空隙也从 72 变成 160 自动清理默认开着，死行多了就清 可开得很久的事务会挡住清理 死行越积越多 还有一件事只能靠 VACUUM 事务号只有 32 位，用过四十多亿个就绕回开头 过去的事务，看起来就像在未来 所以每张表至少每 20 亿个事务要 VACUUM 一遍 它把足够老的行标成*冻结* 冻结的行对谁都算过去，不再比较事务号

### crash · 09 出错怎么办

最后：提交过的修改，断电以后还在吗？ 规矩是先写日志，叫 *WAL* 数据页写盘之前，日志必须先落盘 Alice 改成 43，提交之前，日志还在内存里 提交的那一刻，日志写进磁盘 数据文件里的第 23 页，这时还是旧的 数据页可以晚些再写，提交不必等它 每隔一段时间，做一次*检查点* 检查点之前的修改，都已写进数据文件 检查点后第一次改某页，整页写进日志 万一写数据页时断电，页只写了一半 还能拿日志里的整页来恢复 InnoDB 防同一件事，靠的是双写缓冲区 试一次：Carol 把 Bob 的年龄改成 99，不提交 Alice 改成 43，提交 然后强行停掉数据库 重新启动，它发现上次没有正常关闭 从最近的检查点起，把日志重放一遍 Alice 是 43，提交过的都在 Bob 还是 51，Carol 没提交的 99 不见了 其实 99 那个版本就在页里 它的事务没有提交，状态是「已中止」 谁都看不见 InnoDB 重启后，要用 undo 撤回没提交的修改 PostgreSQL 不用撤 没提交的版本，本来就看不见

### five · 10 五个问题

回头看，PostgreSQL 这样回答五个问题 怎么放：行按到达顺序放进堆 每个索引一棵 B 树，指向行的地址 怎么找：规划器选路 从索引到堆，再看这个版本能不能看见 改和删：不覆盖，写新版本、记下 xmax 旧版本留到没人需要时，再清理回收 怎么并发：快照决定读哪个版本 读写互不挡路，写和写排队 出错怎么办：先写 WAL，崩溃后重放 没提交的，本来就看不见 五个答案，都落在同一个做法上 改一行，就写一个新版本

### tradeoff · 11 取舍

同一张表、同样五个问题，两套答案 InnoDB 按主键找，一棵树走到底 PostgreSQL 要从索引再到堆 可它按名字找，不必再绕主键 改一行，InnoDB 原位改，旧值进 undo PostgreSQL 写新版本，用不上 HOT 就要动每个索引 旧版本留在表里，要靠清理来收 清理跟不上，死行就越积越多 换来的是：读写互不挡路 回滚和崩溃以后，都不用撤销 一个 1986 年在伯克利开始的研究系统 到 2026 年，成了开发者勾选最多的数据库 同一份调查里，第二名是 SQLite 它没有独立的服务进程，直接嵌进程序里 这样小巧的引擎，怎样做成生产级的关系数据库？
