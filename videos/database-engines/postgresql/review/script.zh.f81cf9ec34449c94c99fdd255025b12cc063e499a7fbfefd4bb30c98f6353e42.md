### history · 01 学院出身

1986 年，伯克利开始实现一个研究系统 领头的，是做过关系数据库 Ingres 的斯通布雷克教授 新系统取名 POSTGRES，意思是 Ingres 之后 1994 年，Andrew Yu 和 Jolly Chen 给它加上 SQL 改名 Postgres95，作为开源软件发布 1996 年定名 PostgreSQL，今天的大版本是 18 2014 年度的图灵奖，授给了斯通布雷克 SQL:2023 的核心有 177 项必选特性，它至少符合 170 项 还没有哪个数据库，声称全部符合 建表、加列也能放进事务，回滚就全部撤销 约束由数据库自己把关，不合规矩的数据进不来

### layout · 02 一张表放在哪

在 PostgreSQL 里，这张表是磁盘上的一个文件 文件分成一页一页，每页 8 KB 行按到达的顺序往里放，一页 88 行，一共 47 页 这样的文件，叫作*堆*：不排序，谁先来谁在前 Alice 是第 2050 个注册的，落在第 23 页第 26 项 「第几页、第几项」就是一行的地址，叫 *ctid* 这张表有三个索引：主键、姓名、年龄 每个索引是另外一个文件，各是一棵 B 树 三棵树都是两层：一个根，下面 12、39、5 页叶子 叶子里存的，是键和行的地址 主键 2050 和姓名 Alice 旁边，记着同一个地址 InnoDB 不一样：表本身就是按主键排的那棵树 姓名索引里存的是主键 PostgreSQL 里，没有哪棵树装着整行 每个索引都直接指向堆里的地址

### page · 03 一页之内

打开第 23 页：开头 24 字节是页头 接着是 88 个*项目指针*，每个 4 字节，指向一行 指针从前往后排，行从页尾往前放 两头之间的空隙，只剩 72 字节 第 26 个指针说：Alice 从第 5904 字节开始，占 82 字节 地址记的是第几个指针，不是字节位置 行在页里可能被挪动，指针不会 这 82 字节里，前 24 字节是*行头*，后面才是数据 行头里有三样东西，后面每一章都要用到 *xmin*：写入这一行的事务号，2809 *xmax*：作废这一行的事务号，现在是 0 *t_ctid*：这一行最新版本的地址，现在指着自己 InnoDB 的行头里，记的是事务号和回滚指针

### insert · 04 增

用户一个个注册，新行放进最后一页，放满了再接一页 Alice 注册时，落在当时的最后一页：第 23 页 三个索引各插一项 2050 比已有编号都大，插在主键树最右边的叶子 Alice 排在所有 User 前面，插在姓名树最左边的叶子 叶子放满，就一分为二，上面长出一个根 编号递增，主键树总在最右边分裂，左页只装九成

### query · 05 查

按名字找 Alice：SQL 先交给*规划器* 要找的只有一行，它选姓名索引 从根走到最左边的叶子，拿到地址：第 23 页第 26 项 取出这一页，顺着第 26 个指针找到这一行 再看行头：xmin 已提交，xmax 是 0，看得见 Alice，42 岁；一共只读了根、叶子、堆页三页 统计一共多少人，它不走索引，把 47 页从头读到尾 要找多少行，决定了它走哪条路 InnoDB 按主键找，走到叶子就拿到整行 PostgreSQL 的叶子里只有地址，还得再去一趟堆

### update · 06 改

Alice 过生日，42 岁改成 43 PostgreSQL 不覆盖，另写一个新版本 新版本先看原来那一页放不放得下 第 23 页只剩 72 字节，新版本连同指针要 92 只好写到别的页：第 46 页第 49 项 旧版本的数据不动，行头里改两处 xmax 记上这次修改的事务号，t_ctid 指向新版本 新版本的 xmin，也是这个事务号 同一个 Alice，现在有两个版本 三个索引里的项都指着旧地址，每个都要再插一项 名字和编号没变，也一样要插 InnoDB 原位改，旧值进 undo 它的姓名索引存的是主键，主键没变就不用动 PostgreSQL 也有少动索引的办法，叫 *HOT* 条件有两个：改的列上没有索引，新版本放得进原来那一页 这时新版本留在本页，旧版本指向它，索引一项都不加 换一张每页留一成空位、年龄不建索引的表 同样改年龄，日志里只有一条 HOT 更新 Alice 这次两个条件都不满足 年龄有索引，第 23 页也满了 表默认把页装满；要给更新留位置，可以把填充比例改小

### mvcc · 07 事务与并发

两个版本都在表里，别人来读，该给哪一个？ Alice 改了还没提交，她的事务号是 4856 提交状态另有一处记着，这时是「进行中」 Bob 来读，查询带着一张*快照* 快照写着：4856 和它以后的事务，都还看不见 新版本的 xmin 是 4856，看不见；旧版本的作废也不算数 Bob 读到旧版本 42，不用等 Alice Carol 也要改这一行，她只能等 Alice 的事务结束 Alice 对这一行的锁，就记在行头的 xmax 里，不占内存 Alice 提交，状态变成「已提交」 Carol 接着改的，是 43 这一版；后来她放弃了修改 Bob 再查一次，读到 43 默认的*读已提交*，每条语句都拿一张新快照 换成*可重复读*，整个事务只用开头那张快照 Bob 会一直读到 42；再去改 Alice，就报错 InnoDB 默认的，是可重复读

### delete · 08 删与回收

后来，Alice 注销了账号 DELETE 也不擦掉这一行 只在 xmax 记上删除它的事务 Bob 的可重复读事务还开着，他仍然读到 Alice 收走旧版本和删掉的行，靠 *VACUUM* 趁 Bob 的事务开着做一次：这一行已死，还不能回收 Bob 结束后再做一次，这一行才被收走 三个索引里指向它的项，一起删掉 第 26 个指针空出来，空隙从 72 字节变成 160 哪页空出多少，记进堆旁的另一个小文件：*空闲空间图* Dave 来注册，先问空闲空间图哪页放得下 他落在第 23 页、第 26 个指针，正是 Alice 原来的位置 InnoDB 里，也要等 purge 做完，Dave 才用上这块空间 不是每次都要等 VACUUM 页快满时，读到这一页的查询会顺手清理 Alice 改完年龄后，第 23 页的旧版本就是这样被清掉的 开得很久的事务会挡住清理，死行越积越多 事务号只有 32 位，用过四十多亿个就绕回开头 过去的事务会看起来像在未来 所以每张表至少每 20 亿个事务要 VACUUM 一遍 VACUUM 把足够老的行标成*冻结*，对谁都算过去

### crash · 09 出错怎么办

最后：提交过的修改，断电以后还在吗？ 规矩是先写日志，叫 *WAL*：数据页写盘之前，日志先落盘 Alice 提交的那一刻，日志写进磁盘 数据文件里的第 23 页还是旧的，提交不必等它 *检查点*之前的修改，保证都已写进数据文件 检查点后第一次改某页，整页写进日志，防止页只写了一半 试一次：Carol 把 Bob 的年龄改成 99，不提交 Alice 改成 43，提交；然后强行停掉数据库 重启时，它从最近的检查点起把日志重放一遍 Alice 是 43；Bob 还是 51，99 不见了 99 那个版本还在页里，但它的事务已中止 InnoDB 要用 undo 把没提交的修改撤回去 PostgreSQL 不用撤：没提交的版本，本来就看不见

### five · 10 五个问题

回头看，PostgreSQL 这样回答五个问题 怎么放：行按到达顺序放进堆，索引各是一棵 B 树 怎么找：规划器选路，从索引到堆，再看版本能不能看见 改和删：写新版本、记 xmax，旧版本留到没人需要再回收 怎么并发：快照决定读哪个版本，写和写排队 出错怎么办：先写 WAL，崩溃后重放，没提交的看不见

### tradeoff · 11 取舍

同一张表、同样五个问题，两个引擎给了两套答案 InnoDB 按主键找，一棵树走到底 PostgreSQL 要从索引再到堆，但按名字找不必绕主键 改一行，它要写新版本，用不上 HOT 就要动每个索引 旧版本留在表里，清理跟不上，死行就越积越多 换来的是读写互不挡路，回滚和崩溃以后都不用撤销 一个 1986 年在伯克利开始的研究系统 到 2026 年，成了开发者勾选最多的数据库 同一份调查里，排在它后面的第二名，是 SQLite 它没有独立的服务进程，直接嵌进程序里 这样一个小巧的引擎，怎样做成生产级的关系数据库？
