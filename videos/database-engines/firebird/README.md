本轮取舍：

- 保留八十年代 InterBase → 2000 年开源分支 → 2002 年 Firebird 1.0 的历史线，固定研究对象为 5.0.4，不把实验版本称作“今天最新版”。
- 引子从前三期 MyISAM、InnoDB、PostgreSQL 的不同实现与共同服务形态接起，承接上一期结尾的 Firebird 预告；一句定义 Firebird，再把两种用法与已熟悉的服务、下一期的 SQLite 对照。第 02 章解释可加载的引擎代码如何支持它们，不在开头复讲数据库基础。
- 主体使用同一张 users 表和同一个 Alice；先说明一行怎样住进数据页，再让姓名索引提供找行线索，最后讲修改与落盘。正文不再报“指针页、槽、位图、回溯指针”等内部名词，用页内目录、记录号和历史版本解释实际作用。
- 不复讲 ACID、隔离级别表、读已提交的缺省设置，不另开事务性或并发教程。行版本只解释本次修改为什么保留历史。
- 三处简短对比：InnoDB 主键索引装整行，Firebird 与 PostgreSQL 的行和索引分开；InnoDB 用 undo 信息重建旧值，Pg 保留行版本，Firebird 从当前记录回找历史；InnoDB/Pg 的日志重做与 Firebird 按页面依赖写入。各处只比较当前任务中的职责，不列功能排名。
- 不报二进制体积、不列全部页类型、页数分布、字节偏移与版本清单，不做性能或选型排名。
- 衔接是系列的讲述顺序，不是引擎的高低等级，也不暗示 Firebird 或 SQLite 由 PostgreSQL 演化而来。

## 取证与纠错

沿用本片已有实验，不重新安装 Firebird、不覆盖原回显。新增 [13_query_path.py](research/lab/13_query_path.py) 在独立嵌入式库上复用原示例数据，确认没有计划提示时，按姓名查年龄的执行路径包含姓名索引、位图与按记录号取行；返回 30。二进制与临时 SQL 留在被忽略的 out/lab/，可入库回显不含运行路径或口令。

对 Firebird 5.0.4 同版本源码补查了 BitmapTableScan、DPM_get、prepare_update、TRA_commit、TRA_cleanup 与页面依赖管理。源码与文档的直达地址、函数和范围均记在 FACTS 与 sources.json。旧稿错误的处理：

1. “先写日志，再落数据页”撤回；改为行版本、事务状态与页面依赖写入。未做崩溃实验，不冒称实测恢复成功。
2. “不就地改、旧版留原地”撤回；字节匹配不能判断新旧版本的物理归属。
3. “每两万次事务才回收一次”撤回；回收与 sweep 阈值不能混为一谈。
4. ReadConsistency 参数不等于客户端缺省隔离级别；监控表的活跃状态也不等于 TIP 的提交状态。
5. 服务端体积小不证明它“只负责转发”；双重部署形态也不决定行版本或页结构的算法。
