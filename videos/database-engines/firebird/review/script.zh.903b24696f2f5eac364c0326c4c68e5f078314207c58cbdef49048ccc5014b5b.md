## durable · 06 写到一半，崩了怎么办

预估 73.8 秒。

| 句号 | 字幕 / 旁白原文 |
|---|---|
| w1 | 还有最后一关：修改得真正存下来 |
| w2 | 前面的 InnoDB 和 PostgreSQL，都要记恢复日志 |
| w3 | 数据页没来得及写完，重启后还能按日志补上 |
| w4 | Firebird 的常规恢复，不靠这样一份重做日志 |
| w5 | 它必须管好数据库文件里，各页写入的先后 |
| w6 | 比如，给表新增一个数据页 |
| w7 | 目录也得记住，新的数据页在什么地方 |
| w8 | 如果目录写好了，数据页却还没写好 |
| w9 | 这时一崩溃，目录就可能指向不存在的内容 |
| w10 | 所以，要先写数据页，再写指向它的目录 |
| w11 | 这类先后关系，由引擎来管理 |
| w12 | 回到 Alice 的修改，提交时也是有顺序的 |
| w13 | 先把这次修改需要的页写出去 |
| w14 | 再把事务状态，记成已经提交 |
| w15 | 这里开着强制写，要求这些写入真正落盘 |
| w16 | 如果崩溃后重开库，普通事务还没完成提交 |
| w17 | 就按失败处理，留下的修改不能算已提交 |
