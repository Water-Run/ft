## 简报

- **目标观众已有的知识**：写过 SQL，知道表、行、索引；不一定看过本系列前几集（单集独立可懂，F10），但事务、B 树、日志、快照这些前几集讲过的概念直接用，不再重新下定义（F33）。
- **看完能回答的一个核心问题**：数据住在内存里的 Redis，怎样放、怎样找、怎样改和删、怎样让很多人同时用，进程没了之后又靠什么找回来？最后一章回答整个系列的问题：一个数据库引擎是如何实现的。
- **用哪个具体例子走完解释**：本系列同一批 4096 个用户，Alice 是 `user:2050`、42 岁（FACTS「环境与版本」）。她注册（一个 16 字节对象头的对象 + 27 字节的 listpack；8192 个桶的哈希表）→ 被 Bob 按键找到（服务端 3–5 微秒）；按名字找只能扫 4096 个键（4–5 毫秒）→ 过生日改成 43（同一地址上 `2a` → `2b`）→ Bob、Carol 同时读写（单线程一条条执行；先读后写丢一次加一；MULTI/EXEC、WATCH；没有回滚）→ 进程被 `kill -9`（只有快照：写完立刻杀，0 个键；AOF：交给内核的都在）→ 注销（DEL、过期、内存满）。关键因果：数据在内存里，所以要靠哈希表直达、靠单线程免锁、靠快照和命令日志回来。边界：只测了进程被杀，断电只引文档；只用核心服务端，不讲集群、复制和附带的模块。
- **逐章怎样推进**（第 1 稿，章名即章节卡的问题）：
  - 开场：一条命令一个结果，四微秒 → 数据在内存里 → 前六集数据都在磁盘、内存只是缓存，Redis 倒过来 → 名字、键值数据库、2009 年的来历 → 进程一停、机器一断电，数据还在吗？还是那几个问题。（接住 MongoDB 一集结尾 j11、j12 的两问，FACTS S02）
  - 01 一本字典（没有表，数据放在哪里？）：每人一个键；一张哈希表、桶、哈希值、链；8192 个桶的实测分布。
  - 02 增（Alice 注册时，写下了什么？）：对象头与内嵌键名；27 字节的 listpack 逐段；字段名每人存一遍；55 字节、不到 600 KB；桶翻倍与渐进式 rehash。
  - 03 查（找到 Alice，走了哪条路？）：按键直达，3–5 微秒；压测每秒 13 万次；按名字只能扫全部键，慢上千倍；自己存一个名字到编号的键。
  - 04 改（改一个数字，内存里改了什么？）：同一地址上一个字节；不留旧版本 → Bob 怎么办，留到下一章。
  - 05 事务与并发（有人在读，有人在写，谁等谁？）：一个线程一条条来；不用锁和旧版本；慢命令的代价；两条命令之间被插队；MULTI/EXEC、WATCH；没有回滚及官方理由。
  - 06 出错怎么办（进程没了，数据还在吗？）：RDB 快照与子进程；缺省保存点与两次 kill -9；AOF 记命令、重放；回复前已交给内核，kill -9 不丢；断电约一秒；always；重写；两种同时开。
  - 07 删（删掉的键去了哪里？）：DEL；Dave 的键名；过期的两条路（关掉抽查的实验）；内存满了拒绝写入或淘汰。
  - 08 五个问题：系列约定的五问。
  - 09 同一段经历（七个引擎，七种答案）：七个引擎各一句 → 没有最好的，只有愿意付出什么 → 磁盘与内存、锁与版本与单线程、记一笔再恢复 → 回到第一集开场的那一瞬间 → 系列的问题就是五个问题的答案。
- **决定不讲的材料与理由**：主从复制、哨兵、集群与槽位（不是单机引擎的问题）；附带的查询引擎、JSON 等模块（本片只编译核心服务端，N04）；字符串的三种编码、hash 模板（只作注解，L02、N03）；I/O 线程（缺省关闭）；AOF 截断后的恢复（X08，第 1 稿为控制时长删去，注解可用）；主动过期的比例（文档与源码口径不一，N05）；许可的变迁（H13，可作画面注解）；antirez 离开与回归（H14）。

**已选定（2026-11-25）：视觉 A 桶阵，配乐 C「终章」，配音 `Chinese (Mandarin)_Sincere_Adult`。** 下面是审片时的三个视觉方向，留作记录；原先倾向的「05、06 章借 B 的时间线，02、06 章用 C 的终端特写」不再沿用，各章都在桶阵这一套视觉里解决，需要时间线或字节特写时按 A 的颜色与部件画。

审片时的三个视觉方向（关键帧 `src/design/keyframes.html?d=A|B|C&f=1…4`，截图在审片页）比较的是解释方法：

| 方向 | 解释方法 | 颜色 | 长处 | 风险 |
|---|---|---|---|---|
| A 桶阵 | 8192 个桶按真实桶号排成 128 × 64 的格阵，作全片常驻的主画面；Alice 在第 3271 号桶（FACTS K07：桶位由进程的哈希种子按 SipHash-1-2 算出，链长分布与 `DEBUG HTSTATS` 逐项相同）；增查改删从这一格拉出对象与字节，出错一章上面内存、下面磁盘 | 午夜蓝 `#091a23`、暮蓝 `#163341`，品牌红 `#ff4438` 只给正在讲的那一样 | 结构一直在画面里（F02、F29） | 格阵密，近看靠放大；并发要另画时间线 |
| B 一条线程 | 时间为主轴：所有客户端的命令汇进一条主线程；并发一章三条泳道汇成一队；出错一章主线程下面是子进程与 AOF | 白底墨字，红改用官方红阶 `#d1281e`（白字对比度约 5.2） | 「一个一个来」「谁等谁」最直观，能与电子乐的拍子对齐 | 数据结构不在这个画面里 |
| C 终端与字节 | redis-cli 真实回显与原样字节在前，图形作注解 | 暮蓝底、深色终端、黄绿 `#dcff1e` 标关键值 | 「原样」可信 | 容易成为一屏屏文字（F23、F29） |

制作方倾向：A 为主画面，05、06 章借 B 的时间线，02、06 章用 C 的终端作特写；终章用 A 的七行对照表。颜色只取 redis.io 的色值（`research/MATERIALS.md`）；Redis 商标政策要求不模仿它的视觉识别，所以版式、图形不仿官网，画面不放产品标志（系列约定）。官网用的 Space Grotesk、Space Mono 是 OFL 字体，但仓库的字体清单里没有，本片暂用 Inter、Noto Sans SC、JetBrains Mono；要加须由维护者改 `kit/assets.json`。

配乐小样（`tools/music_demo.py`，各约 60 秒，−18 LUFS，只做了数值自检，没有人耳试听）：A「事件循环」124 拍、D 小调，十六分拨弦一拍一组、嘀嗒不变速；B「微秒」104 拍、E 大调，FM 玻璃钟与极快的装饰音群，无鼓；C「终章」94 拍、C 小调转 C 大调收尾，失谐锯齿铺底逐步打开，一次低频落点，无铜管与合唱。

配音候选（`tools/voice_demo.py`，MiniMax speech-2.8-hd，语速 1.15，15 句代表句）：`Chinese (Mandarin)_Male_Announcer`、`Chinese (Mandarin)_Radio_Host`、`Chinese (Mandarin)_Sincere_Adult`、`male-qn-jingying-jingpin`、`male-qn-daxuesheng-jingpin`。避开了本系列成片用过的男声（Gentleman、Reliable_Executive、Gentle_Youth）。Whisper 回听 5 段都没有漏词，英文命令按单词读；多音字没有人耳听过。
