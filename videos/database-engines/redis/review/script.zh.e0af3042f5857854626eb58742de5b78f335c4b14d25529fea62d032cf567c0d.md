### open · 无章节卡

向 Redis 要 2050 号用户：名字 Alice，年龄 42 服务端做完这件事，大约用了五微秒 这五微秒里，它一次也没有碰磁盘 Alice 的资料，一直就在内存里 内存很快，可是一断电，里面的东西就没了 磁盘慢得多，断了电却还记得 这个系列前六集的数据库，都把数据放在磁盘上 内存多半拿来做缓存，好少读几次磁盘 Redis 反过来，把数据整个放在内存里 磁盘上的文件，只用来在重启之后把数据找回来 它的名字来自 Remote Dictionary Server 远程字典服务：一个键，对应一个值 Redis 是一个*键值数据库* 2009 年，Salvatore Sanfilippo 为了撑住自己的实时日志分析工具，写了它 Redis 把 Alice 交给了一块会忘的内存 进程一停，她还在吗？内存满了，谁要被请出去？ 这一集，就跟着 Alice 这一个键 看 Redis 怎样记住她，又怎样忘掉她

### dict · 01 一张哈希表 不用迁就磁盘，数据怎样放？

前几集的 B 树一层层往下找，为的是少读几页磁盘 数据在内存里，按键找一个值，可以更直接 同样的 4096 个用户，每人一个键，键名由应用来起 例子中是 user 加编号，Alice 的键是 user:2050 所有的键，放进一张*哈希表* 哈希表是一排格子，每一格叫一个桶 一个键先算成一个数，叫哈希值 哈希值决定它落进哪一个桶 找的时候再算一遍，直接到那个桶里去拿 两个键落进同一个桶，就在桶里排成一串 此时，4096 个键分在 8192 个桶里 六成的桶是空的，有键的大多只有一个 最长的一串有 6 个 找一个键，通常比对一两次就找到了

### insert · 02 增 Alice 注册，内存里多了什么？

Alice 注册时，应用发来一条 HSET 写下两个字段：name 和 age Redis 为这个键建一个对象 对象头 16 个字节，记着值的类型和存法 键名就紧跟在后面 值是一段连续的 27 个字节，叫 *listpack* 先是总长和项数，然后 name、Alice、age、42 一项挨着一项 每一项前后各有一个字节，记它的类型和长度 42 是个小整数，只占一个字节 字段少、值又短的时候，Redis 就这样挤在一起存，省内存 和 MongoDB 的文档一样，字段名每个用户都要存一遍 算下来，Alice 这个键占 55 个字节 4096 个用户，一共不到 600 KB

### find · 03 查 找到 Alice，走了哪条路？

Bob 要看 Alice 的资料 发来一条 HGETALL user:2050 Redis 算出这个键的哈希值，找到那个桶，比对键名 拿到对象，把那 27 个字节读出来 开头那五微秒，就花在这里 可要是 Bob 只知道她叫 Alice 呢？ Redis 只认键，没有按名字的索引 只能把 4096 个键一个个取出来，比对名字 这一次用了三四毫秒，比按键找慢了几百倍 所以在 Redis 里，存的时候就要想好将来怎么找 要按名字找，就再存一个键，从名字指到编号

### update · 04 改 改一个数字，内存里改了什么？

Alice 过生日，42 岁变成 43 一条 HSET，把 age 改成 43 这 27 个字节还在原来的地址 只有一个字节变了：2a 变成 2b 42 就这样被盖掉，没有留下旧的一版 InnoDB、PostgreSQL 改的时候，都会留住旧版本 好让正在读的人，照旧读到改之前的样子 Redis 不留，要是这时 Bob 正好在读呢？

### concur · 05 事务与并发 有人在读，有人在写，谁等谁？

Bob 读不到改了一半的 Alice 因为在 Redis 里，执行命令的只有一个线程 所有客户端的命令排成一队，一次执行一条 一条做完，才轮到下一条 两个客户端同时给一个数各加一万次，结果正好是两万 用不着锁，也用不着旧版本 数据在内存里，一条命令几微秒就做完了 一个线程排着队做，也来得及 只是一条慢的，后面的都得等 实验里有人让服务端停了半秒 Bob 的一次读，就跟着多等了 0.4 秒 所以 Redis 尽量不让哪一条命令做太久 连哈希表长大也是这样 4096 个键装满 4096 个桶，桶就翻成 8192 个 旧桶里的键，不一口气搬完 每读写一次，顺手搬一个桶 这叫*渐进式 rehash* 一件事要两条命令，就麻烦了 还是 Alice 过生日：先读出 42，再写回 43 两个客户端同时这样做，都读到 42，都写回 43 加了两次，只多了一岁 *MULTI* 和 *EXEC* 能把几条写命令连在一起做 中间不会插进别人的命令 可先读、再算的那一步，连不进去 这时用 *WATCH*：先盯住这个键，再读、再算、再 EXEC 要是中间有人改过它，这次 EXEC 就什么也不做 实验里 Alice 落空了一次，重读一遍，才得到 44 Redis 的事务也不回滚，连着做的命令里有一条出错 其余的照样生效 官方文档说，支持回滚会大大影响 Redis 的简单和性能

### crash · 06 出错怎么办 进程没了，还记得 Alice 吗？

进程一死，内存里的就都没了 要在重启后找回来，还得往磁盘上写一份 Redis 有两种写法 一种是快照，叫 *RDB* 隔一阵子，把内存里的全部数据写成一个文件 写的时候分出一个子进程去写，主进程照常处理命令 Alice 那 27 个字节，原样在文件里 缺省是改得越多，存得越勤，最短也隔一分钟 实验里，写完 4096 个用户马上杀掉进程 重启之后，一个都不剩 存过一次快照，再把 Alice 改成 43，杀掉 回来的是 42 另一种叫 *AOF*，缺省不开 一打开，先把此刻的数据存成一份快照 之后每执行一条写命令，就原样追加到日志末尾 重启时先读快照，再把日志里的命令执行一遍 和 InnoDB 重放 redo，是一个道理 实验里一边不停地加一，一边杀掉进程 最后收到的回复是 33287 重启之后，还是 33287 Redis 回复之前，已经把命令交给了操作系统 进程死了，这些还在 要是整台机器断电，按官方的说法 可能丢掉最后一秒左右的数据 每条都先落盘再回复，就一条也不丢，只是慢

### delete · 07 删 Redis 什么时候忘掉一个键？

最后，Alice 注销了 应用发来一条 DEL user:2050 这个键当场从哈希表里摘掉，内存随即释放 也可以给键定一个寿命，到期自己消失 有人来访问时发现过期，当场删掉 没人访问的，后台定时抽查一批 实验里关掉抽查，过期的键就一直占着位置 直到被碰一下才消失 内存也装不下太多 给它设了上限，满了以后，缺省是拒绝再写 也可以让 Redis 挑最久没用的键删掉，给新数据腾地方

### five · 08 五个问题 五个问题，Redis 怎样回答？

回头看，Redis 这样回答五个问题 数据怎么放：一张内存里的哈希表，值挤成紧凑的字节 怎么找：只按键，算一次哈希就到 改和删：原地覆盖，当场删除，或者到期消失 怎么并发：一个线程，一次一条 几条要连着做，用 MULTI 和 WATCH 出错怎么办：快照加命令日志，丢多少，看多久落一次盘

### finale · 09 旧的 42 改掉的 42，去了哪里？

一条查询，一行结果，零点零零七秒 这一瞬间，数据库在磁盘上做了什么 那一次查的，就是 alice 七集里，她都过了一次生日 在 Redis 里，这是原地改掉一个字节 内存里的 42，就这样没了 MyISAM 也是原地改，改完想撤回，只得到一句警告 InnoDB 改之前，先把 42 记进 undo，所以撤得回来 Bob 这时来读，读到的也是 undo 里的 42 PostgreSQL 和 MongoDB，也都给他留着 42 ClickHouse 为这一岁，重写了一亿个年龄 旧的那一亿个，至少还留八分钟 SQLite 改之前，先把整页原样抄进回滚日志 进程被杀，再打开时抄回去，Alice 还是 42 undo、旧版本、回滚日志、旧片段 存的都是改之前的样子 留到没人用得着，才清掉 Redis 里，Alice 注销以后，一个字节也不剩 开着 AOF，磁盘上还有一份快照，是她过生日之前存的 后面的日志一条条记着：她过了生日，Dave 注册 最后一条，是她注销 重启时，Redis 从这份快照开始，一条一条再做一遍 那份快照里，她还是 42 岁
