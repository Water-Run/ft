### open · 无章节卡

一条命令，一个结果 向 Redis 要 2050 号用户：名字 Alice，年龄 42 服务端做完这件事，用了大约五微秒 这么快，一个原因是：它不用去磁盘上找 数据就在内存里 这个系列前六集的数据库，数据都住在磁盘上 内存只是一块缓存 Redis 倒了过来：内存里的就是数据本身 磁盘上的文件，只是为了重启之后能找回来 它的名字来自 Remote Dictionary Server 远程字典服务 字典，就是一个键对应一个值 Redis 是一个*键值数据库* 2009 年，Salvatore Sanfilippo 为了撑住自己的实时日志分析工具，写了它 可数据放在内存里，进程一停、机器一断电 它们还在吗？ 还是那几个问题：怎么放，怎么找，怎么改和删 很多人同时用时谁等谁，出了错怎么办

### dict · 01 一本字典 没有表，数据放在哪里？

在 Redis 里，没有表，也没有 SQL 同样的 4096 个用户，每人一个键 键名由应用自己起，例子中是 user 加上编号 Alice 是 2050 号，她的键就是 user:2050 键对应的值，可以是一个字符串，也可以是一组字段 Alice 的值是两个字段：name 是 Alice，age 是 42 4096 个键放在哪里？一张*哈希表* 哈希表是一排格子，每一格叫一个桶 拿到一个键，先把它算成一个数，叫哈希值 哈希值决定它落进哪一个桶 要找的时候再算一遍，就知道去哪个桶里拿 不用排序，也不用从树根一层层往下走 两个键落进同一个桶，就在桶里串成一条链 此时，4096 个键分在 8192 个桶里 六成的桶是空的，有键的大多只有一个 最长的一条链有 6 个 所以找一个键，通常只要比一两次

### insert · 02 增 Alice 注册时，写下了什么？

Alice 注册，应用发来一条 HSET Redis 在内存里为这个键建一个对象 对象头 16 个字节，记着值是什么类型、怎样存放 键名 user:2050 紧跟在对象头后面 值是一段连续的字节，叫 *listpack* Alice 这一段，一共 27 个字节 开头记总长和项数，然后 name、Alice、age、42 一项挨着一项 每一项前后各一个字节，记它的类型和长度 42 是个小整数，一个字节就存下了 最后一个 ff 表示到此为止 和 MongoDB 的文档一样，字段名每个用户都存一遍 Alice 这个键一共占 55 个字节 4096 个用户，一共不到 600 KB 用户越来越多，桶总会不够用 键数一到桶数，桶就翻一倍 这一次，4096 个桶装进 4096 个键，就变成了 8192 个 可旧表里的键，不是一口气搬完 每读写一次，顺手搬一个桶 这叫*渐进式 rehash* 每一步都很小，没有哪条命令要等一次大搬家

### find · 03 查 找到 Alice，走了哪条路？

Bob 要看 Alice 的资料 发一条 HGETALL user:2050 算出这个键的哈希值，找到桶，在桶里比对键名 拿到对象，读出那 27 个字节，就是开头那五微秒 可要是按名字找 Alice 呢？ Redis 只认键，没有按名字建的索引 只能把 4096 个键一个个拿出来，看名字对不对 扫一遍用了三四毫秒，比按键找慢了几百倍 在 Redis 里，要怎么找，存的时候就得想好 要按名字找，就自己再存一个从名字到编号的键

### update · 04 改 改一个数字，内存里改了什么？

Alice 过生日，42 岁变成 43 一条 HSET，把 age 改成 43 改之前、改之后，这 27 个字节在内存里的地址没变 变的只有一个字节：2a 变成了 2b 旧值 42 直接被盖掉 InnoDB、PostgreSQL 改的时候，会留住旧的一版 好让正在读的人，照旧看到改之前的样子 Redis 一版也不留，也没有为撤销另记一笔 那要是 Bob 这时正在读她的资料呢？

### concur · 05 事务与并发 有人在读，有人在写，谁等谁？

Bob 在读，Carol 在写，Redis 的答案很简单 一个一个来 执行命令的，只有一个线程 另外几个线程只做后台杂事，比如关文件、释放内存 所有客户端的命令排成一队，一次执行一条 一条命令执行的时候，谁也插不进来 两个客户端同时给一个计数各加一万次，结果正好两万 不用行锁，也不用留旧版本 同一时刻，只有一条命令在碰数据 所以 Bob 不会读到改了一半的 Alice 代价是：一条慢命令，所有人都得等 实验里 Carol 让服务端停了半秒，Bob 就跟着等 桶要一个一个地搬，也是为此：一口气搬完，所有人都得等 可一件事要两条命令呢？ 回到她过生日那一刻：加一岁，要先读出 42，再写回 43 要是两个客户端同时这样做，都读到 42，都写回 43 加了两次，只多了一岁 两条命令之间，别人的命令插了进来 *MULTI* 让命令先排进队，*EXEC* 时一口气做完 排队的时候，Bob 读到的还是 42；EXEC 之后才是 43 可排进队的命令，要等到 EXEC 才执行 先读出 42 再算出 43，这一读，没法放进队里 所以还有 *WATCH*：先盯住这个键 要是 EXEC 之前它被别人改过，这次 EXEC 什么也不做 这一次 Carol 抢先改成 43，盯着它的 EXEC 回来一个空 重读一遍再做，得到 44：不加锁，冲突了就重来 但 Redis 的事务没有回滚 EXEC 里有一条执行出错，前面那条照样生效 官方的理由是：支持回滚 会大大拖累 Redis 的简单和速度

### crash · 06 出错怎么办 进程没了，数据还在吗？

数据在内存里，进程一死，内存里的就都没了 要在重启后找回来，就得往磁盘上写一份 Redis 有两种写法 第一种是快照：把某一刻内存里的全部数据写成一个文件 叫 *RDB* 写快照时，Redis 分出一个子进程 子进程照着分出那一刻的数据写文件，主进程接着处理命令 Alice 那 27 个字节，原样在文件里 缺省是隔一阵子存一次：改得越多，隔得越短 最短也要隔一分钟 实验里，写完 4096 个用户立刻杀掉进程 重启之后，一个都不剩 存过一次快照、再把 Alice 改成 43，然后杀掉 回来的是 42 上一次快照之后的修改，跟着进程一起没了 第二种是 *AOF*，缺省不开：每执行一条写命令 就把这条命令本身，追加到文件末尾 Alice 改成 43，文件里就多出这一段 重启时，把这些命令从头再执行一遍 和 InnoDB 的 redo 一样，都是靠重放回到崩溃之前 实验里开着 AOF，一边不停地加一，一边杀掉进程 最后收到的回复是 33287 重启之后，还是 33287 因为 Redis 在回复之前，已经把命令交给了操作系统 进程被杀，交出去的还在 可交给了操作系统，还不等于落到了磁盘上 开了 AOF，缺省每秒落一次盘 要是整台机器断电，按官方的说法 可能丢掉大约一秒的数据 一条都不想丢，可以每条命令先落盘再回复，代价是慢 快照恢复得快、丢得多；AOF 丢得少、文件大 两种可以同时开

### delete · 07 删 删掉的键去了哪里？

最后，Alice 注销：DEL user:2050 这个键立刻从哈希表里摘掉，占的内存当场释放 键还可以带一个寿命：到期自己消失 有人来访问时，Redis 发现它过期了，当场删掉 没人访问的，后台定时抽查一批，过期的顺手删掉 实验里关掉抽查，过期的键一直占着位置 直到被碰一下才消失 内存设了上限又满了，缺省是拒绝写入 也可以让它挑最久没用的键删掉，给新数据腾地方

### five · 08 五个问题 五个问题，Redis 怎样回答？

一个数据库引擎必须回答的五个问题，Redis 这样回答 怎么放：一个键一个对象，值是紧凑的字节 全都放在内存里的一张哈希表上 怎么找：只按键找，算一次哈希，直达那个桶 改和删：直接覆盖、立刻删除，或者到期自己消失 怎么并发：一个线程，一条一条执行 MULTI、EXEC 把几条命令打成一包 WATCH 发现有人改过，就不做 出错怎么办：快照加命令日志 丢多少，取决于多久落一次盘

### finale · 09 一个字节 Alice 过生日，七个引擎怎样改？

这个系列的七个引擎，到这里都走完了 同一群人，同一段经历 Alice 注册，被找到，过生日，最后注销 其中最小的一件事，是过生日 年龄加一，数据里只差一个字节 MyISAM 把它写回原处，没有退路 InnoDB 也写回原处，但先把旧值抄进 undo PostgreSQL 不碰原来那一行，另写一个新版本 SQLite 动手之前，先把要改的页原样抄进回滚日志 ClickHouse 的文件从来不改 为了这一个字节，把一亿个年龄重写一遍 MongoDB 在内存里挂上新版本，检查点时整页写到新地方 Redis 就在原地，把 2a 改成 2b，什么也不留 同一个字节，七种改法 改的那一刻，要是有人正在读 MyISAM 锁住整张表，读和写只能轮流 InnoDB、PostgreSQL、MongoDB 留着旧版本 读的人照旧读他的 Redis 一个一个来，没有人会读到一半 改到一半出了事呢？ SQLite 留着原样的页，InnoDB 记着 redo 和 undo Redis 有快照和命令，ClickHouse 的旧文件原封未动 只有 MyISAM 什么也没留，只能事后检查、修复 没有哪一种是最好的 每一种，都是拿一样东西，换另一样 这个系列的第一集，从一个瞬间开始 一条查询，一行结果，零点零零七秒 这一瞬间，数据库在磁盘上做了什么 那一瞬间里，一个引擎替它回答了五个问题 数据放在哪里，怎样找到，怎样改和删 很多人同时来谁等谁，出了事怎样回来 一个数据库引擎是如何实现的？ 就是它对这五个问题的回答 而要读懂这些回答，可以先看它怎样改一个字节
