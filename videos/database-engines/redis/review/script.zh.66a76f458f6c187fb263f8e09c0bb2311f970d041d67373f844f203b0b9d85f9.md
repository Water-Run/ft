### open · 无章节卡

一条命令，一个结果 向 Redis 要 2050 号用户：名字 Alice，年龄 42 服务端做完这件事，用了大约五微秒 这么快，一个原因是：数据根本不在磁盘上 它就在内存里 这个系列前六集的数据库，从 MyISAM 到 MongoDB 数据都住在磁盘上，内存只是一块缓存 Redis 倒了过来：内存里的就是数据本身 磁盘上的文件，只是为了重启之后能找回来 它的名字来自 Remote Dictionary Server 远程字典服务 字典，就是一个键对应一个值 Redis 是一个*键值数据库* 2009 年，Salvatore Sanfilippo 为了撑住自己的实时日志分析工具，写了它 可数据放在内存里，进程一停、机器一断电 它们还在吗？ 还是那几个问题：怎么放，怎么找，怎么改和删 很多人同时用时谁等谁，出了错怎么办

### dict · 01 一本字典 没有表，数据放在哪里？

在 Redis 里，没有表，也没有 SQL 同样的 4096 个用户，每人一个键 键名由应用自己起，例子中是 user 加上编号 Alice 是 2050 号，她的键就是 user:2050 键对应的值，可以是一个字符串、一组字段 也可以是列表、集合 Alice 的值是两个字段：name 是 Alice，age 是 42 4096 个键放在哪里？一张*哈希表* 哈希表是一排格子，每一格叫一个桶 拿到一个键，先把它算成一个数，叫哈希值 哈希值决定它落进哪一个桶 要找的时候再算一遍，就知道去哪个桶里拿 不用排序，也不用从树根一层层往下走 两个键落进同一个桶，就在桶里串成一条链 此时，4096 个键分在 8192 个桶里 六成的桶是空的，有键的大多只有一个 最长的一条链有 6 个 所以找一个键，通常只要比一两次

### insert · 02 增 Alice 注册时，写下了什么？

Alice 注册，应用发来一条 HSET Redis 在内存里为这个键建一个对象 对象头 16 个字节，记着值的类型和编码 键名 user:2050 紧跟在对象头后面 值是一段连续的字节，叫 *listpack* Alice 这一段，一共 27 个字节 开头记总长和项数，然后 name、Alice、age、42 一项挨着一项 每一项前后各一个字节，记它的类型和长度 42 是个小整数，一个字节就存下了 最后一个 ff 表示到此为止 和 MongoDB 的文档一样，字段名每个用户都存一遍 Alice 这个键一共占 55 个字节 4096 个用户，一共不到 600 KB 字段多了、值长了，Redis 会改用真正的哈希表来存 那 8192 个桶是这么来的：键数一到桶数，桶就翻倍 但旧表里的键不是一口气搬完，每读写一次，顺手搬一个桶 这叫*渐进式 rehash* 每一步都很小，没有哪条命令要等一次大搬家

### find · 03 查 找到 Alice，走了哪条路？

Bob 要看 Alice 的资料 发一条 HGETALL user:2050 算出这个键的哈希值，找到桶，在桶里比对键名 拿到对象，读出那 27 个字节，就是开头那五微秒 连着压起来更快：50 个客户端，每秒 16 万次 服务端平均每次只花 0.24 微秒 可要是按名字找 Alice 呢？ Redis 只认键，没有按名字建的索引 只能把 4096 个键一个个拿出来，看名字对不对 这一次用了三四毫秒，比按键找慢了几百倍 在 Redis 里，要怎么找，存的时候就得想好 要按名字找，就自己再存一个从名字到编号的键

### update · 04 改 改一个数字，内存里改了什么？

Alice 过生日，42 岁变成 43 一条 HSET，把 age 改成 43 改之前、改之后，这 27 个字节在内存里的地址没变 变的只有一个字节：2a 变成了 2b 旧值 42 直接被盖掉，没有留旧版本 也没有为撤销它另记一笔 要是 Bob 这时正在读，不怕读到一半吗？ Redis 不用担心这件事，原因在下一章

### concur · 05 事务与并发 有人在读，有人在写，谁等谁？

Bob 在读，Carol 也在写，Redis 的答案很简单 一个一个来 执行命令的，只有一个线程 另外几个线程只做后台杂事，比如把日志刷到磁盘 所有客户端的命令排成一队，一次执行一条 一条命令执行的时候，谁也插不进来 Alice 和 Carol 同时各加一万次，结果正好两万 不用行锁，也不用留旧版本 同一时刻，只有一条命令在碰数据 所以 Bob 不会读到改了一半的 Alice 代价是：一条慢命令，所有人都得等 实验里 Carol 让服务端停了半秒，Bob 就跟着等 可一件事要两条命令呢？ Alice 和 Carol 都先读到 42，各自加一，写回 43 加了两次，只多了一岁 *MULTI* 让命令先排进队，*EXEC* 时一口气做完 排队的时候，Bob 读到的还是 42；EXEC 之后才是 43 *WATCH* 先盯住这个键 要是 EXEC 之前它被别人改过，这次 EXEC 什么也不做 实验里 Carol 抢先改成 43，Alice 的 EXEC 回来一个空 她重读一遍再做，得到 44：不加锁，冲突了就重来 但 Redis 的事务没有回滚 EXEC 里有一条执行出错，前面那条照样生效 官方的理由是：支持回滚 会大大拖累 Redis 的简单和速度

### crash · 06 出错怎么办 进程没了，数据还在吗？

数据在内存里，进程一死，就都没了 要在重启后找回来，就得往磁盘上写一份 Redis 有两种写法 第一种是快照：把某一刻内存里的全部数据写成一个文件 叫 *RDB* 写快照时，Redis 分出一个子进程 子进程照着分出那一刻的内存慢慢写，主进程接着处理命令 Alice 那 27 个字节，原样在文件里 缺省的规则：一小时改过 1 次、五分钟改过 100 次 或者一分钟改过一万次，就存一次快照 实验里，写完 4096 个用户立刻杀掉进程 重启之后，一个都不剩 存过一次快照、再把 Alice 改成 43，然后杀掉 回来的是 42 第二种是 *AOF*，缺省不开：每执行一条写命令 就把这条命令本身，追加到文件末尾 Alice 改成 43，文件里就多出这一段 重启时，把这些命令从头再执行一遍 和 InnoDB 的 redo 一样，都是靠重放回到崩溃之前 命令交给操作系统，还要等它真正落到磁盘 开了 AOF，缺省每秒落一次 Redis 在回复之前，已经把命令交给了操作系统 所以只是进程被杀，交出去的都还在 实验里一边加一一边杀，最后收到的回复是 33287 重启之后，还是 33287 要是整台机器断电，按官方的说法 可能丢掉大约一秒的数据 一条都不想丢，可以每条命令先落盘再回复，代价是慢 AOF 越记越长，所以会不时重写 当前数据存成底稿，新命令接在后面 快照恢复得快、丢得多；AOF 丢得少、文件大 两种可以同时开

### delete · 07 删 删掉的键去了哪里？

Alice 注销：DEL user:2050 这个键立刻从哈希表里摘掉，内存还给分配器 后来 Dave 注册，键名 user:4097 也是应用起的 键还可以带一个寿命：到期自己消失 有人来访问时，Redis 发现它过期了，当场删掉 没人访问的，后台定时抽查一批，过期的顺手删掉 实验里关掉抽查，过期的键一直占着位置 直到被碰一下才消失 内存设了上限又满了，缺省是拒绝写入 也可以让它挑最久没用的键删掉，给新数据腾地方

### five · 08 五个问题 五个问题，Redis 怎样回答？

一个数据库引擎必须回答的五个问题，Redis 这样回答 怎么放：一个键一个对象，值是紧凑的字节 全都放在内存里的一张哈希表上 怎么找：只按键找，算一次哈希，直达那个桶 改和删：直接覆盖、立刻删除，或者到期自己消失 怎么并发：一个线程，一条一条执行 MULTI、EXEC 把几条命令打成一包 WATCH 发现有人改过，就不做 出错怎么办：快照加命令日志 丢多少，取决于多久落一次盘

### finale · 09 同一段经历 七个引擎，七种答案

这个系列的七个引擎，到这里都走完了 同一群人，同一段经历 Alice 注册，被找到，过生日，最后注销 MyISAM 把她写进数据文件，靠一棵 B 树找到她 没有事务，出了错只能事后检查、修复 InnoDB 让整张表就是一棵主键树 用 undo 留住旧版本，用 redo 在崩溃后重做 PostgreSQL 把她放进堆里，每改一次写一个新版本 旧的留给 VACUUM 回收 SQLite 把整个数据库放进一个文件，嵌进程序里 ClickHouse 把一亿个人拆成一列一列 算平均年龄只读一列，改她一行却要重写整列 MongoDB 不要表，整份文档连同字段名存进 B 树 Redis 把她放在内存里，一张哈希表直接找到 七种做法，没有哪一种是最好的 每一种都在回答同一件事：为了这些好处，愿意付出什么 放在磁盘上，就要想办法少读几页 放在内存里，就要想办法别在断电时全丢 很多人同时来，要么加锁，要么留住旧版本 要么干脆一个一个来 怕崩溃，大多先记一笔，出了事照着记录恢复 这个系列的第一集，从一个瞬间开始 一条查询，一行结果，零点零零七秒 这一瞬间，数据库在磁盘上做了什么 那一瞬间里，有文件、有页、有树、有日志 有一个引擎，替它回答了这五个问题 一个数据库引擎是如何实现的？ 就是它对这五个问题的回答
