## 简报

**核心问题**：一条 SQL 进入应用后，SQLite 怎样沿整棵树找到 Alice，再把一次修改可靠地保存下来？

策划者要求（2026-10-22 原话）：

> SQLite大概10分钟, 视觉当然契合SQLite, 简洁有力的音乐

先前选择「梳理选题和切入点，暂不开工」；同日随后要求：

> SQLite推进实时测绘部分吧.

新指令据此取代「暂不开工」，本轮推进到实测取证；约 10 分钟、视觉契合 SQLite、音乐简洁有力的要求保留。视觉、音乐的具体方案由制作方决定。

同次反馈原样记为 [P50](../../../docs/log/feedback.md#2026-10-22数据库引擎的整体结构与理解负担)：Firebird 理解负担过大；InnoDB、PostgreSQL 过分集中于具体页，缺少整体树；MyISAM 对实现过程的讲法最直观。本轮未重看旧片，不把该评价写成自行核查的旧片结论。

本片的内容约束：

- 先建立应用、文件、表树、索引树之间的关系，再定位到页。不能先拆页头，让观众不知道这一页在哪里。
- 沿同一个例子的输入、选择、变化、结果讲；每个局部都说得清属于整体哪里、负责哪一步。
- 先说明根怎样逐层缩小范围，再解释索引为什么返回行号、为什么还要找一次表。
- 修改、并发与恢复先交出同一条记录的旧值、新值和文件变化，再给术语。
- 每集独立可懂；SQLite 表树和索引树按真实结构区分，不统一套成一种 B+ 树。

候选推进顺序：嵌入应用的引擎 → 文件里有哪些树 → 沿姓名索引与表树找 Alice → 页满时树怎样生长 → 修改与提交、读者看到什么 → 出错后的恢复与取舍。这是材料次序，尚非已确认文案或分镜。

暂不作为主讲：逐字节解释完整文件头、每种 varint 与 serial type、逐条虚拟机指令、WAL 校验和算术、全部编译选项。这些证据留给校核，不把全部测绘细节塞进十分钟。

## 实测入口

先看[完整树的文字地图](research/lab/out_02_trees.txt)，再查 [02 的数据](research/lab/out_02_structure.json)。同一主库中：

- users 根页 2 的三个子页是 132、133、261，分隔行号为 1560、3081。
- 找 Alice 的姓名索引逻辑路径是 **262 → 281 → 263**，得到行号 2050。
- 再沿表树 **2 → 133 → 130**，取得 Alice、年龄 42。
- [03](research/lab/out_03_queries.json) 的首次查询页缓存未命中：索引后回表 7、覆盖索引 4、强制扫描 261；同连接第二次都为 0。

这里的路径由真实文件字节重建，并与 DBSTAT 的页集、深度、单元数核对；不是逐页物理 I/O 跟踪。运行计数是 SQLite 页缓存统计，不是磁盘读取次数。

## 交接

主实验显式用 **1024 字节页**，便于较小数据量形成三层树；同批 users 与索引另做 **4096 字节页**对照。页号、层数、分裂阈值仅属于本样本，不是引擎常数。

原始 SQL 和完整回显为每组 out_*.txt，可用数据为 out_*.json。第三方源码、工具包在忽略的 research/_src/；二进制数据库在忽略的 out/lab/。本轮没有清理已有文件或其他片子的材料。

尚未做：函数调用或逐页 VFS I/O 动态追踪、真实断电、设备持久性验证、吞吐与时延压测、操作系统冷缓存、WITHOUT ROWID / 自定义排序 / 自动清理模式的扩展实验。有限观测不外推到这些范围。

没有正式文案和人工确认，尚不满足正式制作交接闸门。经验规则复核保持 pending，不填成片结论。

## 复现

运行：

`python videos/database-engines/sqlite/research/lab/run_all.py`

Python 3.10 或更新；首次联网取得经 SHA3-256 核对的官方工具包与源码。其他系统可指定 FT_SQLITE 为同版本命令行程序；当前只在 Windows 实测。脚本不调用 Python 自带 SQLite。每次在本片 out/lab/ 新建目录，不覆盖、删除已有数据库。

公开证据不带个人路径、主机名或凭据。WAL 的盐值与回滚日志随机校验种子会变化，相关二进制哈希不承诺跨次相同；稳定的整树测绘数据可逐字节比较。
