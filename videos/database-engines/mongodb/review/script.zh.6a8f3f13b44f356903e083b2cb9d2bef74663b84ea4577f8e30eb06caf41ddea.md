### open · 无章节卡

Alice 在一个应用里注册，填了名字和年龄 应用把这两项交给 MongoDB，存了进去 再按名字去找，她的资料回来了，名字和年龄都在 还多出一项 _id，那是替她生成的一个编号 事先没有人规定，她的资料该有哪几项 找她的时候，也没有写一句 SQL 递过去的条件本身就是一小段数据，写着 name 等于 Alice 这个系列已经讲了五期 MyISAM、InnoDB、PostgreSQL、SQLite 最后是 ClickHouse 五个引擎，存放和查找的办法各不相同 可有一点是一样的 数据都摆成一张张表，先建表、定好有哪几列 再用 SQL 去写、去查 就连 ClickHouse 把表拆成一列一列地存，那也还是表 按表来组织数据、用 SQL 来查，这一类叫关系数据库 前面五期，讲的都是关系数据库 MongoDB 不一样：不用先建表、定好列，找人也不写 SQL 这样的数据库有个统称：在 SQL 前面加一个 No *NoSQL* No 有两种说法：不用 SQL，或者 Not only，不只是 SQL 它们不用关系表存数据，所以也叫非关系型数据库 MongoDB 是其中的文档数据库 另一类常见的叫键值数据库，这个系列最后还会遇到 MongoDB 把 Alice 这样一条记录，叫作一份*文档* 文档放在一起，叫一个*集合*，相当于 SQL 里的一张表 只是同一个集合里，文档的样子可以各不相同 比如另一个集合 people 里，Alice 有名字和年龄 同一个集合里，Erin 没有年龄，存着邮箱和两个标签 Frank 只有名字和一个地址 每份文档里，都存着它自己的字段名 表结构可以不要，资料总得放在磁盘上某个地方 要找得回来，要能改、能删 很多人同时读写、进程突然被杀，也得有办法 答案要一直往下找，找到一个叫 WiredTiger 的部件

### whole · 01 一个集合，三棵树 没有表，文档放在哪里？

MongoDB 的服务端，是一个叫 mongod 的进程 它收下查询，决定怎么执行 至于数据在内存和磁盘上怎样存放，交给下面一层 这一层叫*存储引擎* MongoDB 默认用的存储引擎，就是 WiredTiger 它原本是另一家公司做的，2014 年底，MongoDB 宣布收购 WiredTiger 自己，并不认识什么文档 它眼里只有一项一项的键和值 值里装的是什么，它不过问，只当是一串字节 它只管把这些项按键排好、存进文件、再按键找出来 这些键值分成几组，每一组是数据目录里的一个文件 文件里的项按键排好，组织成一棵树 Alice 所在的集合叫 users，它在数据目录里有三个文件 一个放文档本身 一个是按 _id 排好序的*索引*，集合一建好就有 开头是按名字找她的，所以另外按名字建了一个索引 一份文档，在这三棵树里各占一项 先看 Alice 注册的时候，写下的是什么

### insert · 02 增 Alice 注册时，写下了什么？

users 里一共有 4096 个用户，按注册的先后写进来 Alice 是第 2050 个 应用递过来的，只有名字和年龄 没有 _id，应用这边的驱动程序就先替她生成一个 这种编号叫 ObjectId，一共 12 个字节 接着，整份文档编码成一种二进制的格式，叫 *BSON* 开头 4 个字节记着整份的长度，她这一份是 47 个字节 后面每个字段依次写下类型、字段名和值 类型占一个字节，字段名以一个 0 收尾 最后再补一个 0，这份文档就到头了 这 47 个字节里，_id、name、age 三个名字 连同各自结尾的 0，一共占了 13 个，四分之一还多 交给 WiredTiger 之前，这份文档还缺一个键 MongoDB 会另发一个内部编号，叫 *RecordId* 按写进来的先后，从 1 开始一个一个往上加 Alice 的 RecordId，就是 2050 它和 _id 是两个编号，查出来的文档里平时看不到它 有了 2050，三棵树里各放什么就清楚了 集合树里，键是 2050，值是她整份 47 个字节 _id 索引里，键是她的 ObjectId，值里放着 2050 姓名索引里，键是 Alice 后面接上 2050，值是空的 _id 本来就不会重复，2050 放在值里 名字可以重复，2050 接在名字后面，同名的人也就分得开 两个索引，最后都指回 2050 这 4096 个人，是先写进集合，再补建的姓名索引 索引里的项，是建的时候一次写进去的 索引建好之后再注册的人，才是一次写三棵树 要是文档写进去了，索引还没写，进程就停了呢？ MongoDB 在内部替这一次写入开一个*事务* 三处写入都在里面 事务里的修改，要么全部生效，要么全部撤回 做完、让修改生效，叫作提交 所以不会出现文档进去了，索引里却找不到它的情况

### flush · 03 落盘 写完的文档，什么时候进文件？

4096 份都写完了，去数据目录看一眼集合文件 它只有 4 KB，这么多文档根本装不下 文档都还在 WiredTiger 的缓存里，没进集合文件 4096 份不多，缓存装得下 缓存紧张的时候，也会提前把一部分页写出去 写入先改的是缓存里的页，文件要晚一些才轮到 晚到什么时候？ 默认每隔 60 秒，WiredTiger 把这一刻所有改过的页 一起写进文件 这一次写盘，叫*检查点* 写的时候，缓存里的页并不能原样搬过去 内存里的页，摆法照顾的是很多人同时读写 文件里的页，要的是尽量少占地方 所以每一页先整理成磁盘上的格式，集合的页还要再压缩 集合的第一个叶页，整理好、还没压缩时一百一十多 KB 压缩后，在文件里只占 24 KB 做完一次检查点，集合文件变成了 96 KB 这时去看文件，才能看到集合树的形状 最底下一层叫叶页，这里有四个，键和值都在里面 每个叶页装着一段连续的 RecordId，从小到大排开 叶页上面是根页，记着每个叶页从哪个键开始 放在文件的哪里 这样按键排好、一层层往下指的树，叫 *B 树* 找一个键，就从根页出发，看着分界往下走 两个索引文件里，也各是一个根页带着一排叶页 后面每一章的实验，都重新装一遍这 4096 个人 从同样形状的这几棵树出发 先按名字找 Alice，看看走的是哪条路

### find · 04 查 按名字找 Alice，走了哪条路？

先在没有姓名索引的时候，按名字找一次 集合树是按 RecordId 排的，和名字没有关系 只能把集合树的叶页从头翻到尾，一份份比对名字 MongoDB 能报出一次查询看过几份文档 这一回，它看过 4096 份，只返回了 1 份 建上姓名索引，再找一次 索引里的项按名字排好了序，比的是名字的字节 其他人的名字都是 User 加编号的一长串，大写 U 开头 A 比 U 靠前，所以 Alice 排在第一项 从索引的根页出发，按分界走到第一个叶页，找到这一项 它的键是名字后面接着 2050 找到名字，也就拿到了她的 RecordId 拿着 2050，回到集合树 照文件里这棵树，根页记着第二个叶页从 1225 开始 第三个从 2449 开始 2050 落在中间，走第二个 在这个叶页里找到键 2050，取出那 47 个字节 路上的页已经在缓存里就直接用，不在才去文件里读 MongoDB 报的是看过 1 个索引键、1 份文档 可要是找所有 42 岁的人，年龄上没有索引 还是得把 4096 份都看一遍，挑出 66 个人 那为什么不给每个字段都建上索引？ 每多一个索引，插入一份文档就得多写一项 写一份要动三棵树，那改一份呢？

### update · 05 改 改一个数字，磁盘上改了什么？

从刚装好的树开始 Alice 过生日，年龄从 42 改成 43 还是先用姓名索引找到她，1 个索引键，1 份文档 名字和 RecordId 都没变，两个索引一项都不用动 只有集合树里 2050 这一项要改 可 WiredTiger 并不在页上把 42 擦掉、写成 43 它在这一项上挂一个新版本，写着 43 要是再改一次，就再挂一个，一个接一个连成一串 这一串，叫作这一项的*更新链* 旧的 42 还在，谁还需要旧值，照样读得到 这时去看集合文件，大小一个字节都没变 改动还没进集合文件，要等下一次检查点 做一次检查点，改过的这一页要写回文件 但它不写回原来的位置 整个叶页重新整理一遍，写到文件末尾一块新的地方 Alice 这一项里，其实只变了一个字节，42 变成 43 检查点却把整页 24 KB 重新写了一遍 叶页搬了家，根页记着它在哪，所以根页也重写一份 两个索引里记的是 2050，不是页在文件里的位置 页搬了家，索引一项也不用改 另外三个叶页没有改动，留在原地 只改了一个字节，为什么整页搬走？ 这样一来，上一个检查点用到的页，一页都没有被覆盖 新的检查点要是写到一半出了事，上一个还完完整整 重启时，就从那里接着来 等新的检查点写完，旧页占的地方才空出来，留给以后用 所以这一次，文件从 96 KB 长到了 132 KB

### delete · 06 删 删掉的文档去了哪里？

再从刚装好的树出发，这一回，Alice 注销了账号 三棵树都要动：集合树里删掉她的文档 两个索引里，各删掉指向她的一项 在内存里，删除和修改走的是同一条路 更新链上再挂一个版本，只是它不带内容 只说明这一项已经删了，叫*删除标记* 检查点时，第二个叶页和改年龄那次一样，写到了文件末尾 这一回，页里的 2049 后面，紧接着就是 2051 少了一份文档，文件却没有变小，也长到了 132 KB 第二个叶页原来的地方空了出来，等着后来的写入 接着，Dave 注册 他拿到的 RecordId 不是空出来的 2050，而是 4097 空出来的 2050，不会再发给别人 4097 比根页上最后一个分界 3124 还大 Dave 落进了最后一个叶页 检查点要给这一页找个地方写 它被写进了第二个叶页最初的那块地方

### concur · 07 事务与并发 Bob 在读、Carol 在写，谁等谁？

到这里，每一步都只有一个人在动这份文档 真实的应用里，常常有人在读，也有人在改 注册时那个事务，是 MongoDB 在内部替一次写入开的 应用要自己开事务，把几步读写包在一起 单机的 mongod 就不接受了 得跑成*副本集*才行，也就是一组维护同一份数据的 mongod 这一章用的副本集，只有一个成员 同样从 4096 个人刚放好开始，再演一遍 Alice 过生日 Bob 正开着一个事务在看她的资料，读到 42 岁 就在这时，Alice 把年龄改成 43，并且提交了 Bob 在同一个事务里再读一次，看到的还是 42 事务外面的人，此刻读到的已经是 43 等 Bob 结束这个事务再读，才是 43 因为 Bob 的事务一开始，就拿到了一份*快照* 快照记下的是那一刻，哪些修改已经提交，哪些还没有 之后他再读，快照之后才提交的新版本，他一律跳过 所以读到的还是 42 Bob 的事务还开着，Alice 的修改照样提交了 Bob 这边，也没停下来等 同一个集合里，改的要是不同的文档，也能同时改 两个人改的要是同一份文档，就不能各改各的了 Alice 在一个事务里改了自己的资料，还没有提交 管理员 Carol 在另一个事务里，也要改这份文档 一种办法，是让 Carol 排队，等 Alice 做完 WiredTiger 发现两人撞上了 MongoDB 不让 Carol 排队，直接回她一个错误，叫*写冲突* 错误上带着一个标签，意思是整个事务可以重来一遍 等 Alice 提交之后，Carol 把事务重做一遍，这次成功了 不先排队，真撞上了才让一方重来 WiredTiger 的多数读写都是这样，叫乐观并发 要是 Carol 没开事务，只是直接改这一份文档呢？ 她不会看到错误，MongoDB 在服务端替她一遍遍重试 直到大约一秒后 Alice 提交，Carol 的修改才成了 看起来像在等，其实这一秒里，服务端重试了很多次

### crash · 08 出错怎么办 进程被强制结束，丢了什么？

再回到检查点。它默认 60 秒才做一次 两次检查点之间的修改，都还没进数据文件 这时进程被杀掉，这些修改去哪里找？ 每一次修改，同时还记进了一份*日志* 日志是 journal 目录里的文件，新的记录一条条接在后面 它默认每隔 100 毫秒，落到磁盘上一次 可回复「写好了」的时候，日志不一定已经落盘 单机默认的写法，写进内存就回复成功 写的时候加上一个选项 j: true 才会等日志写进磁盘，再回复 来试一次。换回单机的 mongod，4096 个人重新放好 检查点刚做完，Alice 改了年龄，这一笔加了 j: true 接着 Dave 注册，用的是默认写法 两笔都回复成功之后，mongod 被强制结束 打开磁盘上的日志，最后一个检查点之后，记着两笔 一笔是 Alice，记下的是她整份新文档，43 岁 另一笔是 Dave，一个事务里三次写入，三棵树各一次 Dave 这一笔，也赶在结束之前进了磁盘上的日志 重启时，WiredTiger 先回到最后一个检查点 再把它之后的日志，一条一条重放一遍 Alice 又是 43 岁，Dave 也在，4097 份文档一份不少 那默认写法，什么时候会丢？ 用默认写法写一笔，回复成功后立刻结束进程 试了两轮，每轮五次 一轮一次都没留下，另一轮只留下 1 次 换成 j: true，同样立刻结束，五次都在 还是默认写法，只是隔 0.3 秒再结束，五次也都在 0.3 秒，比 100 毫秒一次的落盘要长 这只试了结束进程 这种情况下，可能丢的 是回复成功之后、日志还没落盘的那一小段 整台机器断电时，还要看操作系统有没有真把日志写到盘上 要不要多等这一下，写的时候自己选：加不加 j: true

### five · 09 五个问题 MongoDB 怎样回答？

文档编成 BSON，以 RecordId 为键放进集合树 每个索引另是一棵树，最后都指回 RecordId 找的时候，先在索引里拿到 RecordId，再回集合树取文档 改和删，先在内存里挂上新版本或删除标记 检查点时整页写到新地方，旧页不覆盖 同时读写，读的人看自己的快照 改同一份文档撞上了，就有一方重来 出了错，回到最后一个检查点，再重放日志 单机默认写法下，最后那一小段可能会丢

### beyond · 10 不是 SQL 没有了表，换来什么，付出什么？

没有了固定的表结构，换来了什么？ 只要没给集合设校验规则 除了 _id，每份文档想有哪些字段，就有哪些 Erin 的标签、Frank 的地址，直接写进去，事先不用声明 代价是字段名要跟着每份文档存一遍 4096 个人，_id、name、age 这三个名字 就存了 4096 遍 一路看下来，MongoDB 的数据最后住在磁盘上这几棵树里 内存只是一层缓存 从关系数据库的表，到 MongoDB 的文档 数据的样子，已经不用事先定好 还能不能更简单一点？ WiredTiger 在最底下，其实只认一项一项的键和值 开头提到的键值数据库，就是更简单的那一类 每一项就是一个键、一个值 它们常把数据放在内存里，读写都快 要是数据干脆全住在内存里，磁盘只用来保存呢？ 进程一死，内存里的东西又靠什么回来？ 这个系列的最后一站，是一个更简单的数据库 Redis
