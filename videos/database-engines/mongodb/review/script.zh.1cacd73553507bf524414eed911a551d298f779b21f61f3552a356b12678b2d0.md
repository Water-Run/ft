### open · 无章节卡

Alice 注册，填了名字和年龄 这两项交给 MongoDB，存了进去 事先没有建表，也没有定好有哪几列 再按名字去找，她的资料回来了，还多出一项 _id 找的条件，也写成同样的样子：name 是 Alice 整个过程，没有写一句 SQL 这个系列前五集的数据库 MyISAM、InnoDB、PostgreSQL SQLite，还有 ClickHouse 它们都是 SQL 关系数据库 先建表、定好列，再用 SQL 去写、去查 就连 ClickHouse 把表拆成一列一列地存，那也还是表 MongoDB 不用事先建表、定列，也不用 SQL 这一集，在 SQL 前面加一个 No 不要表，Alice 的资料是怎样存进磁盘 又怎样被找出来的？

### nosql · 01 NoSQL 一个数据库，为什么不要表？

先定好表、再用 SQL 去查，这样的数据库叫关系数据库 早在 2000 年代初，Google 发表过一篇论文 讲它的分布式存储系统 Bigtable 按 MongoDB 的说法，到了 2000 年代末 存储便宜了很多，数据越来越多，样子也越来越杂 比如有人填了年龄，有人只留邮箱和几个标签 有人只写了地址 表要是事先定死，这样的数据就很难装 云计算兴起，人们也更想多加几台机器，把数据分散开 而关系数据库，主要靠把一台机器换得更强 做 MongoDB 的人，就碰上过这样的难处 他们原来在广告公司 DoubleClick 那里每秒要服务四十多万条广告 照他们自己的说法，量一上去，关系数据库就很难扩展 2007 年，他们办了一家公司，叫 10gen 那几年，冒出了一批新的数据库，各走各的路 2009 年 6 月，旧金山有一场聚会 Cassandra、HBase、CouchDB 都上台介绍了 还有 MongoDB NoSQL 这个名字，就是从这场聚会传开的 这个词其实更早就有：90 年代末 一个开源的关系数据库，就叫 NoSQL 大约两个月后，MongoDB 发布了第一个版本 名字取自 humongous，意思是巨大 公司后来也改叫 MongoDB 再回到 NoSQL 这个名字：在 SQL 前面，加一个 No 有人把这个 No 读作不用 SQL 也有人读作 Not only，不只用 SQL 这些数据库没有统一的定义，只有几个常见的共同点 不用关系表和 SQL；记录可以随时加字段 还有，为在一大群机器上运行而设计 因为不按关系表存数据，它们也叫*非关系型数据库* NoSQL 常分四类：文档、键值、宽列、图 键值数据库，这个系列的最后还会遇到 MongoDB 属于文档数据库 开头 Alice 那份资料，在 MongoDB 里就叫一份*文档*

### whole · 02 一个集合，三棵树 没有表，文档放在哪里？

一份份文档放在一起，叫一个*集合* 相当于关系数据库里的一张表 不同的是，集合默认不规定文档长什么样 把第一章说的那几种人，放进另一个集合 people Alice 有名字和年龄 Erin 没有年龄，存着邮箱和两个标签 Frank 只有名字和一个地址 字段名就存在每份文档里，各带各的 这些文档各长各的样子，MongoDB 照样要把它们写进文件 再按名字找出来 MongoDB 的服务端是一个进程，叫 mongod，它分两层 上层收下查询，决定怎么执行 下层管数据在内存和磁盘上怎样存放，叫*存储引擎* MongoDB 的存储引擎叫 WiredTiger 原本是一家同名公司的产品 2014 年底被 MongoDB 收购 2015 年初的 3.0 版带上了它 如今的 9.0 版，默认就用它 WiredTiger 并不认识文档 它只存一项一项的键和值 值是一串字节，里面装的是什么，它不过问 这些键值按键排好序，存进数据目录里的文件 每个文件里排成一棵树，找起来不用从头翻 users 这个集合和它的两个索引 在数据目录里各占一个文件 一个放文档本身，叫集合树 一个是按 _id 排好序的*索引*，集合一建好就有 开头是按名字找她的，所以另外按名字建了一个索引 Alice 这一份文档，在三棵树里各占一项 从她注册的那一刻看起

### insert · 03 增 Alice 注册时，写下了什么？

users 里一共有 4096 个用户，按注册的先后写进来 Alice 是第 2050 个 应用递过来的，只有名字和年龄 开头查出来多的那项 _id，就是这时候来的 应用这边的驱动程序，先替她生成一个编号，叫 ObjectId 接着，整份文档编码成一种二进制格式，叫 *BSON* Alice 这一份，一共 47 个字节 里面一个字段接一个字段，每个字段都带着自己的名字 _id、name、age 这三个名字，各带一个结尾的 0 占了其中 13 个字节，四分之一还多 交给 WiredTiger 之前，还缺一个键 MongoDB 另发一个内部编号，叫 *RecordId* 按写入的先后，从 1 开始往上加 Alice 的 RecordId 是 2050 它和 _id 是两个编号；平时查出来的文档里，看不到它 有了 2050，三棵树里的三项就都能写出来了 集合树里，键是 2050，值是整份 47 个字节 _id 索引里，键是她的 ObjectId，值是 2050 姓名索引里，键是 Alice 再接上 2050，值是空的 _id 不会重复，_id 索引把 2050 放在值里 名字可能重名，姓名索引把 2050 接在名字后面 同名的也能分开 两个索引，最后都指回 2050 这 4096 个人是先写进来的，姓名索引后来才建 Alice 那一项，是建索引时补上的 之后再注册的人，比如后面的 Dave，三棵树都要各写一项 要是文档写进去了，索引还没写，进程就停了呢？ MongoDB 把这三处写入，放进同一个*事务* 事务里的修改，要么全部生效，要么全部撤回 生效的那一下，叫提交 文档进去了、索引里却找不到它，这种事不会发生

### flush · 04 落盘 写完的文档，什么时候进文件？

4096 个人写完，去数据目录看一眼集合文件 它只有 4 KB，装不下这么多文档 文档还在内存里，在 WiredTiger 的缓存中 缓存里按页存放，一页装着一批排好序的键值 写入先改缓存里的页，文件要过一会儿才更新 这 4096 份不多，缓存装得下 缓存要腾地方时，也会提前写出一部分 默认每隔 60 秒，WiredTiger 把改过的页写进文件 这一次写盘，叫*检查点* 做完一次检查点，集合文件从 4 KB 长到了 96 KB 这时打开文件，能看到集合树的样子 最底下一层是叶页，一共四个，键和值都在叶页里 每个叶页装着一段连续的 RecordId 叶页上面是根页，记着每个叶页从哪个键开始 在文件的哪里 找一个键，就从根页出发，看它落在哪一段，往下走 这样一层层往下指的树，叫 *B 树* 两个索引文件里，也各是一个根页带着一排叶页 页在内存里和在文件里，是两种样子 在内存里，页要方便很多人同时读写 写进文件，就要尽量少占地方 所以每一页先整理成磁盘上的格式，集合的页再压缩一遍 第一个叶页，整理好时一百一十多 KB 压缩以后，在文件里只占 24 KB 现在拿着一个名字，到这几棵树上找 Alice

### find · 05 查 按名字找 Alice，走了哪条路？

要是没有姓名索引，按名字找她，只能翻集合树 集合树按 RecordId 排序，和名字无关 只能把叶页从头翻到尾，一份份比对名字 MongoDB 报告：看了 4096 份文档，找到 1 份 有了姓名索引，再找一次 索引里的名字，按字节排好了序 这 4096 个人里，别人的名字都是 User 加编号 大写 U 开头；A 排在 U 前面 所以 Alice 就是索引里的第一项 从索引的根页往下，走到第一个叶页，找到她 这一项的键是 Alice 接 2050 这一项的键里，就带着她的 RecordId 拿着 2050，回到集合树 上一章检查点写出的那棵树里 根页记着：第二个叶页从 1225 开始 第三个从 2449 开始，第四个从 3124 开始 2050 落在第二个叶页，在那里取出她那 47 个字节 路上的页如果在缓存里，就直接用；不在，才去读文件 MongoDB 报告：这一次看了 1 个索引键、1 份文档 年龄上没有索引 找所有 42 岁的人，又要看完 4096 份，挑出 66 个 不过，索引越多，每插入一份文档要写的树也越多

### update · 06 改 改一个数字，磁盘上改了什么？

找到了她，再来改她 回到 4096 人刚写完、集合文件 96 KB 的时候 Alice 过生日，年龄从 42 改成 43 先用姓名索引找到她：1 个索引键，1 份文档 名字没变，RecordId 也没变，两个索引都不用动 只有集合树里 2050 这一项要改 WiredTiger 不在页上把 42 擦掉 它在这一项上挂一个新版本：43 再改一次，就再挂一个，连成一串，叫*更新链* 旧的 42 也还留着；要是有人同时在读，就会用到它 这时集合文件的大小没变，改动还在缓存里 做一次检查点，改过的这一页才写回文件 但不写回原来的位置 整个叶页重新整理，写到文件末尾一块新的地方 Alice 这一项里，只有一个字节变了：42 变成 43 检查点却把整页 24 KB 重新写了一遍 叶页换了位置，根页也得重写一份，记下新位置 两个索引里记的是 2050，不是位置，一项都不用改 另外三个叶页，留在原地 写到新地方，上一个检查点用到的页就原样留着 新的检查点要是写到一半出了事 重启时还能回到上一个，它完好无损 新的写完，旧页的地方才空出来，留给以后用 所以这一次，文件从 96 KB 长到了 132 KB 改一个字节，文件反而长了 那删掉一份，它会变小吗？

### delete · 07 删 删掉的文档去了哪里？

还是从那个 96 KB 的文件开始 这一回，Alice 注销了账号 三棵树都要动：集合树删掉她的文档 两个索引各删掉一项 在内存里，删除也是在更新链上挂一个版本 只是这个版本不带内容，只说这一项删了 它叫*删除标记* 检查点时，第二个叶页和改年龄那次一样，写到了文件末尾 页里的 2049 后面，紧接着就是 2051 少了一份文档，文件却没有变小，也长到了 132 KB 第二个叶页原来的地方，空了出来 接着，Dave 注册 他拿到的 RecordId 不是空出来的 2050，而是 4097 编号接着往上加，空出来的 2050 没有再发出去 4097 比根页上最后一个分界 3124 还大 Dave 落进了最后一个叶页 检查点给这一页找地方 用上了第二个叶页空出来的地方 根页也挪进了空出来的地方，文件末尾那一块用不着了 文件缩回 120 KB；还有 24 KB 空着，留给后来的写入 到这里，每一次都只有一个人在读写

### concur · 08 事务与并发 有人在读，有人在改

同一份文档，常常是有人在读，同时有人在改 第三章那个事务，是 MongoDB 替一次写入在内部开的 应用也可以自己开事务，把几份文档的读写包在一起 这是 2018 年的 4.0 版加上的 这样的事务，单机的 mongod 不接受 几台 mongod 维护同一份数据，叫一个*副本集* 这里的副本集，只有一台 同样从刚写完 4096 人的时候开始 再看一遍 Alice 过生日 Bob 开了一个事务，正在看她的资料：42 岁 这时 Alice 把年龄改成 43，提交了 Bob 在同一个事务里再读一次，还是 42 这时在事务外面读，已经是 43 Bob 结束事务以后再读，才是 43 Bob 的事务一开始，就拿到了一份*快照* 快照记下那一刻：哪些修改已经提交，哪些还没有 他顺着更新链往回找，快照之后才提交的 43 跳过去 读到的还是 42 Bob 的事务还开着，Alice 的修改照样完成，不用等 Bob 这些旧版本，也不会一直挂在内存里 页写回文件时，集合文件里只放每一项最新的版本 更旧、还有读者要用的，写进另一个文件，叫历史存储 读的人不挡改的人。两个人都在改呢？ 改同一个集合里不同的文档，可以同时进行 两个人改的要是同一份文档，就不能各改各的了 Alice 在一个事务里改了自己的资料，还没提交 管理员 Carol 在另一个事务里，也要改这份文档 可以让 Carol 排队，等 Alice 提交。MongoDB 没这么做 WiredTiger 一发现两人改的是同一份文档 Carol 就直接收到一个错误，叫*写冲突* 错误上带着标签，意思是整个事务可以重来 Alice 提交以后，Carol 重做一遍事务，成功了 先不排队，撞上了再让一方重来，这叫乐观并发 按 MongoDB 的文档，它的多数读写都这样处理 要是 Carol 没开事务，只改这一份文档 她看不到错误，MongoDB 在服务端替她一遍遍重试 大约一秒后 Alice 提交，Carol 的修改也就成了 可要是 mongod 自己突然被杀了，还没写进文件的修改呢？

### crash · 09 出错怎么办 进程被强制结束，丢了什么？

检查点默认 60 秒才做一次 两次检查点之间，修改不一定已经进了数据文件 进程要是这时被杀，这些修改还找得回来吗？ 每一次修改，都同时记进一份*日志* 新的记录一条条接在日志后面，默认每 100 毫秒落一次盘 不过，回复「写好了」的时候，日志不一定已经落盘 写入时带上 j: true，j 指的就是日志 这样会等日志写进磁盘，再回复 不带的话，单机上写进内存就回复 还是刚写完 4096 人的时候，用一台单独的 mongod 检查点刚做完，Alice 改了年龄，这一笔加了 j: true 接着 Dave 注册，不带 j 两笔都回复成功后，mongod 被强制结束 日志文件里，检查点之后记着两笔 一笔是 Alice 的整份新文档，43 岁 一笔是 Dave：一个事务，三次写入，三棵树各一次 Dave 这一笔，也赶在结束之前写进了日志文件 重启时，WiredTiger 回到最后一个检查点 再把之后的日志，一条条重放 Alice 又是 43 岁，Dave 也在，4097 份一份不少 那不带 j 的写法，什么时候会丢？ 不带 j 写一笔，回复成功后立刻结束进程 这样试了两轮，每轮五次 一轮五次全丢了，另一轮只留下一次 换成 j: true，同样立刻结束，五次都在 不带 j，但隔 300 毫秒再结束，五次也都在 300 毫秒，已经超过了日志 100 毫秒一次的落盘间隔 这只是进程被强制结束 这种情况下，可能丢的只有最后一小段 已经回复了成功、还没写进日志文件的写入 断电又不同：写进了日志文件 还要看操作系统有没有把它真正写到磁盘上 要不要等这一下，写的时候自己选

### five · 10 五个问题 MongoDB 怎样回答，又换来了什么？

一个数据库引擎要回答的五个问题，MongoDB 是这样答的 数据怎么放：文档编成 BSON，按 RecordId 放进集合树 每个索引另是一棵树，最后都指回 RecordId 怎么找：在索引里拿到 RecordId，再回集合树取文档 改和删：内存里挂新版本、挂删除标记 检查点时，整页写到新地方，旧页不覆盖 怎么并发：读的人看快照，改同一份文档撞上了，一方重来 出错怎么办：回到最后一个检查点，重放日志 单机上不带 j，进程被杀时，最后一小段可能会丢 开头，Alice 的资料没建表就存了进去 不要表，换来了什么？ 集合默认不规定文档的样子 除了 _id，每份文档想有哪些字段，就有哪些 Erin 的标签、Frank 的地址，直接写进去，事先不用声明 代价是字段名跟着每份文档存一遍 4096 个人，_id、name、age 这几个名字 就存了 4096 遍 第一章说的另一件事，把数据分到很多台机器上 这一集没有讲；这里只看一台机器里的存储引擎 再往下一层，WiredTiger 其实只认一项一项的键和值 第一章说过，NoSQL 里有一类就叫键值数据库 每一项就是一个键、一个值，是更简单的一类数据库 它们常把数据放在内存里，读写都快 MongoDB 的数据住在磁盘上的树里，内存只是缓存 要是倒过来，数据全住在内存里，磁盘只用来保存呢？ 进程一死，内存里的数据又靠什么回来？ 这个系列的最后一站，一个更简单的数据库 Redis
