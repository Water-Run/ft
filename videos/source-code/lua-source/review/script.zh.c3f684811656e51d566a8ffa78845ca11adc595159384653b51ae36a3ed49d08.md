### intro · 01 认识 Lua

Lua 出自巴西的里约热内卢天主教大学 最早的版本在 1993 年就已投入使用 名字在葡萄牙语里是「月亮」 它的标志画的正是一颗行星，和环绕着它的月亮 从设计上说，Lua 首先是一个 C 库 用 C 写的程序可以把它链接进来 加载 Lua 脚本，调用其中的函数，再把结果取回去 这样调用 Lua 的程序，称为*宿主* 官网把 Lua 描述为一种可嵌入的脚本语言 并且提到，它常用在嵌入式系统和游戏里 官方发布包自带一个宿主，就是命令行程序 lua 它的源码 lua.c 只有 794 行 另一个程序 luac，能把编译出来的指令逐条列出 整个发布包压缩以后是 398643 字节，不到 400 KB 语言的全部实现、标准库和参考手册都在里面

### value · 03 一个值

同一个变量 x，先存 1，再存字符串 one，最后存一张表 type 依次报出 number、string、table 变量本身没有类型，类型属于值 数字还分两种 math.type(3) 是 integer math.type(3.0) 是 float 可 3 == 3.0 又成立 比较时，整数和浮点数按数值来比 最大的整数加 1，变成了最小的整数 2 的 53 次方加 1，结果和原数相等 乘方算出的总是浮点数 前一个是 64 位整数的回绕 后一个是浮点数的精度用完了 两种数在解释器里确实是两样东西 这就给解释器提出了要求 一个变量、一个表的格子，事先不知道会放进什么 存放值的每一个位置，都得放得下任何一种值 还要能说明此刻放的是哪一种 lobject.h 把一个值拆成两部分 一部分是 8 字节的联合体 Value 联合体是 C 的一种类型，几个成员共用同一块内存 同一时刻只用其中一个 共用这 8 个字节的，有指针、整数和浮点数 另一部分是 1 字节的类型标签 两部分合在一起称为*标签值*，类型名是 TValue 在 64 位的 Windows 上，一个 TValue 占 16 字节 其中 7 字节是为对齐留下的空隙 标签字节从第 0 位数起，0 到 3 位记录基本类型 Lua 的基本类型共有 8 种 nil、布尔、数字、字符串、函数、userdata、线程和表 第 4、5 位区分同一类型下的变体 整数和浮点数，就是数字的两个变体 math.type 分得出 integer 和 float 靠的就是这个变体 第 6 位表明这个值是否归垃圾回收器管理 数字直接存在这 8 个字节里，不必另外分配内存 布尔和 nil 更简单，只靠标签就能区分 字符串、表、函数这类对象大小不定 只能在堆上单独分配 TValue 里存的是指向它们的指针 x 从 1 换成字符串、再换成表 变的只是这 16 个字节 标签换了，内容从一个整数换成了一个指针 堆上的这些对象，开头都是同样的三个字段 tt 记录类型，marked 供垃圾回收使用 next 把新建的对象一个个挂到回收器的链表上 字符串在 Lua 程序里用得极多 字段名、全局变量的名字，都是字符串 如果同样的内容每出现一次就新建一份 比较两个字符串就只能逐个字节地比 lstring.c 对不超过 40 字节的短字符串另有安排 创建之前，先到一张全局的字符串表里查找 已经有内容相同的，就直接复用那一个对象 这种做法称为字符串*驻留* 驻留之后，内容相同的两个短字符串必定是同一个对象 比较时只需比较指针 短字符串在创建时还会算好自己的哈希值，存在对象里 查表时直接拿来用 更长的字符串不驻留 在 C 程序里，用两块独立的内存各写一次 label 交给 Lua 创建字符串，得到的是同一个对象 两次写入 41 字节的相同内容，得到的则是两个对象 值有了表示，接下来是一段源码怎样被读进来

### lex · 04 读入与记号

把 local while = 1 交给 load，它拒绝编译 报错说，在 while 附近，期望的是一个名字 local global = 5 却能正常运行，打印出 5 1，接一段注释，再加 2，结果是 3 这几行的命运，在第一道工序里就定下了 加载时，库先看输入的第一个字节 如果是 0x1B，说明这是 luac 预先编译好的文件 交给 lundump 读取 否则就当作源码文本，交给语法分析器 对编译器来说，源码起初只是一串字符 l、o、c、a、l、空格、w…… 语法分析需要的却是更大的单位 比如关键字 local、一个名字、一个等号、一个数字 把字符流切分成这样的单位，称为*词法分析* 切出的每个单位，称为一个*记号* llex.c 里，一个记号由两部分组成 一个表示种类的整数，加上附带的内容 名字和字符串附带一个指向字符串对象的指针 数字附带它的数值 切分本身由一个大的 switch 完成，看当前字符决定怎样读 空白和换行直接跳过 两个连续的减号开始注释 后面紧跟方括号时，整段长注释一起跳过 所以 1、注释、加 2，切完只剩 1、加号、2 三个记号 引号开始字符串，数字开始数值，字母开始一个名字 0x10 读成整数 16，1e2 读成浮点数 100.0 7 // 2 是整除，得整数 3 读名字时要处理一个问题 local、function、while 这些保留字也由字母组成 必须和普通的名字区分开 最直接的做法，是拿每个名字去查一张保留字表 Lua 没有这样做，它借用了字符串的驻留 每个字符串对象里，有一个叫 extra 的字节 解释器启动时，先把 23 个保留字全部创建成字符串 并在它们的 extra 里写下各自的编号 之后每读到一个名字，照常为它创建字符串 如果它恰好是保留字，驻留会交回启动时建好的那个对象 所以判断是不是保留字，只要看 extra 是否为 0 编号从 1 排起，最后一个 while 是 23 普通名字的 extra 都是 0 local 后面跟着 while 分析器要的是一个名字，拿到的却是保留字，于是报错 global 是 5.5 新增的关键字，用来声明全局变量 手册把它列为保留字 不过发布包的默认配置打开了一个兼容选项 字符串 global 的 extra 是 0，仍是普通的名字 只有出现在语句开头、后面紧跟名字之类的记号时 分析器才把它当作声明 语法分析器每次向 llex 要一个记号 必要时可以再往后多看一个 判断 global 是不是声明，用的正是多看的这一个 过去把 global 当变量名的程序，因此照样能运行 记号切出来以后，要变成可以执行的指令

### parse · 05 边读边生成

三行程序：a、b、c 分别是 1、2、3 a 等于 b 加 c 乘 2，d 等于 2 乘 3 luac 列出它编译出来的指令，一共 10 条 d 那一行只剩一条：把 6 放进寄存器 2 乘 3 在编译时就算完了 a 那一行，乘法排在加法前面 加法的结果直接写进 a，中间没有多余的搬运 这些都是编译器一边读、一边决定的 不少编译器拿到记号以后，先建一棵完整的语法树 再遍历这棵树生成代码 Lua 的编译器没有这样做 它在读源码的同时，就把指令生成了出来 先看「读」的部分 语法本身是层层嵌套的 语句里有表达式，表达式里又有更小的表达式 lparser.c 为每一种语法结构写了一个函数 结构怎样嵌套，这些函数就怎样互相调用 比如读一条赋值语句，statement 先调用处理赋值的函数 后者再调用 expr，去读等号右边 这种按语法结构逐层调用的写法，称为*递归下降* Lua 的不同之处在于，这些函数每认出一部分 就当场调用 lcode.c，生成对应的指令 源码读完一遍，指令也就全部生成好了 生成的指令按函数存放 源码里的每一个函数，编译后成为一个*函数原型* 类型名是 Proto 原型里存着这个函数的指令、常量 以及嵌套在它里面的函数的原型 整个文件也当作一个函数来编译，称为主函数 这三行没有定义别的函数，只有一个主函数 生成指令之前，得先定下一件事 局部变量和计算的中间结果放在哪里 Lua 把它们放在解释器自己管理的一块栈上 它和 C 程序的调用栈不是一回事 每次调用函数，都在栈上分到连续的一段格子 编译时就要决定每个值放在第几格 这些格子在 Lua 里称为*寄存器* 但它们只是栈上的编号，和 CPU 的寄存器无关 局部变量按声明的顺序占用寄存器 a、b、c 是 0、1、2 号 前三条 LOADI，把 1、2、3 依次放进去 编译器为正在编译的函数记着进度 已经生成了几条指令、用了哪些常量 下一个空闲的寄存器是几号，此刻是 3 号 接着读 a 等于 b 加 c 乘 2 读到 a，分析器在当前函数里找到这个局部变量，在 0 号 这时还不知道 a 是要读还是要写 所以先不生成指令 只在一个 expdesc 结构里记下：0 号寄存器里的局部变量 expdesc 描述的是一个还没有落地的表达式 等用途确定了，再决定生成哪条指令 读到等号，说明 a 是赋值的目标，先放在一边 右边先是 b，在 1 号寄存器，同样记成 expdesc 它本来就在寄存器里，不需要任何指令 接着是加号，加号后面是 c，再后面是乘号 lparser.c 里有一张优先级表，加法是 10，乘法是 11 分析器看到后面的乘号优先级更高 就先把 c 乘 2 读完 c 在 2 号寄存器，2 是常量 于是生成 MULK：2 号乘常量 2 积放进下一个空闲的寄存器，也就是 3 号 后面紧跟一条 MMBINK 只在乘法遇到不是数字的值时才执行 乘法完成，回到加法 左边 b 在 1 号，右边的积在 3 号 生成 ADD，后面同样跟一条 MMBIN 加法的结果放到哪里，此刻还是一个 expdesc 回到等号左边，目标是 0 号寄存器里的 a 编译器就把 ADD 的结果直接定在 0 号 最终的指令是 ADD 0 1 3：1 号加 3 号，写进 0 号 一条语句结束，用过的临时寄存器全部释放 3 号又空了出来 下一行 local d 等于 2 乘 3 两边都是常量，编译器直接算出 6 d 是第四个局部变量，占 3 号 于是只有一条 LOADI 3 6 第一条 VARARGPREP，是因为主函数总接受可变个数的参数 最后一条 RETURN 是主函数的结尾 三行源码，一共 10 条指令

### code · 06 指令

刚才那条 ADD 0 1 3，在内存里是一个 32 位的整数 十六进制写作 03010022 这样的指令，通常称为*字节码* 最低 7 位是操作码，表示做什么 其余 25 位按不同的格式，切分成几个操作数 最常用的格式是 iABC A 占 8 位，接着是 1 位的标志 k 然后 B 和 C 各占 8 位 拆开 03010022：低 7 位是 34，正是 ADD 的操作码 往上 8 位是 A，等于 0 k 是 0，B 是 1，C 是 3 另一种格式 iABx，把 k、B、C 合成一个 17 位的操作数 用来存放常量的编号 格式 isJ 则把 25 位全部用来存放跳转距离 5.5.1 一共定义了 85 种操作码 A、B、C 大多直接就是寄存器的编号 一条指令本身就写明了读哪几个寄存器、结果写到哪里 这样设计的解释器，称为*寄存器式虚拟机* Lua 并不是一开始就这样 把 a = b + c 交给 Lua 4.0 的编译器 得到的是另一种指令 它先把 b 和 c 依次压到栈顶 ADD 不带任何操作数 它弹出栈顶的两个值相加，再把结果压回去 最后再弹出来，存进 a 操作数隐含在栈顶的这种设计，称为*栈式虚拟机* 从 5.0 起，同一句只需要一条带三个操作数的 ADD 指令的条数少了，每条指令带的操作数多了 到了 5.4，ADD 后面又多出一条 MMBIN ADD 只负责数字相加 两个操作数都是数字时，ADD 做完就跳过后面那一条 只有遇到不是数字的操作数，执行才会落到 MMBIN 由它去查有没有另外规定过加法该怎么做

### vm · 07 解释循环

字符串 "3.0" 加 1，这几个版本都得 4.0 字符串 "10" 加 1 呢 在 Lua 5.5.1 里，结果是整数 11 在 Lua 5.3 里，结果却是浮点数 11.0 一张空表加 1，这几个版本都报错：不能对表做算术 差别出在执行指令的那段代码 执行指令的，是 lvm.c 里的函数 luaV_execute lua.c 调用主函数时，执行就进入了这个函数 它的主体是一个循环 一个指针 pc 指向下一条要执行的指令 取出这条指令，pc 前进一格 再按低 7 位的操作码，跳到对应的处理代码 处理完毕，回到循环开头取下一条 怎样跳到对应的处理代码，有两种写法 用 GCC 及兼容的编译器时，它用一张地址表直接跳转 其余的编译器则用 switch 语句 所有指令操作的都是同一样东西 栈上属于当前函数的那一段寄存器 base 指向当前函数的 0 号寄存器 指令里的 A 是几，就从 base 往后数几格 以 ADD 的处理代码为例 它先检查两个操作数的标签 如果都是整数，就做整数加法 结果写入 A 号寄存器，标签设为整数 然后 pc 再前进一格，跳过后面的 MMBIN 如果不都是整数，但都是数字 就按浮点数相加，同样跳过 MMBIN 这两条快路只认数字，字符串一概不碰 "10" 是字符串，快路不成立，执行落到 MMBIN MMBIN 去找这两个值有没有另外规定过加法 先查第一个操作数 "10"，它是字符串 字符串库给所有字符串都设好了这样的规定 它把 "10" 转成整数 10，再和 1 相加，得到整数 11 Lua 5.3 走的是另一条路 它的 ADD 自己就会把字符串转成数字 转出来的是浮点数，所以得到 11.0 到了 5.4，ADD 不再转换字符串，这件事交给了字符串库 ADD 只管数字，少见的情况交给后面的 MMBIN 一张空表既不是数字，也没有这样的规定，于是报错 读字段的指令也是这样 先在表里直接按键查找 查不到，才转入通用的处理 常见的情况先走快路，不成再转入通用的处理 lvm.c 里的许多指令都是这样写的

### call · 08 调用

### coro · 13 协程

### gc · 14 回收

一个函数建了两张互相引用的表，其中一张存了十万个整数 创建它们的函数返回以后，内存多出约 1152 KB 做一次完整的回收，多出的部分回到 0 两张表仍在互相引用，却都被回收了 Lua 程序从不手动释放内存 手册的说法是，Lua 自动管理内存 由垃圾回收器回收所有死去的对象 所谓死去，是指回收器能够确定 程序以后再也不会访问到它 回收器从几个*根*出发，主要是主线程和注册表 主线程是宿主最初建立的那份 lua_State 它的栈上，放着正在使用的值 注册表是解释器内部的一张表，全局表就放在里面 沿着引用能走到的对象都还活着，走不到的就是垃圾 函数返回以后，从根出发已经走不到这两张表 它们彼此之间的引用，不起作用 程序里用来观察的 watch，元表里写了 __mode 这样的表称为*弱表*，它的引用不妨碍回收 所以回收之后，watch 里的那一项也空了 判断能否走到，用的是三种颜色 白色表示还没有访问到 灰色表示已经访问到，但它引用的对象还没检查 黑色表示它和它直接引用的对象，都已经检查过 一轮开始时，所有对象都是白色，根被涂成灰色 之后每一步取出一个灰色对象 把它引用的白色对象涂灰，再把它自己涂黑 灰色对象处理完时，仍是白色的就是走不到的 最后沿着对象链表清扫一遍，释放这些白色对象 设置了 __gc 元方法的对象例外 回收器先调用它的 __gc，通常到下一轮才释放 这样完整地走一遍，可能要处理大量对象 如果一口气做完，程序就得停下来等 所以 lua_newstate 建立解释器状态时 回收器处于*增量*模式 回收工作被切成小步，与程序交替进行 程序每分配一定数量的内存，回收器就向前推进一小步 交替进行会带来一个问题 假设回收器已经把表 A 涂黑，认为它检查完了 程序这时执行 A.x = B，而 B 还是白色 B 现在只被黑色的 A 引用，A 又不会再被检查 到最后 B 仍是白色，会被当作垃圾释放 所以程序往对象里写入引用时，要经过*写屏障* 黑色对象一旦指向白色对象，写屏障就当场补救 对表，是把这张表重新涂灰，稍后再检查一遍 对闭包、上值这类对象，是直接把被指向的对象涂灰 标记的最后有一个不能拆分的原子阶段，负责收尾 清扫同样分步进行，期间程序还在不断创建新对象 新对象是白色的，但它们并不是垃圾 为此回收器准备了两种白色 原子阶段结束时，「当前白色」切换为另一种 新对象涂上新的当前白色，清扫只释放带旧白色的对象 增量模式每一轮都要把所有活着的对象标记一遍 一直活着的对象，每一轮都被重复检查 另一种做法基于一个假设：多数对象死得早 那么平时只检查新近创建的对象就够了 这就是*分代*回收 5.2 曾把它作为实验特性，5.3 又去掉了 5.4 重新加入了分代模式 对象带一个年龄，分为新建的、活过一轮的和老的 平时只做遍历新对象的小回收 老对象占用的内存增长到一定程度 再做一次遍历全部对象的大回收 官方命令行程序 lua 启动时，会主动切换到分代模式 5.5 又让分代模式下的大回收也能分步完成 这些对象都在 Lua 一侧 用 C 写的宿主，又怎样拿到它们、把值交给它们

### capi · 15 与 C 的边界

Lua 首先是给 C 程序嵌入用的 宿主要能调用 Lua 的函数 Lua 也要能调用宿主用 C 写的函数 这就需要在两种语言之间传递值 难点在于，C 的变量有固定的类型，Lua 的值没有 而 TValue 是解释器的内部结构，并不交给宿主 C API 用一个*虚拟栈*来传值 宿主把值压进栈，再按位置从栈里读出来 一个最小的宿主 先把一个 C 函数 c_add 注册为全局变量 再加载 return c_add(19, 23)，这时栈上多了一个函数 调用这个函数，进入 c_add 时 它看到的栈上正好有两个参数 c_add 读出 19 和 23，把 42 压进栈 然后返回 1，表示有 1 个返回值 回到宿主，栈上只剩下这个 42 每个 C 函数看到的，只是属于自己的那一段栈 位置从 1 数起，1 号就是第一个参数 这和寄存器从 0 数起不同 Lua 调用 C 写的函数，走的就是这条路 标准库也是这样写成的 print、pcall 和 coroutine.resume 都是普通的 C 函数 它们通过同一套 API 读写 Lua 的值，从不接触内部结构 加载哪些库，由宿主决定 require 加载过的模块 会缓存在 package.loaded 里 再次 require 时直接返回缓存 lua.c 的 main，也只是这套 API 的一个使用者 它建立状态，在保护模式下调用 pmain pmain 打开标准库，把回收器切换到分代模式 然后加载并运行脚本 最后由 lua_close 释放所有对象
