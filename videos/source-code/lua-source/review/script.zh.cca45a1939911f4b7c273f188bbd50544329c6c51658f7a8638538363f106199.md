### map · 01 源码地图

### value · 02 一个值

Lua 的变量没有类型，类型属于值 同一个变量，可以先放一个整数，再放一个字符串 所以解释器里每个存放值的格子，都要放得下任何一种值 还要能看出此刻放的是哪一种 lobject.h 把一个值分成两部分 一部分是 8 个字节的联合体，放内容 指针、整数、浮点数，共用这 8 个字节 另一部分是 1 个字节的标签，记着类型 这样一对，叫作*标签值*，类型名是 TValue 在这台 64 位机器上，一个 TValue 占 16 个字节 多出来的 7 个字节，是对齐留下的空隙 标签的低 4 位是基本类型 语言里一共 8 种：nil、布尔、数字、字符串 函数、userdata、线程和表 第 4、5 位区分同一种类型下的变体 比如数字分整数和浮点数，标签不同 第 6 位标出这个值是否需要回收 整数 40 直接存进那 8 个字节，不用另外分配内存 nil 和布尔，只看标签就够了 字符串、表、函数，8 个字节放不下 它们在堆上单独分配，那 8 个字节里只存一个指针 堆上的这些对象，开头都是同样的三个字段 next 指向下一个对象，新建的对象由它串进一条链表 tt 是类型，marked 留给垃圾回收 这条链表，讲回收的时候还会用到 字符串还有一个特别的处理 同样的短字符串会在程序里反复出现，比如字段名 value 如果每次都新建一份，比较两个字符串只能逐字节比 lstring.c 的做法是：创建短字符串之前 先查一张全局的哈希表 已经有内容相同的，就直接用那一个，不再新建 这叫*驻留* 驻留以后，两个短字符串内容相同，就一定是同一个对象 比较它们，只要比较指针 「短」的界线是 40 个字节 更长的字符串不驻留，每次都新建对象 用两块独立的内存各写一次 label，创建出的是同一个对象 两次创建 41 个字节的相同内容，得到两个对象 值的表示就是这些。下面回到主线：脚本怎样被读进来

### lex · 03 读入与记号

lua.c 把脚本文件交给库加载 加载先看第一个字节 如果是 0x1B，这是 luac 预先编译好的文件 交给 lundump 去读 否则就是源码文本，交给语法分析器 第 2 行是一串字符：l、o、c、a、l、空格、f…… 语法分析关心的不是单个字符 而是 local、名字、等号、数字这样有意义的单位 把字符切成这样的单位，叫*词法分析* 切出来的每个单位，叫一个*记号* llex.c 里，这件事由一个 switch 完成 看当前字符：空格和换行，跳过 两个减号开始注释，一直跳到行尾 引号开始字符串，数字开始数值 字母开始一个名字 读名字时有一个问题 local、function、end 也由字母组成，它们是保留字 必须和普通的名字分开 一种做法，是拿名字去查一张保留字表 Lua 借用了刚才的驻留 解释器启动时，先把 23 个保留字都创建成字符串 在每个字符串的 extra 字节里，写下它的序号 读到一个名字，照常创建字符串 如果它是保留字，驻留会交回启动时建好的那个对象 看一眼 extra：不是 0，就是保留字 while 排在保留字表的最后，它的 extra 是 23 5.5 新增了 global 声明 但发布包默认仍把 global 当作普通名字 它的 extra 是 0 只有在语句开头、后面紧跟名字这类记号时，才算声明 这样，默认构建下，把 global 当变量名的旧程序仍能运行 以计数器里的这一行为例 它被切成 9 个记号 名字 state、点、名字 value、等号 又一遍 state、点、value，加号，名字 delta 语法分析器每次向 llex 要一个记号 需要时，可以再往后多看一个 下一步，这些记号怎样变成指令

### code · 05 指令

每条指令是一个 32 位的整数 这样的指令，也叫*字节码* 最低 7 位是操作码，说明做什么 其余 25 位，按格式切成几个操作数 最常用的格式叫 iABC A 占 8 位，一个标志位 k，B 和 C 各占 8 位 内层函数里那条 ADD，编码是 0x000100A2 低 7 位是 34，正是 ADD 的操作码 往上 8 位是 A，等于 1 再往上，k 是 0，B 是 1，C 是 0 合起来：1 号寄存器加 0 号，结果写进 1 号 另一种格式 iABx，把 k、B、C 合成一个 17 位的操作数 用来放常量的编号 格式 isJ 留出 25 位，放跳转的距离 5.5.1 一共有 85 种操作码 A、B、C 大多是寄存器的编号 一条指令自己就说清楚了：用哪几个寄存器，结果放到哪里 这种设计叫*寄存器式虚拟机* Lua 并不是一直这样 同一句 a = b + c，交给 Lua 4.0 的编译器 它先把 b 压到栈顶，再把 c 压到栈顶 ADD 不带操作数：弹出两个，相加，把结果压回去 最后再弹出来，存进 a 操作数都隐含在栈顶，这是*栈式虚拟机* 从 5.0 开始，同一句只要一条 ADD 指令条数少了，每条指令要解出的字段多了 到 5.4，ADD 后面多出一条 MMBIN ADD 只处理数字相加 两个操作数都是数字，ADD 做完就跳过下一条 不是数字时，执行落到 MMBIN，由它去找元方法 计数器整段运行下来，内层函数的 ADD 执行了 3 次 MMBIN 一次也没有执行 指令有了，接下来看它们怎样被执行

### vm · 06 解释循环

lua.c 调用主函数以后 执行进入 lvm.c 里的 luaV_execute 它的主体是一个循环 一个指针 pc 指向下一条要执行的指令 取出这条指令，pc 前进一格 看低 7 位的操作码，跳到对应的处理代码 处理完，回到循环开头，取下一条 怎样跳到处理代码，取决于编译 Lua 的 C 编译器 用 GCC 时，它用一张地址表直接跳转 其他编译器，用 switch 本片用的 5.5.1 由 GCC 编译，走地址表 循环里的每条指令，操作的是同一样东西 栈上的一段寄存器 base 指向当前函数的 0 号寄存器 指令里的 A 是几，就是从 base 往后数几格 看 ADD 的处理代码 先看两个格子的标签：都是整数，就做整数加法 结果写进 A 号格子，标签设为整数 然后 pc 再前进一格，跳过后面的 MMBIN 不都是整数、但都能当浮点数，就做浮点加法，同样跳过 两样都不行，才不跳过，交给 MMBIN 把计数器的第一次调用，逐条执行一遍 0 号寄存器里是参数 2 GETTABUP 先从上值拿到 state 表 键 value 是短字符串，直接在表里查到 40，放进 1 号 ADD 算出 42，写回 1 号 SETTABUP 把 42 写回表里 GETTABUP 再取出 42，RETURN1 把它返回 执行 RETURN1 之前，1 号寄存器里正是整数 42 GETTABUP 也分快慢两条路 快路：在表里直接按键查找 查不到，才进入慢路，去看这张表有没有元表 先试最常见的情况，不成再走通用的路 lvm.c 里很多指令都是这样写的 这次执行，从主函数里的一次调用开始。调用是怎样发生的

### call · 07 调用

程序第 16 行，一行里有三次调用 先看 next_value(2) 主函数把要调用的函数放进一个寄存器 参数紧接着放在它后面 CALL 指令写明：函数在几号寄存器 带几个参数，要几个结果 ldo.c 的 luaD_precall 先看被调用的是什么 如果是 C 函数，当场调用，结果留在栈上 如果是 Lua 函数，就要记下几件事 它的寄存器从哪一格开始，用到哪一格为止 执行到了哪一条指令 记这些信息的结构，叫*调用帧* 它的类型叫 CallInfo 新函数的 0 号寄存器，紧挨在函数本身后面 参数本来就放在那里，不需要搬动 这一刻的栈是这样的 主函数的寄存器，从第 3 格开始 next_value 在第 8 格，也就是主函数的 5 号寄存器 它自己的 0 号寄存器在第 9 格，放着参数 2 调用方的两个格子，直接成了被调用方的函数和参数 一个个 CallInfo 连成一条链 这一刻有三层：内层函数、主函数，最底下是宿主 新帧建好以后，luaV_execute 并不递归调用自己 它把当前帧换成新帧，跳回循环开头，接着取指令 返回时，RETURN1 把结果放到原来函数所在的那一格 再把当前帧换回上一层，继续执行调用方的下一条指令 所以 Lua 函数调用 Lua 函数，不会让 C 的栈变深 一个 Lua 函数非尾递归 100000 层，可以正常结束 经过 C 函数就不同了，比如 pcall C 函数必须在 C 的栈上真正调用一次 所以 C 调用的嵌套层数设了上限，200 一个函数经由 pcall 调用自己，到第 198 层就报错 C stack overflow 还有一种调用，连新帧都不用建 return f(x) 这样的调用，当前函数之后已无事可做 这叫*尾调用* TAILCALL 指令让被调用的函数直接用掉当前的帧 协程体的最后一句 return next_value(1) 编译出来就是 TAILCALL 函数一返回，它的帧就结束了 那么，闭包怎样留住外层函数的变量

### closure · 08 闭包与上值

### table · 09 表

### meta · 10 元表

### error · 11 错误

第 26 行，pcall 调用一个函数，那个函数调用 error 出错的地方，可能已经在好几层调用之下 控制要直接回到 pcall，中间各层都不再继续 这几层里有 C 函数，而 C 语言没有异常 ldo.c 用的是 C 标准库里的两个函数 setjmp 和 longjmp setjmp 记下此刻 C 程序执行到的位置 longjmp 从更深的地方，直接跳回这个位置 pcall 最终调用 luaD_rawrunprotected 它在 C 的栈上放一个跳转点，用 setjmp 记下位置 把这个跳转点挂到当前线程上，链接到上一个跳转点 然后才调用目标函数 error 最终调用 luaD_throw 它取出最近挂上的跳转点，执行 longjmp C 的执行回到 setjmp 那里，这一次带着错误状态 跳回来以后，Lua 这边也要恢复 调用帧恢复到 pcall 开始前的那一层 这期间打开的上值，要一一关闭 错误对象被放到栈上原来的位置 pcall 返回 false 以及错误对象 counter-error 错误对象可以是任何值，不一定是字符串 用 C++ 编译 Lua 时，同样的位置换成 try 和 throw 5.4 加入了*待关闭变量* 标为 close 的局部变量离开作用域时，调用它的 __close 正常离开时调用；出错时，就在刚才这条恢复的路上调用 longjmp 一下跳过了中间所有的 C 函数 协程的暂停，用的也是这一招

### coro · 12 协程

第 18 行创建了一个协程 第一次 resume，它运行到 yield，交出 45，然后暂停 第二次 resume，它从暂停的地方接着运行 暂停时要保存：局部变量，调用到了哪一层 每一层执行到了哪条指令 Lua 让每个协程有自己的一份 lua_State 里面有自己的栈，有自己的 CallInfo 链 全局表、字符串表、回收器 放在另一个结构 global_State 里 所有协程共用这一份 协程不是操作系统的线程，同一时刻只有一个在运行 resume 把参数搬到协程的栈上，在保护模式下运行它 也就是说，resume 也设下了一个跳转点 协程体运行到 coroutine.yield yield 是一个 C 函数 它把协程的状态设为暂停，记下交出了几个值 然后调用 luaD_throw，和抛出错误是同一个函数 longjmp 回到 resume 设下的跳转点 C 栈上，resume 以下的部分全部丢弃 协程自己的栈和 CallInfo 链，原样留着 要保存的，正好就是这些 resume 返回 true 和 45，状态是 suspended 第二次 resume，看到协程正处于暂停 先把那次 yield 调用收尾 resume 的参数，成为 yield 的返回值 再沿着 CallInfo 链，继续执行协程体 协程体调用 next_value(1)，得到 46，返回 resume 返回 true 和 46，状态变成 dead 这个做法有一个限制：yield 时，C 栈被丢弃了 如果协程中途调用过一个普通的 C 函数 这个 C 函数执行到一半的状态，就没有了 这时 yield 会报错：不能跨越 C 调用的边界让出 5.2 起，C 函数可以登记一个续接函数 协程恢复时，由 Lua 调用它 pcall 就是这样写的 所以在协程里，pcall 内部也能 yield 协程、闭包、表，都在不断创建对象 这些对象由谁来释放

### gc · 13 回收

程序运行时一直在创建对象：表、闭包、上值、协程 一个对象什么时候可以释放 当程序再也访问不到它的时候 回收器从几个*根*出发：主线程、注册表、全局元表 全局表就在注册表里，栈上的值属于线程 沿着引用能走到的对象，都还活着 走不到的，就是垃圾 两个对象互相引用，只要从根走不到，照样回收 回收器给对象涂上三种颜色 白色：还没有访问到 灰色：访问到了，但它引用的对象还没检查 黑色：它自己和它直接引用的对象，都检查过了 一开始，对象都是白色，根被涂成灰色 每一步，取一个灰色对象，把它引用的白色对象涂灰 它自己涂黑 灰色处理完时，仍是白色的，就是走不到的 最后沿着对象链表清扫一遍，释放白色对象 这样一遍，可能要处理大量对象 一口气做完，程序就得停下来等 lua_newstate 建立状态时，回收器处于*增量*模式 回收的工作被切成小步，和程序交替进行 程序每分配一定数量的内存，就做一小步 交替进行，带来一个问题 回收器已经把表 A 涂黑，认为它检查完了 程序这时执行 A.x = B，而 B 还是白色 B 现在只被黑色的 A 引用，而 A 不会再被检查 到最后 B 仍是白色，会被当成垃圾释放 所以往对象里写引用时，要经过*写屏障* 黑色对象一旦指向了白色对象，就当场补救 对表，把这张表重新涂灰，稍后再检查一遍 对闭包、上值这类对象，把被指向的对象直接涂灰 标记的最后，有一个不能拆开的原子阶段，处理收尾工作 清扫也是分步进行的，期间程序还在创建新对象 新对象是白色，可它们不是垃圾 所以白色有两种 原子阶段结束时，「当前白色」换成另一种 新对象涂的是新的当前白色，清扫只释放旧的那一种 增量模式的每一轮，都要把所有活着的对象标记一遍 一直活着的对象，每一轮都要再查一次 5.4 加入了*分代*模式 对象带一个年龄：新建的，活过一轮的，老的 平时做小回收，只遍历新近创建的对象 老对象的内存涨到一定程度 再做一次遍历全部对象的大回收 官方的命令行程序 lua 启动时，主动切换到分代模式 5.5 让分代模式下的大回收，也能分步完成 元表的 __mode 可以把一张表声明为*弱表* 只被弱表引用的对象，照样会被回收 回收器管的是 Lua 自己的对象 宿主和 Lua 之间的值，又是怎样传递的

### capi · 14 与 C 的边界

C 的变量有固定的类型，Lua 的值没有 TValue 是内部结构，不交给宿主 C API 用一个*虚拟栈*来传值 宿主把值压进栈，再按位置从栈里读出来 一个最小的宿主 先把一个 C 函数 c_add 注册为全局变量 加载 return c_add(19, 23)，栈上多了一个函数 调用它。进入 c_add 时，它看到的栈上有两个参数 读出 19 和 23，把 42 压进栈，返回 1，表示有 1 个结果 回到宿主，栈上只剩这个 42 每个 C 函数看到的，只是自己这一段栈 1 号位置就是第一个参数 这就是 luaD_precall 里 C 函数的那条路 标准库也是这样写的 print、pcall、coroutine.resume 都是普通的 C 函数 它们通过这套 API 读写 Lua 的值，不碰内部结构 加载哪些库，由宿主决定 require 加载过的模块 缓存在 package.loaded 里 再次 require，直接返回缓存 lua.c 的 main，也只是这套 API 的一个使用者 它建立状态，在保护模式下调用 pmain pmain 打开标准库，切换到分代回收，加载并运行脚本 最后 lua_close 释放所有对象
