### intro · 01 认识 Lua

Lua 来自巴西，出自里约热内卢天主教大学 1993 年，最早的版本就已经投入使用 Lua 在葡萄牙语里是「月亮」的意思 它的标志画的正是一颗行星，和绕着它的月亮 从设计上说，Lua 首先是一个 C 库 C 程序把它链接进来，就能加载 Lua 脚本 调用脚本里的函数，再把结果取回去 这样把 Lua 嵌进去用的程序，叫作*宿主* 官网对 Lua 的定位，是一种可嵌入的脚本语言 说它常用在嵌入式系统和游戏里 官方发布包里自带一个宿主，就是命令行程序 lua 它的源码 lua.c 只有 794 行 另一个程序 luac，能把编译出的指令逐条列出来 整个发布包压缩以后不到 400 KB 语言的全部实现、标准库和参考手册，都在里面

### value · 03 一个值

同一个变量 x，先存 1，再存字符串 one，最后存一张表 type 依次报出 number、string、table 变量本身没有类型，类型跟着值走 数字还分两种 math.type(3) 是 integer math.type(3.0) 是 float 可是 3 == 3.0 又成立，比较时按数值来比 再看两种到了头的情况 最大的整数加 1，变成了最小的整数 这是 64 位整数的回绕 2 的 53 次方加 1，结果和原数相等 乘方算出的总是浮点数 这回是浮点数的精度用完了 整数和浮点数，在解释器里确实是两样东西 这就给解释器出了一道题 一个变量、表里的一个格子，事先不知道会放进什么 每个存放值的位置，都得放得下任何一种值 还得说清楚，此刻放的是哪一种 lobject.h 的做法，是把一个值拆成两部分 一部分是 8 字节的联合体 Value 指针、整数、浮点数共用这 8 个字节 同一时刻只用其中一种 另一部分是 1 字节的类型标签 两部分合起来，就是*标签值*，类型名 TValue 在 64 位的 Windows 上，一个 TValue 占 16 字节 其中 7 字节是为了对齐留下的空隙 标签这个字节，从第 0 位数起 0 到 3 位记基本类型 手册里的基本类型有 8 种 nil、布尔、数字、字符串、函数、表 userdata，用来在 Lua 里存放 C 的数据 还有线程，代表一段能停下、能恢复的执行过程 内部的编号却有 9 个 因为 userdata 又分轻量和完整两种，各占一个编号 第 4、5 位区分同一类型下的变体 整数和浮点数，就是数字的两个变体 math.type 分得出 integer 和 float，看的就是它 第 6 位表示这个值归不归垃圾回收器管 数字直接存在那 8 个字节里，不用另外分配内存 布尔和 nil 更简单，只靠标签就能区分 字符串、表这类对象，大小不定 只能在堆上单独分配 TValue 里存的，是指向它们的指针 x 从 1 换成字符串、再换成表 变的只是这 16 个字节 标签换了，内容从一个整数换成了一个指针 堆上的这些对象，开头都是同样三个字段 tt 记类型，marked 留给垃圾回收用 next 把新建的对象一个个挂到回收器的链表上 字符串在 Lua 程序里用得极多 字段名、全局变量的名字，都是字符串 要是同样的内容每出现一次就新建一份 比较两个字符串，就只能一个字节一个字节地比 lstring.c 对不超过 40 字节的短字符串另有安排 创建之前，先到一张全局的字符串表里查一查 已经有内容相同的，就直接用那一个对象 这叫字符串*驻留* 驻留以后，内容相同的短字符串一定是同一个对象 比较时只要比指针 短字符串在创建时还会算好自己的哈希值，存在对象里 拿来查表时直接用 超过 40 字节的长字符串不驻留 从两块不同的内存，各创建一次字符串 label 拿到的是同一个对象 换成两段 41 字节的相同内容，就成了两个对象

### lex · 04 读入与记号

load 能把一段字符串当作源码来编译 把 local while = 1 交给它，它拒绝了 报错说，在 while 附近，这里应该是一个名字 换成 local global = 5，却能正常运行，打印出 5 还有一行：1，接一段注释，再加 2，结果是 3 这三行能不能过、怎样过，在读入字符时就定下了 加载时，库先看输入的第一个字节 如果是 0x1B，说明这是 luac 预先编译好的文件 交给 lundump 去读 否则就当作源码文本来编译 对编译器来说，源码起初只是一串字符 l、o、c、a、l、空格、w…… 可分析语法时，要的是更大的单位 比如关键字 local、一个名字、一个等号、一个数字 把字符流切成这样的单位，就是*词法分析* 切出来的每一个单位，叫一个*记号* llex.c 里，一个记号由两部分组成 一个表示种类的整数，加上附带的内容 名字和字符串，附带一个指向字符串对象的指针 数字附带它的数值 切分本身是一个大的 switch，看当前字符决定怎么读 空白和换行直接跳过 两个连续的减号开始注释 后面紧跟方括号，就把整段长注释一起跳过 所以那行 1、注释、加 2，切完只剩三个记号 1、加号、2 引号开始字符串，数字开始数值，字母开始一个名字 0x10 读成整数 16，1e2 读成浮点数 100.0 7 // 2 是整除，得整数 3 读名字时有个麻烦 local、function、while 这些保留字，也是由字母组成的 得和普通的名字区分开 最直接的办法，是拿每个名字去查一张保留字表 Lua 没这么做，它借用了字符串的驻留 每个字符串对象里，有一个叫 extra 的字节 解释器启动时，先把 23 个保留字都创建成字符串 在它们的 extra 里写下各自的编号，从 1 排到 23 普通名字的 extra 都是 0 之后每读到一个名字，照常为它创建字符串 如果它恰好是保留字 驻留交回来的，就是启动时建好的那个对象 所以判断是不是保留字，只要看 extra 是不是 0 local 后面跟着 while 语法分析要的是一个名字，拿到的却是保留字，于是报错 global 是 5.5 新加的关键字，用来声明全局变量 手册也把它列为保留字 可是发布包默认打开了一个兼容选项 每次开始读一段源码，都把 global 的 extra 改回 0 于是它又成了普通的名字 只有在语句开头，后面又紧跟名字、星号这类记号时 语法分析才把它当作声明 它向 llex 要记号时，必要时可以往后多看一个 判断 global 是不是声明，靠的就是多看的这一个 所以过去拿 global 当变量名的程序，照样能跑

### code · 06 指令

刚才那条 ADD 0 1 3，在内存里是一个 32 位整数 十六进制写作 03010022 这样一条条编好的指令，就是*字节码* 最低 7 位是操作码，说明做什么 其余 25 位按不同的格式，切成几个操作数 最常用的格式是 iABC A 占 8 位，接着是 1 位的标志 k，含义随指令而定 然后 B 和 C 各占 8 位 拆开 03010022 最低 7 位是十六进制 22，也就是 34 正是 ADD 的操作码 往上 8 位是 A，等于 0 k 是 0，B 是 1，C 是 3 另一种格式 iABx，把 k、B、C 合成一个 17 位的操作数 用来放常量的编号 isJ 则把 25 位全部用来放跳转的距离 5.5.1 一共定义了 85 种操作码 A、B、C 大多直接就是寄存器的编号 一条指令自己就写明了读哪几格、结果写到哪一格 这样设计的虚拟机，叫*寄存器式虚拟机* Lua 不是一开始就这样 把 a = b + c 交给 Lua 4.0 的编译器 得到的是另一种指令 先把 b 和 c 依次压到栈顶 ADD 不带任何操作数 它弹出栈顶的两个值相加，再把结果压回去 最后再弹出来，存进 a 操作数默认都在栈顶，这是*栈式虚拟机* 从 5.0 起，同一句只要一条带三个操作数的 ADD 指令的条数少了，每条带的操作数多了 5.4 又在 ADD 后面加了一条 MMBIN 两个数字相加，ADD 自己做完，跳过它 碰到不是数字的操作数，执行才落到 MMBIN 由它去查，有没有另外规定过加法该怎么做

### vm · 07 解释循环

变量 s 是字符串 "10"，n 是整数 1 s 加 n，在 Lua 5.5.1 里得到整数 11 在 Lua 5.3 里，却得到浮点数 11.0 字符串 "3.0" 加 n，几个版本都得 4.0 一张空表加 n，几个版本都报错，说不能对表做算术 差别出在执行指令的那段代码里 执行指令的，是 lvm.c 里的函数 luaV_execute lua.c 调用主函数时，就进入了这个函数 它的主体是一个循环 一个指针 pc，指着下一条要执行的指令 取出这条指令，pc 前进一格 再按低 7 位的操作码，跳到对应的处理代码 处理完，回到循环开头取下一条 怎样跳到对应的处理代码，有两种写法 用 GCC 这类编译器时 把每种指令处理代码的地址存成一张表 按操作码直接跳过去 别的编译器就用 switch 语句 所有指令操作的都是同一样东西 栈上属于当前函数的那一段寄存器 base 指向当前函数的 0 号寄存器 指令里的 A 是几，就从 base 往后数几格 s 加 n，编出来的是 ADD，后面跟着 MMBIN ADD 的处理代码，先看两个操作数的标签 都是整数，就做整数加法 结果写进 A 号寄存器，标签设成整数 然后 pc 再前进一格，跳过后面的 MMBIN 不都是整数，但都是数字 就按浮点数相加，同样跳过 MMBIN 这两条快路只认数字，字符串一概不碰 s 是字符串，快路走不通，执行落到 MMBIN MMBIN 去找这两个值有没有另外规定过加法 先查第一个操作数 s，它是字符串 字符串库给所有字符串都规定好了加法 它把 "10" 转成整数 10，再和 1 相加，得到整数 11 Lua 5.3 走的是另一条路 它的 ADD 自己就会把字符串转成数字 转出来的是浮点数，所以得到 11.0 从 5.4 起，ADD 不再转换字符串，这件事交给了字符串库 一张空表既不是数字，也没有规定过加法，于是报错 读字段的指令也是这么写的 先在表里直接按键查找 查不到，才转去通用的处理 lvm.c 里的很多指令都是这样 先走快路，走不通再转去通用的处理

### call · 08 调用

### table · 10 表

### coro · 13 协程

### gc · 14 回收

一个函数建了两张互相引用的表，其中一张存了十万个整数 函数返回以后，内存多出约 1152 KB 做一次完整的回收，多出的部分回到 0 两张表还在互相引用，却都被回收了 Lua 程序从不手动释放内存 手册的说法是，Lua 自动管理内存 由垃圾回收器回收所有死去的对象 死去，指的是回收器能确定 程序以后再也不会访问到它 回收器从几个*根*出发，主要是主线程和注册表 主线程是宿主最初建立的那份 lua_State 它的栈上，放着正在使用的值 注册表是解释器内部的一张表，全局表就放在里面 沿着引用能走到的对象都还活着，走不到的就是垃圾 函数返回以后，从根出发已经走不到这两张表 它们彼此之间的引用，不起作用 程序里用来观察的 watch，元表里写了 __mode 这样的表是*弱表*，它的引用挡不住回收 所以回收之后，watch 里的那一项也空了 判断能不能走到，用的是三种颜色 白色表示还没访问到 灰色表示已经访问到，但它引用的对象还没检查 黑色表示它和它直接引用的对象，都已经检查过 一轮开始时，所有对象都是白色，根被涂成灰色 之后每一步取出一个灰色对象 把它引用的白色对象涂灰，再把它自己涂黑 灰色对象处理完时，还是白色的，就是走不到的 最后沿着对象链表清扫一遍，释放这些白色对象 设置了 __gc 元方法的对象例外 回收器先调用它的 __gc 可 __gc 还要用到这个对象，所以它先被「复活」 内存通常要到下一轮才释放 这样完整地走一遍，可能要处理大量对象 一口气做完，程序就得停下来等 所以 lua_newstate 建立解释器状态时 回收器处在*增量*模式 回收工作被切成小步，和程序交替进行 程序每分配一定数量的内存，回收器就往前推进一小步 交替进行会带来一个问题 假设回收器已经把表 A 涂黑，认为它查完了 程序这时执行 A.x = B，而 B 还是白色 B 现在只被黑色的 A 引用，A 又不会再被检查 到最后 B 还是白色，会被当作垃圾释放 所以程序往对象里写入引用时，要经过*写屏障* 黑色对象一旦指向白色对象，写屏障就当场补救 对表，是把这张表重新涂灰，稍后再查一遍 对闭包、上值这类对象，是直接把被指向的对象涂灰 标记的最后，有一个不能拆开的原子阶段 它把被写屏障重新涂灰的对象再查一遍 清理弱表，挑出要执行 __gc 的对象 这些都得一口气做完 清扫同样分步进行，这期间程序还在不断创建新对象 新对象是白色的，可它们并不是垃圾 为此回收器准备了两种白色 原子阶段结束时，「当前白色」换成另一种 新对象涂上新的当前白色，清扫只释放带旧白色的对象 增量模式每一轮，都要把所有活着的对象标记一遍 一直活着的对象，每一轮都被重复检查 另一种做法基于一个假设：多数对象死得早 那么平时只检查新近创建的对象就够了 这就是*分代*回收 5.2 曾把它作为实验特性，5.3 又去掉了 5.4 重新加入了分代模式 每个对象带着一个年龄 大致分为新建的、活过一轮的和老的 平时只做遍历新对象的小回收 老对象占的内存涨到一定程度 再做一次遍历全部对象的大回收 官方命令行程序 lua 启动时，会主动切换到分代模式 5.5 又让分代模式下的大回收也能分步完成

### capi · 15 与 C 的边界

Lua 首先是给 C 程序嵌入用的 宿主要能调用 Lua 的函数 Lua 也要能调用宿主用 C 写的函数 这就得在两种语言之间传值 难点在于，C 的变量有固定的类型，Lua 的值没有 而 TValue 是解释器的内部结构，并不交给宿主 C API 在两边之间放了一个*虚拟栈* 宿主把值压进栈，再按位置从栈里读出来 来看一个最小的宿主 它先把一个 C 函数 c_add 注册成全局变量 再加载 return c_add(19, 23)，这时栈上多了一个函数 调用这个函数，进入 c_add 时 它看到的栈上，正好是两个参数 c_add 读出 19 和 23，把 42 压进栈 然后返回 1，表示有 1 个返回值 回到宿主，栈上只剩下这个 42 每个 C 函数看到的，只是属于自己的那一段栈 正数下标从 1 数起，1 号就是第一个参数 这和寄存器从 0 数起不同 负数下标从栈顶倒着数，-1 就是栈顶 Lua 调用 C 写的函数，走的就是这条路 标准库也是这样写成的 print、pcall 和 coroutine.resume，都是普通的 C 函数 它们通过同一套 API 读写 Lua 的值，从不碰内部结构 加载哪些库，由宿主决定 用 require 加载的模块 会缓存在 package.loaded 里 再次 require 时直接返回缓存 lua.c 的 main，也只是这套 API 的一个使用者 它建立状态，在保护模式下调用 pmain pmain 打开标准库，把回收器切换到分代模式 然后加载并运行脚本 最后由 lua_close 释放所有对象
