### value · 04 一个值

一个值写进一个变量，或者一个表的格子 解释器事先并不知道它会是什么类型 所以存放值的每一个位置，都得放得下任何一种值 还要能说明此刻放的是哪一种 lobject.h 把一个值拆成两部分 一部分是 8 字节的联合体 Value 联合体是 C 的一种类型，几个成员共用同一块内存 同一时刻只用其中一个 共用这 8 个字节的，有指针、整数和浮点数 另一部分是 1 字节的类型标签 两部分合在一起称为*标签值*，类型名是 TValue 在本片使用的 64 位机器上，一个 TValue 占 16 字节 其中 7 字节是为对齐留下的空隙 标签字节从第 0 位数起，0 到 3 位记录基本类型 Lua 的基本类型共有 8 种 nil、布尔、数字、字符串、函数、userdata、线程和表 第 4、5 位区分同一类型下的变体 比如数字有整数和浮点数，字符串有短串和长串 第 6 位表明这个值是否归垃圾回收器管理 数字直接存在这 8 个字节里，不必另外分配内存 布尔和 nil 更简单，只靠标签就能区分 state 里的整数 40 就是一个标签为整数、内容为 40 的 TValue 字符串、表、函数这类对象大小不定 只能在堆上单独分配 TValue 里存的是指向它们的指针 堆上的这些对象，开头都是同样的三个字段 tt 记录类型，marked 供垃圾回收使用 next 把新建的对象一个个挂到回收器的链表上 讲回收的时候，这条链表还会出现 字符串在 Lua 程序里用得极多 字段名、全局变量的名字，都是字符串 如果同样的内容每出现一次就新建一份 比较两个字符串就只能逐个字节地比 lstring.c 对不超过 40 字节的短字符串另有安排 创建之前，先到一张全局的字符串表里查找 已经有内容相同的，就直接复用那一个对象 这种做法称为字符串*驻留* 驻留之后，内容相同的两个短字符串必定是同一个对象 比较时只需比较指针 短字符串在创建时还会算好自己的哈希值，存在对象里 后面查表时会直接用到 更长的字符串不驻留 在 C 程序里，用两块独立的内存各写一次 label 交给 Lua 创建字符串，得到的是同一个对象 两次写入 41 字节的相同内容，得到的则是两个对象

### lex · 05 读入与记号

回到源码地图，读入和编译这一段从 lzio 和 llex 开始 加载时，库先看输入的第一个字节 如果是 0x1B，说明这是 luac 预先编译好的文件 交给 lundump 读取 否则就当作源码文本，交给语法分析器 对编译器来说，源码起初只是一串字符 第 2 行开头是 l、o、c、a、l、空格、f…… 语法分析需要的却是更大的单位 比如关键字 local、一个名字、一个等号、一个数字 把字符流切分成这样的单位，称为*词法分析* 切出的每个单位，称为一个*记号* llex.c 里，一个记号由两部分组成 一个表示种类的整数，加上附带的内容 名字和字符串附带一个指向字符串对象的指针 数字附带它的数值 切分本身由一个大的 switch 完成，看当前字符决定怎样读 空白和换行直接跳过 两个连续的减号开始注释，一直读到行尾 引号开始字符串，数字开始数值，字母开始一个名字 读名字时要处理一个问题 local、function、end 这些保留字同样由字母组成 必须和普通的名字区分开 最直接的做法，是拿每个名字去查一张保留字表 Lua 没有这样做，它借用了上一章的驻留 每个字符串对象里，有一个叫 extra 的字节 解释器启动时，先把 23 个保留字全部创建成字符串 并在它们的 extra 里写下各自的编号 之后每读到一个名字，照常为它创建字符串 如果它恰好是保留字，驻留会交回启动时建好的那个对象 所以判断是不是保留字，只要看 extra 是否为 0 编号从 1 排起，最后一个 while 是 23 普通名字的 extra 都是 0 以内层函数的第一行为例 state.value = state.value + delta 被切成 9 个记号 state、点、value、等号 state、点、value、加号、delta 语法分析器每次向 llex 要一个记号 必要时可以再往后多看一个

### parse · 06 边读边生成

不少编译器拿到记号以后，先建一棵完整的语法树 再遍历这棵树生成代码 Lua 的编译器没有这样做 它在读源码的同时，就把指令生成了出来 先看「读」的部分 语法本身是层层嵌套的 语句里有表达式，表达式里又有更小的表达式 lparser.c 为每一种语法结构写了一个函数 结构怎样嵌套，这些函数就怎样互相调用 比如读一条赋值语句，statement 先调用处理赋值的函数 后者再调用 expr，去读等号右边 这种按语法结构逐层调用的写法，称为*递归下降* Lua 的不同之处在于，这些函数每认出一部分 就当场调用 lcode.c，生成对应的指令 源码读完一遍，指令也就全部生成好了 生成的指令按函数存放 源码里的每一个函数，编译后成为一个*函数原型* 类型名是 Proto 原型里存着这个函数的指令、常量 以及嵌套在它里面的函数的原型 整个文件也当作一个函数来编译，称为主函数 这段程序的主函数里嵌着 4 个原型 make_counter、给 __index 用的函数 协程体，以及交给 pcall 的函数 make_counter 里面还嵌着一个，就是它返回的内层函数 生成指令之前，得先定下一件事 函数运行时，局部变量和计算的中间结果放在哪里 Lua 把它们放在解释器自己管理的一块栈上 它和 C 程序的调用栈不是一回事 每次调用函数，都在栈上分到连续的一段格子 编译时就要决定每个值放在第几格 这些格子在 Lua 里称为*寄存器* 但它们只是栈上的编号，和 CPU 的寄存器无关 编译器为正在编译的函数记着进度 已经生成了几条指令、用了哪些常量 下一个空闲的寄存器是几号 下面跟着编译器，读内层函数的第一行 第一个记号是 state，分析器先在当前函数里找这个名字 当前函数只有一个局部变量，就是参数 delta 它占 0 号寄存器，名字不是 state 于是到外面一层的 make_counter 里去找 在那里找到了，state 是 make_counter 的局部变量 它的 0 号是参数 start，state 在 1 号 函数用到外层函数的局部变量 这个变量对它来说就是*上值* 上值按出现的顺序编号，state 是第一个，编号为 0 编译器在内层函数的原型里记下一条 0 号上值，来自外层函数的 1 号寄存器 要是各层都找不到这个名字，它就是全局变量 这种情况放到讲闭包时再说 接着读到点和 value 这时还不知道这个字段是要读还是要写 所以先不生成指令 只在一个 expdesc 结构里记下 0 号上值所指的那张表，它的 value 字段 expdesc 描述的是一个还没有落地的表达式 等用途确定了，再决定生成哪条指令 寄存器、上值、expdesc，后面会一再用到 寄存器是栈上的编号格子 上值是函数用到的外层变量 expdesc 是还没有生成指令的表达式 读到等号，说明左边是赋值的目标，先放在一边 右边又是 state.value，同样先记成 expdesc 读到加号时，加法要求左边的操作数已经在寄存器里 编译器这才生成第一条指令 GETTABUP 从上值所指的表里取出字段 放进下一个空闲的寄存器，也就是 1 号 加号右边是 delta，本来就在 0 号寄存器 不需要任何指令 两边都已就位，于是生成 ADD 1 号与 0 号相加，结果放回 1 号 紧跟其后还有一条 MMBIN，它的用途留到讲指令时说明 最后回到等号左边，生成 SETTABUP 把 1 号寄存器的值写回表的 value 字段 一行源码，就这样变成了四条指令 运算符的优先级，也是在这个过程中处理的 lparser.c 里有一张优先级表，乘法排在加法之上 读 a 加 b 乘 c 时，分析器看到后面的乘号优先级更高 就先把 b 乘 c 编译完，再生成加法 一条语句结束，用过的临时寄存器全部释放 0 号一直是 delta，下一条语句的临时值又从 1 号开始 第 6 行 return state.value 生成两条指令 一条 GETTABUP 取值，一条 RETURN1 返回一个值 函数末尾还有一条兜底的 RETURN0 内层函数一共 7 条指令，最多用到 2 个寄存器 字段名 value 在常量表里只存一份 三条读写字段的指令，都通过编号引用它 编译时就能算出结果的表达式，编译器会直接算好 源码写 2 乘 3，生成的只是一条把 6 放进寄存器的指令 主函数、它嵌着的 4 个，再加上内层函数 整段程序编译完，一共 6 个函数原型、107 条指令

### code · 07 指令

每条指令是一个 32 位的无符号整数 这样的指令，通常称为*字节码* 最低 7 位是操作码，表示做什么 其余 25 位按不同的格式，切分成几个操作数 最常用的格式是 iABC A 占 8 位，接着是 1 位的标志 k 然后 B 和 C 各占 8 位 内层函数里那条 ADD，编码是十六进制的 000100A2 拆开来看，低 7 位是 34，正是 ADD 的操作码 再往上 8 位是 A，等于 1 接下来 k 是 0，B 是 1，C 是 0 合起来的意思是 1 号寄存器加 0 号寄存器，结果写入 1 号 另一种格式 iABx，把 k、B、C 合成一个 17 位的操作数 用来存放常量的编号 格式 isJ 则把 25 位全部用来存放跳转距离 5.5.1 一共定义了 85 种操作码 A、B、C 大多直接就是寄存器的编号 一条指令本身就写明了读哪几个寄存器、结果写到哪里 这样设计的解释器，称为*寄存器式虚拟机* Lua 并不是一开始就这样 把 a = b + c 交给 Lua 4.0 的编译器 得到的是另一种指令 它先把 b 和 c 依次压到栈顶 ADD 不带任何操作数 它弹出栈顶的两个值相加，再把结果压回去 最后再弹出来，存进 a 操作数隐含在栈顶的这种设计，称为*栈式虚拟机* 从 5.0 起，同一句只需要一条带三个操作数的 ADD 指令的条数少了，每条指令带的操作数多了 到了 5.4，ADD 后面又多出一条 MMBIN 原因是 ADD 只负责数字相加 两个操作数都是数字时，ADD 做完就跳过后面那一条 只有遇到不是数字的操作数，执行才会落到 MMBIN 由它去查元表里是否规定了加法 next_value 被调用三次，分别加 2、加 3、加 1 内层函数的 ADD 执行了 3 次 MMBIN 一次也没有执行

### vm · 08 解释循环

执行这些指令的，是 lvm.c 里的函数 luaV_execute lua.c 调用主函数时，执行就进入了这个函数 它的主体是一个循环 一个指针 pc 指向下一条要执行的指令 取出这条指令，pc 前进一格 再按低 7 位的操作码，跳到对应的处理代码 处理完毕，回到循环开头取下一条 怎样跳到对应的处理代码，有两种写法 取决于编译 Lua 所用的 C 编译器 用 GCC 及兼容的编译器时，它用一张地址表直接跳转 其余的编译器则用 switch 语句 本片的 5.5.1 由 GCC 编译，走的是地址表 所有指令操作的都是同一样东西 栈上属于当前函数的那一段寄存器 base 指向当前函数的 0 号寄存器 指令里的 A 是几，就从 base 往后数几格 以 ADD 的处理代码为例 它先检查两个操作数的标签 如果都是整数，就做整数加法 结果写入 A 号寄存器，标签设为整数 然后 pc 再前进一格，跳过后面的 MMBIN 如果不都是整数，但都能当作浮点数 就做浮点加法，同样跳过 MMBIN 两种情况都不满足，才不跳过，让 MMBIN 接手 把 next_value(2) 这次调用逐条走一遍 0 号寄存器里是参数 2 GETTABUP 通过上值拿到 state 表 键 value 是短字符串，在表里直接查到 40，放进 1 号 ADD 算出 42，写回 1 号 SETTABUP 把 42 写回表里 再一条 GETTABUP 取出 42，由 RETURN1 返回 RETURN1 执行前，1 号寄存器里确实是整数 42 GETTABUP 也分快慢两条路 先在表里直接按键查找 查不到，才去看这张表有没有元表 先处理最常见的情况，不成再转入通用的处理 lvm.c 里的许多指令都是这样写的 这几条指令能够执行，是因为主函数调用了 next_value 调用本身是怎样完成的，还没有说

### call · 09 调用

程序第 16 行在一行里做了三次调用 先看其中的 next_value(2) 调用之前，主函数把要调用的函数放进一个寄存器 参数紧跟在它后面 CALL 指令写明函数在几号寄存器 带几个参数，要几个返回值 执行 CALL 时，ldo.c 里准备调用的那个函数 先检查被调用的是什么 如果是用 C 写的函数，比如 print，就地调用 结果留在栈上 如果是 Lua 函数，就要记下这次调用的几项信息 它的寄存器从哪一格开始、到哪一格为止 以及当前执行到哪条指令 记录这些信息的结构称为*调用帧*，类型名是 CallInfo 新函数的 0 号寄存器紧挨着函数本身 参数原本就在那里，不需要搬动 把这段程序交给一个最简单的宿主运行 按格子从栈底往上数，这一刻的情形是这样 主函数本身在第 2 格，它的寄存器从第 3 格开始 next_value 在第 8 格，也就是主函数的 5 号寄存器 它自己的 0 号寄存器在第 9 格，里面是参数 2 调用方的两个格子 原样成了被调用方的函数和参数 各层的 CallInfo 连成一条链 这时一共三层：内层函数、主函数，最底下是宿主 新帧准备好以后，luaV_execute 并不递归调用自身 它把当前帧换成新帧，回到循环开头继续取指令 返回时，RETURN1 把结果放到原来函数所在的格子 再把当前帧换回上一层 接着执行调用方的下一条指令 所以 Lua 函数调用 Lua 函数，不会加深 C 的栈 一个 Lua 函数递归调用自己 100000 层 每层都等下一层返回，也能正常结束 经过 C 函数时，情况就不同了 pcall 就是一个 C 函数 C 函数必须在 C 的栈上真正调用一次 所以 C 调用的嵌套层数有上限，是 200 一个函数通过 pcall 调用自己，到第 198 层就会报错 错误信息是 C stack overflow 还有一种调用，连新帧都不需要建 像 return f(x) 这样的调用 当前函数在它之后已经无事可做 这种调用称为*尾调用* TAILCALL 指令让被调用的函数直接沿用当前的帧 协程体最后一句 return next_value(1) 编译出来就是一条 TAILCALL 前半段的路线到此走完 脚本被切成记号，编译成原型和指令 指令在栈上的寄存器里一条条执行 每次调用 Lua 函数，就建立一个调用帧 后半段看执行当中用到的几项机制

### closure · 10 闭包与上值

函数既然是值，就可以作为参数传给别的函数 比如把一个「加 3」的函数传进去，连用两次 1 就变成了 7 函数定义本身，也是一个在运行时执行的表达式 每执行一次，就产生一个新的函数实例 手册把运行时产生的每个函数实例都称为闭包 next_value 就是其中之一 闭包可以使用定义它的那个作用域里的局部变量 即使那个作用域已经结束 计数器正是这样 make_counter 返回以后 next_value 仍在读写 state 问题在于 state 的位置 它放在 make_counter 的 1 号寄存器里 make_counter 一返回，它的帧就结束了 那一段栈，随后会被别的调用覆盖 所以返回出去的不能只有指令 还要带上它用到的外层变量 在实现上，一个闭包由两部分组成 一个函数原型，以及一组指向上值的引用 每调用一次 make_counter 就用同一个原型生成一个新的闭包 编译时，原型里只记了一句 0 号上值，来自外层函数的 1 号寄存器 运行到 CLOSURE 指令时，才真正去找这个寄存器 lfunc.c 维护着一张链表，记录哪些栈格已经被闭包捕获 这些仍然指向栈的上值，称为*开放上值* 要捕获的格子已经在链表里，就直接复用那个上值对象 否则新建一个 UpVal 用一个指针指向栈上的那一格 此时内层函数读写上值，实际读写的就是栈上的 state make_counter 执行 RETURN 时，这一帧即将消失 它的 RETURN 指令带着一个标志 表示这一帧可能还有开放上值，于是开始关闭它们 关闭的做法，是把栈上那一格的 TValue 复制到 UpVal 内部 再让指针改指这份复制 从此读写这个上值，就不再经过栈 复制的只是一个 TValue，也就是一个指向表的指针 表本身没有复制 所以闭包里的 state 和外面拿到的 state，仍是同一张表 next_value 第一次执行时 它的上值已经关闭，开放上值的链表是空的 上值没有在创建闭包时就复制 原因是几个闭包可能捕获同一个变量 创建时，它们在链表里找到同一个开放上值 从此共用一个 UpVal 关闭时只复制一次，几个闭包看到的仍是同一份值 两个闭包共用一个上值，一个负责加一，一个负责读取 交替进行，读到的依次是 1、1、2、2 而两次调用 make_counter 会各自新建 state 得到的是两个互不相干的计数器 闭包也解释了全局变量的工作方式 print、setmetatable 这些名字 分析器在各层函数里都找不到 这时，名字 print 被改写成 _ENV.print _ENV 是每个主函数都带有的 0 号上值 负责加载的 lua_load，把存放全局变量的全局表 放进这个上值 所以全局变量，其实就是全局表里的一个字段 主函数读取 print，用的同样是 GETTABUP 只是上值换成了 _ENV 这种做法从 5.2 开始 5.1 里，每个函数另有一个独立的环境 5.5 又加入了 global 声明 写 global x，就声明 x 是一个全局变量 一旦作用域里写了这样的声明 没有声明过的名字，会在编译时报错 没有任何 global 声明的程序，行为和以前一样 默认配置里，global 并不是保留字，它的 extra 是 0 只在语句开头、后面紧跟名字之类的记号时才算声明 过去把 global 当变量名的程序，照样能运行 闭包带走的 state，是一张表 这张表本身又是怎样存放的

### table · 11 表

表是 Lua 唯一的数据结构机制 数组、列表、集合、记录、树和图，都用表来表示 同一张表里，可以有 t[1] 这样的整数下标 也可以有 t.name 这样的字段 t.name 只是 t["name"] 的简写 如果只用哈希表来实现，连续的整数下标也要计算哈希 如果只用数组，又放不下 name、value 这样的键 ltable.c 因此把一张表分成两部分 *数组部分*存放从 1 开始的整数键，按下标直接定位 其余的键放进*哈希部分* 哈希部分的节点数总是 2 的幂 每个节点存一个键、一个值，以及一个 next 偏移 一个键根据哈希值对应到的节点，称为它的*主位置* 字符串键用创建时就算好的哈希值 整数键则直接取它除以某个数的余数 两个键的主位置相同，就发生冲突 下面拿一张有 8 个节点的表来演示 整数键的除数取节点数减 1 8 个节点时是 7，主位置就是除以 7 的余数 放入 3，余数是 3，3 号节点空着，直接放进去 放入 10，余数也是 3，冲突了 3 号里的 3 正处在自己的主位置上，所以它不动 10 去找空节点，空节点从表尾往前找，找到 7 号 3 号节点的 next 记下 4 意思是同一条链上，往后 4 格还有一个键 查找 10 时，先到主位置 3 号，再沿 next 走到 7 号 放入 0，直接进 0 号 放入 7，余数是 0，冲突，7 进入下一个空节点 6 号 0 号的 next 记下 6 再放入 6，它的主位置 6 号却被 7 占着 7 的主位置是 0 号，它只是借用了这个节点 于是 7 被挪到下一个空节点 5 号 0 号的 next 随之改为 5 6 住进自己的主位置 规则可以概括为一句 借用别人主位置的键，遇到主人就让出 这样一来，每个键都能从自己的主位置出发，沿一条链找到 再放入 1、2、4，8 个节点全满了 放入 5 时找不到空节点 这时要对整张表*重新散列* 先数一遍所有的整数键，再重新决定两部分各有多大 数组的大小在 2 的幂里挑选 一个哈希节点占用的内存，大约是数组一格的 3 倍 所以落在范围里的整数键，要至少占三分之一 结果是，数组部分 16 格，1 到 7 和 10 都搬了进去 16 格里有 8 个键，超过了三分之一 哈希部分只剩 1 个节点，存放键 0 数组部分从 1 开始，0 不在其中 程序里的 state 只有一个键 value 没有数组部分，哈希部分只有 1 个节点 字符串键落在哪个节点，取决于字符串的哈希值 而计算哈希用的种子，在启动时由内存地址和时间算出 所以同一个字符串键在两次运行中，所在的节点可能不同 5.5 还改变了数组部分的存储方式 5.4 的数组每格是一个 16 字节的 TValue 其中 7 字节是对齐空隙 5.5.1 把它拆开存放 8 字节的内容放在一边，1 字节的标签放在另一边 同样预留 1024 格，5.4.9 需要 16384 字节 5.5.1 只需要 9220 字节 需要注意，数组的容量并不等于表的长度 用 table.create 预留 8 格，表的长度仍是 0 回到第 16 行 读出的 counter 并不在 state 里，它来自元表

### meta · 12 元表

元表让程序可以改变一个值在某些操作下的行为 元表本身就是一张普通的表 其中以两个下划线开头的特定字段 各自对应一种操作，称为*元方法* 比如 __add 规定加法 两张表本来不能相加 如果其中一张的元表里有 __add，Lua 就调用它 把它的返回值当作相加的结果 比如向量 1、2 和向量 10、20 相加，得到 11、22 __add 被调用了一次 __index 规定读取一个不存在的键时怎么办 这段程序用的就是它 主函数读取 state.label state 在主函数里是局部变量，就在寄存器里 所以用的是按字段名读表的指令 GETFIELD 快路在 state 里没有找到 label 于是转入慢路，去查 state 的元表 元表里的 __index 是一个函数 解释器以 state 和 "label" 为参数调用它 返回的 "counter"，就是这次读取的结果 如果 __index 是一张表，就到那张表里接着查找 那张表还可以有自己的元表，一层接一层，最多 2000 层 写入也有对应的元方法 __newindex 它只在键不存在时触发，已有的键直接写入 每次查找元方法，本来都要在元表里按名字查一次哈希 而大多数元表只定义了少数几个元方法 表头有一个字节 flags，每一位对应一种常用的元方法 查过一次发现没有，就把对应的那一位设为 1 下次先看这一位，是 1 就不再查哈希 __index、__newindex、__eq 等 6 种元方法有这个缓存 算术类的元方法，走的是 MMBIN 这条路 向量相加时，ADD 的快路不成立，执行落到 MMBIN MMBIN 带着事件号 6，也就是 __add 依次到两个操作数的元表里查找，找到就调用 Lua 一共定义了 25 种元方法事件

### error · 13 错误

Lua 程序可以调用 error，主动抛出一个错误 错误发生后，当前的函数就不再继续执行 如果不想让错误终止整个程序 就用 pcall 以保护模式调用函数 被调用的函数一旦出错，控制立刻回到 pcall pcall 返回 false，以及错误对象 这相当于其他语言里的 try 和 catch 只不过 Lua 用一次函数调用来表达 错误对象可以是任何值，不一定是字符串 实验里抛出一张表，pcall 接住的正是那张表 第 26 行的 error 发生时，可能已经处在好几层调用之下 控制必须直接回到 pcall，中间各层都不再继续 这几层里有 C 函数，而 C 语言本身没有异常机制 ldo.c 用的是 C 标准库里的两个函数 setjmp 和 longjmp setjmp 记下 C 程序此刻的执行位置 longjmp 能从更深的调用里，直接跳回这个位置 pcall 最终会走到 ldo.c 里设置跳转点的函数 它在 C 栈上放一个跳转点，用 setjmp 记下位置 再把它记到解释器的当前状态上，并链接到上一个跳转点 然后才调用目标函数 error 最终会调用 ldo.c 里抛出错误的函数 它取出最近记下的那个跳转点，执行 longjmp C 的执行回到 setjmp 那里，这一次带着错误状态 跳回来以后，Lua 这边的状态也要恢复 调用帧退回到 pcall 自己所在的那一层 这期间留下的开放上值一一关闭 错误对象放到栈上原来的位置 pcall 于是返回 false 以及错误对象 counter-error 如果用 C++ 编译 Lua，同样的位置会改用 try 和 throw 5.4 还加入了*待关闭变量* 局部变量声明时标上 close 离开作用域时，就会调用它的 __close 正常离开时调用 因出错离开时，则在刚才这条恢复的路上调用 longjmp 一下子跳过了中间所有的 C 函数 协程的暂停，用的也是这个办法

### coro · 14 协程

普通的函数调用，要等被调用的函数运行到返回 控制才回到调用方 协程可以在中途暂停，把控制交还给调用方 之后再从暂停的地方继续 语言里，协程通过 coroutine 库的几个函数来使用 coroutine.create 把一个函数包装成协程 这时它还没有开始运行 coroutine.resume 让它运行 直到函数结束，或者调用 coroutine.yield 暂停 yield 的参数会成为 resume 的返回值 下一次 resume 的参数，又成为 yield 的返回值 两段代码就这样轮流执行，相互传递数据 比如一个协程，先交出参数加 1，再把收到的值乘 2 返回 第一次 resume 传进 10，它交出 11 第二次传进 21，它返回 42 用协程还可以写生成器 比如一个协程在循环里依次交出 1、2、3 每恢复一次，就得到下一个数 协程尚未运行或暂停时，状态是 suspended 正在运行时是 running，运行结束是 dead 它和操作系统的线程不同 同一时刻只有一个协程在运行 切换只发生在显式调用 yield 的地方 回到这段程序，第一次 resume 让协程运行到 yield 交出 45 后暂停 第二次 resume 从暂停处继续，最终返回 46 要做到这一点，暂停时必须保存三样东西 协程的局部变量，调用到了哪一层 以及每一层执行到了哪条指令 Lua 内部把协程也称为线程 代表它的结构，是 lua_State 每个协程都有自己的一份，里面有自己的栈和 CallInfo 链 全局表、字符串表和垃圾回收器 放在另一个结构 global_State 里，所有协程共用一份 resume 把参数搬到协程的栈上，在保护模式下运行它 也就是说，resume 同样设下了一个跳转点 协程体运行到 coroutine.yield 而 yield 本身是一个 C 函数 它把协程的状态设为暂停，记下交出了几个值 然后调用抛出错误时用的同一个函数 longjmp 回到 resume 设下的跳转点 C 栈上比 resume 更深的部分，被整个丢弃 但协程自己的栈和 CallInfo 链原样保留 需要保存的，恰好就是这些 resume 返回 true 和 45 协程的状态是 suspended 第二次 resume 发现协程正处于暂停状态 它先替那次 yield 调用收尾 resume 的参数，成为 yield 的返回值 再沿着 CallInfo 链继续执行协程体 协程体尾调用 next_value(1)，46 直接交给 resume resume 返回 true 和 46，状态变为 dead 这种做法也带来一个限制 yield 时 C 栈被丢弃 如果 yield 时，调用链中间夹着一个普通的 C 函数 那个函数执行到一半的状态就会丢失 遇到这种情况，yield 会报错 提示不能跨越 C 调用的边界让出 从 5.2 起，C 函数可以登记一个续接函数 协程恢复时，由 Lua 调用它接着往下做 pcall 就是这样写的 所以在协程里，pcall 内部也可以 yield 表、闭包、协程，程序一直在创建对象 却从来没有释放过一个

### gc · 15 回收

Lua 程序从不手动释放内存 手册的说法是，Lua 自动管理内存 由垃圾回收器回收所有死去的对象 所谓死去，是指回收器能够确定 程序以后再也不会访问到它 回收器从几个*根*出发，主要是主线程和注册表 主线程是宿主最初建立的那份 lua_State 它的栈上，放着正在使用的值 注册表是解释器内部的一张表，全局表就放在里面 沿着引用能走到的对象都还活着，走不到的就是垃圾 这段程序里，next_value 就在主线程的栈上 从它经过上值能走到 state，所以 state 一直活着 所以两个对象即使互相引用 只要从根走不到，照样会被回收 判断能否走到，用的是三种颜色 白色表示还没有访问到 灰色表示已经访问到，但它引用的对象还没检查 黑色表示它和它直接引用的对象，都已经检查过 一轮开始时，所有对象都是白色，根被涂成灰色 之后每一步取出一个灰色对象 把它引用的白色对象涂灰，再把它自己涂黑 灰色对象处理完时，仍是白色的就是走不到的 最后沿着对象链表清扫一遍，释放这些白色对象 设置了 __gc 元方法的对象例外 回收器先调用它的 __gc，通常到下一轮才释放 这样完整地走一遍，可能要处理大量对象 如果一口气做完，程序就得停下来等 所以 lua_newstate 建立解释器状态时 回收器处于*增量*模式 回收工作被切成小步，与程序交替进行 程序每分配一定数量的内存，回收器就向前推进一小步 交替进行会带来一个问题 假设回收器已经把表 A 涂黑，认为它检查完了 程序这时执行 A.x = B，而 B 还是白色 B 现在只被黑色的 A 引用，A 又不会再被检查 到最后 B 仍是白色，会被当作垃圾释放 所以程序往对象里写入引用时，要经过*写屏障* 黑色对象一旦指向白色对象，写屏障就当场补救 对表，是把这张表重新涂灰，稍后再检查一遍 对闭包、上值这类对象，是直接把被指向的对象涂灰 标记的最后有一个不能拆分的原子阶段，负责收尾 清扫同样分步进行，期间程序还在不断创建新对象 新对象是白色的，但它们并不是垃圾 为此回收器准备了两种白色 原子阶段结束时，「当前白色」切换为另一种 新对象涂上新的当前白色，清扫只释放带旧白色的对象 增量模式每一轮都要把所有活着的对象标记一遍 一直活着的对象，每一轮都被重复检查 另一种做法基于一个假设：多数对象死得早 那么平时只检查新近创建的对象就够了 这就是*分代*回收 5.2 曾把它作为实验特性，5.3 又去掉了 5.4 重新加入了分代模式 对象带一个年龄，分为新建的、活过一轮的和老的 平时只做遍历新对象的小回收 老对象占用的内存增长到一定程度 再做一次遍历全部对象的大回收 官方命令行程序 lua 启动时，会主动切换到分代模式 所以这段程序实际是在分代模式下运行的 5.5 又让分代模式下的大回收也能分步完成 这些对象都在 Lua 一侧 用 C 写的宿主，又怎样拿到它们、把值交给它们

### capi · 16 与 C 的边界
