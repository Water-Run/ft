## cookie · 无章节卡

预估 38.0 秒。

| 句号 | 字幕 / 旁白原文 |
|---|---|
| c1 | 服务器生成一个随机会话编号，放进 cookie。 |
| c2 | 浏览器之后每次请求，自动带上这个编号。 |
| c3 | 服务器查会话表：编号存在、没过期，就认这次会话。 |
| c4 | 所以它验证的是会话连续，不是重新验证你这个人。 |
| c5 | 第一个缺点：这张表要存在服务器上。 |
| c6 | 服务器一多，就要共享这张表；表丢了，登录状态也没了。 |
| c7 | 第二个缺点：编号被偷，别人就能冒充你。 |
| c8 | 第三个缺点：浏览器会自动带 cookie，跨站请求也能利用它。 |

## jwt · 无章节卡

预估 29.7 秒。

| 句号 | 字幕 / 旁白原文 |
|---|---|
| j1 | 为了不存这张表，可以把验证结果签进一个令牌。 |
| j2 | JWT 就是这种令牌：头部、载荷、签名。 |
| j3 | 前两段只是编码，不是加密；谁拿到都能读。 |
| j4 | 服务器验签，再查过期和受众，才相信载荷。 |
| j5 | 它解决了查表，但带来新问题：撤销麻烦。 |
| j6 | 令牌发出去，到期前通常一直有效；被偷也一样。 |
| j7 | 所以要短命，必要时维护撤销名单。 |
