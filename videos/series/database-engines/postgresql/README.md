## 叙事与预算

主问题：PostgreSQL 怎样实现一条记录的存储、查询、修改、并发与恢复；这些设计与 InnoDB 相比，带来什么能力与成本？在机制展开后，再解释它为何值得新项目优先评估。

主线与系列前两集一致：定位与来历 → 数据怎么放 → 怎么找 → 一次修改 → 怎么并发 → 回收 → 出错怎么办 → InnoDB 对照与选型 → 四个问题。开场报出 2026 年调查的 57.9% / 35.1%，比较章将实现差异、能力组合和实际采用案例归纳；不把调查比例写成全球市场份额或迁移因果。“开源巅峰”保留为策划指定标题。

正文舍弃：市场排名大全、参数大全、完整版本年表、遍历所有索引与隔离级别、高可用部署教程、未经同负载实测的性能优劣。原型年代的存储实验与现代实现明确区分。

独立比较章放在恢复之后，以前面已解释的机制为依据；部分索引、JSONB 与预约约束只作短例，不另开一条长业务故事。Django / Supabase 是具体采用路径，PostGIS / pgvector 是扩展用途，不冒称本机测试过所有扩展或全行业已默认采用 Pg。

## InnoDB 对照的轴与结论

| 比较轴 | PostgreSQL 18.4 | InnoDB / MySQL 9.7 | 本稿表达的取舍 |
|---|---|---|---|
| 主键读整行 | 普通索引找到堆版本 | 聚簇主键叶子直接存行 | 保留 InnoDB 路径直接的长处，不据图直接判定整体速度。 |
| 二级索引与键宽 | 普通索引引用堆位置 | 二级索引带主键，再找聚簇记录 | Pg 不会自动把宽主键复制到每个其他索引，仍需看具体索引、覆盖与负载。 |
| 旧版本与清理 | heap 版本、HOT、剪枝 / VACUUM | undo 信息重建历史、purge 等维护 | 两边都有历史维护；Pg 高频更新与长事务成本明确保留。 |
| 默认隔离 | 出厂为读已提交 | 出厂为可重复读 | 配置可改变，比较行为前先对齐级别，不说某默认值全面更好。 |
| 系统能力与采用 | 部分索引、JSONB/GIN、范围/排他约束、开放扩展接口、社区与工具 | MySQL 同样有 JSON / 空间能力，InnoDB 本身是其中的存储组件 | 选型比较整套系统；优势在适合任务的组合和现成采用路径，不把所有功能说成 Pg 独有。 |
