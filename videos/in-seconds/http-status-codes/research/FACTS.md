## 取证范围与限制

- 取证日期：2026-10-20（第一轮）、2026-10-21（复核与补强）。对象：HTTP 响应状态码——五类的分界、实际最常遇到的那几个、每个码是谁发出的、以及 4xx 与 5xx 的责任归属。
- 一手来源：RFC 9110（HTTP Semantics，2022-06）第 15 章；RFC 6585（Additional HTTP Status Codes，2012-04）第 4 章；IANA「Hypertext Transfer Protocol (HTTP) Status Code Registry」（注册表 `updated` 2025-09-15）。
- 实验：`research/lab/11_status_codes.ps1` 起一个最小 HTTP 服务（`11_status_codes_server.js`），用 curl 逐个触发状态码，完整回显在 `research/lab/out_11_status_codes.txt`。回显里的状态行与头字段是实测值，与 RFC 的条文逐条对照。
- 本机没有 bash，实验脚本用 PowerShell 写（本仓库 `wsl` 一集同此做法）；脚本按执行顺序编号，回显与脚本同名对应。回显为本机原样保存的 CRLF 形式，未做换行转换。
- 脱敏：实验只监听 127.0.0.1 的临时端口；回显中不含主机名、用户名、本机路径或任何真实站点。已逐行检查。
- 讲解对象自己的材料（状态行文法、原因短语、官方码表、相关头字段）另记在 `research/MATERIALS.md`。

本轮补强实验（见 `out_11_status_codes.txt`），新增三组可复查的实测：

| 新增场景 | 实测结果 | 支撑的事实 |
|---|---|---|
| 同一个资源 `/private`，带有效凭据但权限不够 | `HTTP/1.1 403 Forbidden`，不带 `WWW-Authenticate` | 02-11、02-12 |
| 同一个资源 `/private`，带有效凭据且权限够 | `HTTP/1.1 200 OK` | 02-11、02-12 |
| 服务器回一个未登记的码 | `HTTP/1.1 471 unknown` | 01-4、01-5 |
| 同一个 404 经网关转发 | 状态码仍是 404，且响应里多出网关自己的 `X-Gateway: demo-gateway` 头 | 03-7 |

第一条补上了一个原先只有单一出处的关键对比：401 与 403 的分界不再只靠 RFC 措辞，还有实测——同一个资源、同一份有效凭据，只因权限不同就分别给出 403 与 200，而凭据不对时给 401 并带 WWW-Authenticate。

第四条把 03-7 的证据从「头字段大小写差异」升级为硬证据：网关给响应打上自己的标记头，标记头在场说明响应确实经过了网关，而状态码仍是上游那个 404。

本轮另外核对了 HTTP/2 的报文结构：RFC 9113 §8.1、§8.3.2 确认状态码放在 `:status` 伪头字段、HTTP/2 报文里没有状态行这一项。RFC 9113 全文没有出现 "reason phrase" 一词，因此「HTTP/2 没有原因短语的位置」是本片的推论而非规范原话，记在 `research/MATERIALS.md` 第 1 节。

**沿革与本片对象的关系**（供文案取舍，不作旁白陈述）：状态码这套体系自 HTTP/1.0 才进入协议，HTTP/0.9 只有一个 GET 方法与纯文本响应；HTTP/2 与 HTTP/3 改用伪头字段承载状态码，HTTP/1.1 的状态行不再是报文形态，但三位数与五类划分始终没变——三个大版本共享同一套语义（05-9）。这是「沿革」这一段能收进 96 秒而不喧宾夺主的理由：只讲「状态码本身没变」这一件事。
