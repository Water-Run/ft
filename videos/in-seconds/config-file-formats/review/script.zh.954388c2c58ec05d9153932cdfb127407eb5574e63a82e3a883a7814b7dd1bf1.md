## 连贯阅读

先通读问题、解释与章节推进，再到逐句表定位意见。下文按源稿顺序连接字幕，保留原文字与标点；不含静默 cue。口播读法与停顿另按配音规则核对。

### open · 无章节卡

改掉软件的一个参数，不需要重新编译代码 只需打开外面的一个纯文本，改掉里面的数字 这种专门存参数的外部文本，叫配置文件 1985 年，Windows 1.0 用 .ini 文件存放设置 它只靠两样东西排版：方括号分出章节，等号写出键值 简单直接，谁都能看懂 但它只有平铺的一层 遇到一层套一层的复杂数据，就装不下了

### xml · 无章节卡

1998 年成为标准的 .xml 改用成对的尖括号标签来表达层级 一头一尾两个标签，把数据夹在中间 大标签里再套小标签，就能搭出任意深度的树状结构 标签内还能附加属性 配上文档类型定义，还能逐项校验格式 但代价是每个数据都得有头有尾 层级一深，外面的标签，比里面的数据本身还要长出一大截

### json · 无章节卡

2001 年提出的 .json，砍掉了繁琐的闭合标签 它改用大括号层层包裹，同一段配置短了一大截 还直接区分数字、字符串、布尔值、数组与对象 每行写一个完整的 JSON 值，就是 .jsonl 适合日志这类逐条记录的数据 但 JSON 更迁就机器：满屏引号与括号，而且没有注释

### yaml · 无章节卡

同在 2001 年出现的 .yaml，把重心转向人的阅读 它的块式写法不用括号，多数字符串也不必加引号 只靠行首缩进区分层级 还能用井号随时写注释 但省掉括号，也带来了隐患 少敲一个空格，要么解析报错，要么层级悄悄变了样 按 YAML 1.1 的规则，不加引号的 NO，代表挪威 却会被当成布尔值的“否”

### toml · 无章节卡

2013 年出现的 .toml，想兼顾直观与严谨 它请回了 .ini 的方括号 在里面加颗圆点，就写出了多层嵌套 缩进不影响结构，既能写注释，又有明确的数据类型 这五种格式的演进，其实一直在两端寻找平衡 一端是机器好解析，一端是人类好读写 无论选哪一种，作用都一样：不必重改代码，只需改动配置
