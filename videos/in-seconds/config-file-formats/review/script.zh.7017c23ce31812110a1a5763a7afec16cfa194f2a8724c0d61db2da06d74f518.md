## 连贯阅读

先通读问题、解释与章节推进，再到逐句表定位意见。下文按源稿顺序连接字幕，保留原文字与标点；不含静默 cue。口播读法与停顿另按配音规则核对。

### open · 无章节卡

改掉软件的一个参数，不需要重新编译代码 只需打开外面的一个纯文本，改掉里面的数字 这种专门存参数的外部文本，叫配置文件 1980 年代普及的 .ini，是最早的常见格式 它只靠两样东西排版：方括号分出章节，等号写出键值 简单直接，谁都能看懂 但它只有平铺的一层，遇到一层套一层的复杂数据，就装不下了

### xml · 无章节卡

1998 年成为标准的 .xml，改用成对的尖括号标签来表达层级 一头一尾两个标签，把数据夹在中间 大标签里再套小标签，就能搭出任意深度的树状结构 标签内还能附加属性，并严格校验每一项的格式 但代价是每个数据都得有头有尾 层级一深，外面的标签，比里面的数据本身还要长出一大截

### json · 无章节卡

2001 年提出的 .json，砍掉了繁琐的闭合标签 它改用大括号层层包裹，体积立刻小了一半 同时直接区分数字、文本、数组与布尔值，机器读写极快 把每个大括号压成独立的一行，就是 .jsonl，适合日志与 AI 数据逐行追加 但 JSON 更迁就机器：满屏引号与括号，而且不允许写注释

### yaml · 无章节卡

同在 2001 年诞生的 .yaml，把重心转向人类的阅读体验 它去掉了所有括号和引号，只靠左边的空格缩进来区分层级 还能用井号随时添加注释，常用于编写复杂的部署清单 但省掉括号，也带来了隐患 几十行往下，只要少敲一个空格，整个文件就会解析失败 不加引号的简写，比如代表挪威的 NO，还会被自动当成布尔值的“否”

### toml · 无章节卡

2013 年发布的 .toml，把直观与严谨合二为一 它请回了 .ini 的方括号，在里面加颗圆点，就解决了多层嵌套 不用数空格，既能写注释，又有严格的数据类型 这五种格式的演进，其实一直在两端寻找平衡 一端是机器好解析，一端是人类好读写 无论选哪一种，作用都一样：不必重改代码，只需改动配置
