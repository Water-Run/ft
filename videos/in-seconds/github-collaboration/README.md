「这些」指同一次会话里对 GitHub 协作的讲解，要点是：

- 创建 PR 为什么要先 Fork 仓库、再开一个新分支，而不是直接往别人的仓库里加代码。
- PR 不是「把代码加进去」，而是请求合并的申请页；代码在提 PR 之前就已经提交并推送到某个分支上。
- Issue 与 PR 为什么共用同一套编号，号码为什么不回收，为什么编号属于仓库而不是属于人。
- 草稿 PR、合并，以及 `Refs` 与 `Closes` 的区别。

「没提到的东西」由制作时按下面的取舍表补齐，不在本次登记里定稿。

### 受众与核心问题

- **受众**：没有用过 GitHub 协作的人，包括新手程序员和不写代码、只参与协作的人。按系列约定，低认知负担，不假设观众会 Git 命令。
- **核心问题**：我没有权限改别人的项目，为什么还能给它提改动？
- **一句话答案（草案，待取证后定稿）**：没有写权限，就 Fork 出自己的副本；开分支把这次改动和主线隔开；再用 PR 请原仓库的维护者审了决定要不要并入。

### 解释路径（草案，以文案为准）

按系列结构骨架：现象或问题 → 片名卡 → 它是什么 → 它怎么工作 → 边界或比较 → 一句结论 → 片尾。

1. **现象**：想给别人的项目改一行字，却发现推不上去。
2. **它是什么**：Fork 是一份属于自己的完整副本；分支是副本里一条与主线隔开的工作线。
3. **它怎么工作**（重头）：在分支上改并提交、推到自己的副本，再对原仓库发起 PR。强调 PR 是「申请页」：看到的改动早就在分支里，合并前不影响原仓库主线。Issue 是说清「要解决什么」的地方；PR 与 Issue 共用编号，所以 `#12` 在这个仓库里只指向一件事。
4. **边界或比较**：有写权限的团队可以不 Fork、直接在原仓库开分支；Fork 的编号与原仓库各自独立；合并之后改动才进主线。
5. **结论**：Fork 解决没有权限，分支解决要隔开，PR 解决要被审。

### 取舍：「没提到的东西」怎么处理

旁白主动教的新名词不超过四个：Fork、分支、Pull Request（PR）、Issue。其余的只在画面上当标签，或留给别的集。

| 内容 | 建议 |
|---|---|
| clone、远端名 `origin` 与 `upstream` | 画面标签，不进旁白；演示 Fork 副本与本机、原仓库三者的关系时一笔带过 |
| commit 与 push | 一句话带过，不演示命令，细节归《150 秒速通 Git》 |
| 草稿 PR（Draft） | 进旁白一句：还没准备好合并，先给人看 |
| 审查（review）与自动检查 | 画面上出现，旁白一句话说明「合并前有人看、有机器查」，不展开 Actions |
| 合并方式（merge commit、squash、rebase） | 留给别的集，本集只说「合并」 |
| 保持 Fork 与原仓库同步 | 边界部分一句话提及，不演示 |
| 标签、指派、里程碑 | 不讲 |
| `Refs` 与 `Closes` | 进旁白：只是关联，还是合并时自动关闭，取证后再定怎么说 |
| 编号共用与不回收 | 本集的一个「原来如此」，放在 Issue 与 PR 一起出现的地方，约 20 秒 |
