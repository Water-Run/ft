核心问题：我没有权限改别人的项目，为什么还能给它提改动？

一句话答案：没有写权限，就 Fork 出自己的副本；开分支把这次改动和主线隔开；再用 PR 请原仓库的维护者审了决定要不要并入。

贯穿例子：给 GitHub 官方练习仓库 octocat/Spoon-Knife 的 README 改一个错别字（eatting → eating），从「推不上去」走到「合并进主线」。错别字是虚构演示，不是该仓库真实内容（见待定问题③）。

F1 · Fork：没有写权限时的自己的副本7 条 · 官方文档
#陈述依据（原文摘录）
F1.1Fork 是从上游仓库复制出来的仓库，有自己的设置与权限，仍与上游连接“Forks are repositories that start as copies of another repository, called the upstream repository.” docs.github.com/en/pull-requests/reference/forks
F1.2Fork 是独立仓库，不是分支；可有自己的分支、Issue 与 PR 等“A branch is part of one repository. A fork is a separate repository with its own settings and collaboration space.”
F1.3往自己 Fork 推代码不需要上游许可“You do not need permission from the upstream repository to push to a fork you created.” …/reference/pull-requests
F1.4有读权限即可 Fork（所有者允许时）“anyone can fork an existing ("upstream") repository if they have read access…”
F1.5Fork 让人在不影响上游的前提下提议改动“Forking a repository lets you propose changes to a project without affecting the upstream repository.” …/how-tos/work-with-forks/fork-a-repo
F1.6没有写权限时推不上去（Desktop 会自动建 Fork）“if you clone a repository that you do not have write access to, and then attempt to push … a fork will be created for you.” 网页端回显待实测
F1.7边界：网络内共享 Git 数据，「独立」指设置/权限/协作空间，不是对象级完全隔离“Repositories in the network share Git data…” 文案不得说「完全隔离」

#陈述依据（原文摘录）
F2.1开分支＝开辟不影响默认分支的工作空间“By creating a branch, you create a space to work without affecting the default branch.” docs.github.com/en/get-started/using-github/github-flow
F2.2合并前改动不进默认分支；改错可撤回“Your changes will not end up on the default branch until you merge your branch.”
F2.3有写权限的团队可不 Fork，直接在原仓库开主题分支“collaborators have push access to a single shared repository and create topic branches…”
F2.4分支名短而达意（画面标签用）“For example, increase-test-timeout or add-code-of-conduct.”
F3 · PR：请求合并的申请页7 条 · 官方文档
#陈述依据（原文摘录）
F3.1PR 是把改动并入项目的提议，合并前讨论与审查“Pull requests are proposals to merge code changes into a project.”
F3.2顺序：分支上提交并推送 → 创建 PR 请求反馈“Commit and push your changes to your branch.” → “Create a pull request to ask collaborators for feedback on your changes.”
F3.3PR 页有自动检查与合并状态（阻塞项、缺少批准）“The Checks tab shows automated tests, builds, and other validations.”
F3.4审查后继续提交，PR 自动更新“Your pull request will update automatically.”
F3.5批准后合并，改动出现在默认分支“Once your pull request is approved, merge your pull request.”
F3.6合并需要写权限：提议者不一定能自己合并“To merge pull requests, you must have write permissions in the repository.” …/reference/pull-request-merges
F3.7合并后删分支；PR 与提交历史不删，可恢复/回退“Your pull request and commit history will not be deleted.” 本集不展开
