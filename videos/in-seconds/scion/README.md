看完应能回答的一个核心问题：Anthropic 为什么放弃 Git 重写了一套源码控制，他们的新做法解决了什么问题、代价与边界又是什么？

逐章怎样推进问题、最后回答什么：

| 章 | 提出的问题 | 本章给出的答案 | 下一问 |
|---|---|---|---|
| 0 现象 | Git 在什么地方先撑不住了？ | 合并量从 2026 年 5 月的约 2,500 次/天涨到 9 月的 3 万次/天，仓库历史近 100 GB、每天约 2,500 万次 CI 检出；git 的离线、完整克隆、去中心化这些长处在这个规模上变成负担 | 既然要重做，那它做成了什么样？ |
| 1 它是什么 | Scion 是什么？ | 工作单元从 commit 变成 changeset（预写式日志里的一条记录，存相对第一个父提交变化的文件列表）；前提是「客户端永远在线」——几乎所有客户端都是智能体和作业 | 具体做了哪几件事？ |
| 2 三个关键做法 | 它怎么解决上面的规模问题？ | 一、服务端提交与合并：没有 push 可做，成本只随改动量增长；二、全部源码控制查询开成 API，CI 不必再检出本地仓库；三、三层缓存（scion-daemon → scion-cache → scion-server）+ 稀疏与虚拟化检出，各层命中率超 99% | 这么做的收益有多大？ |
| 3 收益 | 收益有多大？ | 官方给出的数字：基础设施占用小 200 倍、检出快两个数量级、CI 释放 25% CPU 容量 | 是不是谁都能这么用？ |
| 4 边界 | 是不是谁都能这么用？ | 不是：官方明说不适合替代 git 的一般用途，也没有公开实现可下载 | 所以该怎么记住它？ |
| 5 结论 | 结论 | git 的长处在离线与完整克隆；Scion 的做法是让服务端干重活、让客户端按需取——这套思路可以搬回 git 服务器，不必搬整个系统 | 片尾名单 |
