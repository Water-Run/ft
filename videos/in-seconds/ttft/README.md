## 叙事（第三稿）

前两稿围着「TTFT 是什么」打转：名字五个字就说清了，剩下的只是定义的延伸，没有原理。第三稿把 96 秒用来讲大模型的工作方式：

1. 现象、重要性与名字（open、define，约 31 秒）：提问后光标闪一会儿，第一个字才出现，之后文字一个接一个冒出来；这段等待是对话里体感延迟的主要来源。它叫首 Token 延迟，缩写 TTFT，从发出请求到收到第一段有内容的输出。
2. 模型怎么写（write）：模型每次只写一个 Token，写每一个都要参考前面所有的 Token。
3. 为什么第一个慢、重复提问时的缓存命中（prefill，全片重头）：所以写第一个之前要先读完整个输入，输入的 Token 同时处理，中间结果存进缓存；之后每个新 Token 只在缓存上续一小步；重复提问时，开头相同的部分会命中缓存、不用重新读，首 Token 延迟通常更短（官方文档写「通常改善」，不保证，所以不写数字）。
4. 输入越长越晚（length）：同样的问题附上整个代码文件，要先读的内容多了，第一个 Token 就更晚。
5. 多长算快（scale）：聊天里一秒以内算快，开着深度思考的要几十秒以上；首 Token 延迟短，不代表整段写完快。
6. 收束（close）：第一个 Token 慢，是因为要先读完输入，之后才一个接一个地写。

只在画面上、旁白不讲的信息：再次提问时命中缓存、括号变短（不写秒数）；每个 Token 的间隔交互场景的目标是 10–50 毫秒；长输入的首 Token 延迟是几秒；调得好的部署 0.2–0.5 秒；缓存命中要求开头完全一致。

新名词：Token（d1，先说一小段一小段写出来，再起名）、首 Token 延迟与 TTFT（d3，TTFT 作为缩写，画面展开成全称）；「缓存」旁白里一句带过，画面带注解。依据都在 FACTS：NVIDIA 技术博客（预填充并行处理输入、自回归一次一个 token、KV 缓存）、NVIDIA NIM 指标文档（提示越长 TTFT 越大；端到端 = TTFT + 生成时间）、ClickHouse 指南（2026-07，体感响应、尺度、前缀缓存）、Anthropic 与 OpenAI 的提示缓存文档、Artificial Analysis 方法与榜单（首个答案 token 含思考时间）。

时间线：100 BPM，一小节 2.4 秒。open 0、define 14.4、write 31.2、prefill 40.8（9 小节）、length 62.4、scale 72.0（5 小节）、close 84.0、片尾名单 93.0（3.0 秒）。余量：按估算 open 0.1、define 3.1（给 TTFT 展开留停留）、write 1.2、prefill 2.5、length 1.7、scale 0.7、close 2.1 秒；用 15 句实测替换后最小为 scale 0.5、write 1.0。配音后只调 `gap`/`lead`/`tail`，不改含义。
