# TTFT：事实与依据

取证日期：2026-11-17；2026-11-18 第三稿补八条（标「补」）。对象：流式大语言模型请求的首段输出延迟；不限定模型或产品版本。环境：阅读公开的一手文档，未连接实际推理服务。例子中的数字（两秒、各阶段的长短、请求 A/B/C 的 TTFT 与总时长）都是人为设定，用来演示，不是性能实测；画面标「示例」。

## 对象与解释路径

客户端发送请求，经网络到达服务端，可能排队，再处理输入、生成并返回输出。客户端收到第一段非空输出时结束计时；此后仍可能有输出，直到全文结束。这个客户端口径与从服务端接收请求开始的口径不同。首段可能包含多个 token，界面上看到的文字也不一定与单个 token 一一对应。

| 陈述 | 可复查依据与状态 |
|---|---|
| 客户端口径从发送请求到收到第一个 token 或包含 token 的数据块；计入网络、排队、输入处理与首段生成。 | 已核查：[NVIDIA AIPerf Metrics Reference，Time to First Token](https://docs.nvidia.com/aiperf/v0.13.0/reference/ai-perf-metrics-reference)；[Google Cloud AI infrastructure，Time-to-first-token](https://cloud.google.com/resources/report/content/an-it-leaders-encyclopedia-for-ai-infrastructure?hl=it)。两份均于 2026-11-17 阅读。 |

| TTFT 不等于完整响应时间；排队、输入长度及负载可能影响比较。 | 已核查：[NVIDIA NIM Metrics，TTFT 与 End-to-End Request Latency](https://docs.nvidia.com/nim/benchmarking/llm/1.0.0/metrics.html)；[Google Cloud，Consumption options，Latency](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/deploy/consumption-options)。2026-11-17 阅读。 |
| 服务端的起点和客户端可不同；某些产品还区分思考输出和最终答案的首段。 | 已核查：[NVIDIA Dynamo Glossary，Time-To-First-Token](https://docs.nvidia.com/dynamo/dev/reference/glossary)；[Google Cloud Access metrics，Latency metrics](https://docs.cloud.google.com/gemini/enterprise/docs/access-metrics?hl=en)。2026-11-17 阅读。 |
| 补：写出第一个 token 之前，要先处理完整个输入：预填充阶段并行处理输入 token；各 token 的 key / value 张量存进缓存（KV cache），之后才进入逐个生成的循环。 | 已核查：[NVIDIA Technical Blog，Mastering LLM Techniques: Inference Optimization](https://developer.nvidia.com/blog/mastering-llm-techniques-inference-optimization/)，“Prefill phase or processing the input”（输入 token 并行处理）、“Key-value caching”（可缓存在 GPU 显存，避免重算）；[NVIDIA NIM Metrics](https://docs.nvidia.com/nim/benchmarking/llm/1.0.0/metrics.html)，注意力“需要整段输入序列来计算并建立 KV cache”，之后“迭代生成循环才能开始”。2026-11-18 阅读。 |
| 补：生成阶段是自回归的：一次只生成一个 token，每个新 token 依赖此前所有 token 的状态；缓存让这些状态不必每步重算，每轮追加新的条目，所以之后每个 token 只多做一小步。 | 已核查：同上 NVIDIA Technical Blog，“Decode phase or generating the output”（“generates output tokens autoregressively one at a time”“Each sequential output token needs to know all the previous iterations’ output states”）与“Key-value caching”。“只多做一小步”是对缓存机制的概括，不是原文数字。2026-11-18 阅读。 |
| 补：输入越长，TTFT 越大。 | 已核查：[NVIDIA NIM Metrics](https://docs.nvidia.com/nim/benchmarking/llm/1.0.0/metrics.html)，“The longer the prompt, the larger the TTFT.”；[ClickHouse，LLM inference latency](https://clickhouse.com/resources/engineering/llm-inference-latency)（页内日期 2026-07-29），TTFT 随提示长度上升，因为模型要先摄入全部输入 token。2026-11-18 阅读。 |
| 补：整段回答的端到端延迟 = TTFT + 生成时间（第一个 token 之后到最后一个 token）。 | 已核查：NVIDIA NIM Metrics，“e2e_latency = TTFT + Generation_time”。2026-11-18 阅读。 |
| 补：尺度（交互场景的目标，不是实测）：短提示的交互聊天，TTFT 约一秒以内；调得好的部署约 200–500 ms；很长的上下文，数秒属正常；相邻 token 的间隔（TPOT / ITL）目标 10–50 ms，即每个请求每秒 20–100 个 token。 | 已核查：ClickHouse，LLM inference latency（页内日期 2026-07-29），原文 “Under ~1 s for interactive chat with short prompts”“multi-second is normal for very long contexts”“200–500 ms”“10–50 ms (20–100 tokens/s per request)”；NVIDIA NIM Metrics 将 ITL 定义为相邻 token 的平均间隔，只反映解码部分。2026-11-18 阅读。厂商指南给出的是目标范围，视频里说“要求”“算快”，不写成实测。 |
| 补：「首个答案 token」可以含思考时间：开着深度思考（推理）的模型，第一个答案 token 前要先完成推理；普通 TTFT 在返回推理 token 的模型上可能指第一个推理 token。榜单快照：同一指标（First Answer Token）里，最高推理档位的模型约 40–360 秒，最快的轻量模型 0.18 秒。 | 已核查：[Artificial Analysis，Performance benchmarking methodology](https://artificialanalysis.ai/methodology/performance-benchmarking)（“For reasoning models, this includes the time spent reasoning”“this will be the first reasoning token”；1k / 10k / 100k 输入与多轮会话的平均，Google Cloud us-central1 发起、含网络，5 天内各次中位数的平均，每 6 小时测一次）；[Artificial Analysis，Models leaderboard](https://artificialanalysis.ai/leaderboards/models)（2026-11-18 读取，页面无测量日期，榜单随时间变动）。视频只说“要等几十秒以上”，不点名模型或厂商，不据此评判产品。 |
| 补：对流式聊天界面，首 token 延迟主导体感响应：用户有意识感受到的唯一等待，是第一个 token 出现之前的沉默；优化它比提高吞吐更能提升体感速度。对不面向人的消费者（如 agent），首 token 延迟几乎不重要。 | 已核查：[ClickHouse，LLM inference latency](https://clickhouse.com/resources/engineering/llm-inference-latency)（页内日期 2026-07-29），原文 “TTFT dominates perceived responsiveness because streaming UIs hide generation time behind reading time”“the only wait they consciously experience is the silence before the first token appears”“Optimizing TTFT therefore buys more perceived speed than raising throughput”“The calculus inverts for non-interactive consumers”。2026-11-18 阅读。该页没有用“主要问题”的字样，文案写成“对话里体感延迟的主要来源”，只限交互式对话（对非交互的 agent 几乎不重要，旁白不展开）。 |
| 补：前缀缓存：多个请求共享相同的提示开头时，可以复用已有的缓存（KV cache），省去重复处理这一段输入的时间；命中要求开头完全一致；官方文档称长文档上首 token 延迟通常会改善，但不保证每个请求都命中、都更快；缓存不改变输出。 | 已核查：[Anthropic，Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)（“Cache hits require 100 percent identical prompt segments”“You generally see improved time-to-first-token for long documents”“Prompt caching has no effect on output token generation”）；[OpenAI，Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)（“Prompt caching reuses work when requests share the same prompt prefix”“Reduce the time spent processing input before the response starts”“does not guarantee that every request reuses stored KV tensors or has lower latency”）；ClickHouse（“Prefix caching reuses the KV cache for shared prompt prefixes, collapsing prefill cost”）。2026-11-18 阅读。旁白只说“重复提问时，开头相同的部分会命中缓存，不用重新读，首 Token 延迟通常更短”（“重复提问”指后一次请求与前一次共享相同的提示开头；命中要求开头完全一致）：“通常”对应 Anthropic 的 “generally see improved time-to-first-token for long documents”，不写成保证（OpenAI 明确不保证每个请求都更快），不写命中率、延迟减少的数字、价格与有效期。 |
